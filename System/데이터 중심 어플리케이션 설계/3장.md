## 3.1 데이터베이스를 강력하게 만드는 데이터 구조

세상에서 제일 간단한 DB는 bash 함수 두 개로 만들 수 있다.

```bash
db_set () { echo "$1,$2" >> database; }       # key,value를 파일 끝에 추가
db_get () { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }
```

이게 **로그(log)** 의 본질이다. 쓰기는 파일 끝에 갖다 붙이기만 하니까 엄청 빠르다(append-only). 같은 키를 여러 번 쓰면 옛 값을 안 지우고 그냥 새 줄을 붙이고, 읽을 때 마지막 값을 쓴다.

문제는 읽기다. `db_get`은 전체 파일을 처음부터 끝까지 스캔하니 레코드가 많아지면 O(n)으로 느려진다. 그래서 **색인(index)** 이 필요하다.

> 색인은 공짜가 아니라는 게 이 장 첫 교훈인 듯. 읽기를 빠르게 하려고 부가 구조를 두는 건데, 그 대가로 쓰기가 느려진다. 쓸 때마다 색인도 같이 갱신해야 하니까. 그래서 DB가 모든 칼럼을 자동 색인하지 않는 거고, 어떤 질의가 자주 오는지 보고 사람이 골라야 한다. 회사에서 인덱스 막 추가했다가 쓰기 느려지는 거 겪어봤는데 그 이유가 이거였다.

### 해시 색인

제일 단순한 색인은 인메모리 해시맵이다. 키 → (데이터 파일 안의) 바이트 오프셋을 메모리에 들고 있다가, 조회할 때 오프셋으로 바로 점프해서 값을 읽는다.

<img width="595" height="266" alt="image" src="https://github.com/user-attachments/assets/20174af3-0327-411f-94a4-f0c09a3e7c6c" />

> CSV 유사 형식의 키-값 로그 저장 + 인메모리 해시맵으로 색인. 키마다 파일 안 바이트 오프셋을 들고 있다.

이게 **비트캐스크(Bitcask, Riak의 기본 엔진)** 가 쓰는 방식이다. 모든 키가 메모리에 올라가야 하지만 값은 디스크에 둔다. 키 개수는 적은데 값이 자주 갱신되는 작업부하(예: 키=동영상 URL, 값=재생 횟수)에 잘 맞는다.

append만 하면 디스크가 결국 꽉 찬다. 그래서 로그를 일정 크기 **세그먼트(segment)** 로 자르고, 세그먼트가 차면 닫은 뒤 **컴팩션(compaction)** 을 돌린다. 컴팩션 = 중복 키 버리고 각 키의 최신 값만 남기기. 여러 세그먼트를 백그라운드에서 병합하기도 한다.

<img width="646" height="227" alt="image" src="https://github.com/user-attachments/assets/efb7df55-bb9c-48f7-af77-9be65e865b99" />

> 키-값 갱신 로그를 컴팩션해서 각 키의 최신 값만 유지.

<img width="646" height="301" alt="image" src="https://github.com/user-attachments/assets/76ec7c30-6aa0-46f0-8865-dd0d3ef9089f" />

> 컴팩션과 세그먼트 병합을 동시에 수행. 병합된 세그먼트는 새 파일로 만든다.

실제 구현에서 챙겨야 할 것들:

- **파일 형식**: CSV 말고 바이너리가 더 빠르고 간단
- **레코드 삭제**: 삭제 표시용 특수 레코드(**톰스톤, tombstone**)를 추가하고, 병합 때 실제로 버림
- **고장 복구**: 인메모리 해시맵은 재시작하면 날아가니 복구 필요(Bitcask는 스냅숏을 디스크에 둠)
- **부분 쓰기**: 추가 도중 죽을 수 있어 체크섬으로 손상 부분 탐지
- **동시성 제어**: 쓰기는 보통 단일 스레드(순차 추가), 읽기는 다중 스레드 OK

append-only가 직관과 달리 좋은 이유: 순차 쓰기가 무작위 쓰기보다 훨씬 빠르고(특히 자기 디스크, SSD도), 동시성·고장 복구가 간단하다.

한계도 명확하다. 해시 테이블이 메모리에 다 올라가야 해서 키가 너무 많으면 곤란하고, **범위 질의(range query)** 에 약하다(kitty00000 ~ kitty99999를 한 번에 스캔 못 하고 키마다 따로 조회).

### SS테이블과 LSM 트리

해시 색인의 한계를 푸는 게 SS테이블이다. 세그먼트의 키-값 쌍을 **키로 정렬**해두는 것. 이걸 **SS테이블(Sorted String Table)** 이라 부르고, 각 키는 병합된 세그먼트 안에 한 번만 나온다.

정렬해두면 생기는 장점:

**①** 병합이 효율적이다. 정렬된 파일들이라 **병합 정렬(mergesort)** 방식으로 합칠 수 있다.

<img width="640" height="350" alt="image" src="https://github.com/user-attachments/assets/a7a97edb-d2df-4cd0-ae40-d61d8ad0a94a" />

> 여러 SS테이블 세그먼트를 병합하면서 각 키의 최신 값만 유지.

**②** 전체 색인을 메모리에 안 둬도 된다. 키가 정렬돼 있으니 듬성듬성한 **드문드문 색인(sparse index)** 만 들고, 그 사이는 스캔하면 된다.

<img width="590" height="277" alt="image" src="https://github.com/user-attachments/assets/9b05b623-4acd-4171-93d0-6a1ffed206eb" />

> 인메모리 sparse 색인을 가진 SS테이블. 일부 키의 오프셋만 메모리에.

**③** sparse 색인 구간을 블록으로 묶어 압축해두면 디스크 공간과 I/O 대역폭을 아낀다.

**SS테이블 만드는 법**: 쓰기가 들어오면 일단 인메모리 균형 트리(레드-블랙 트리 등)에 넣는다. 이걸 **멤테이블(memtable)** 이라 한다. 멤테이블이 임계값(수 MB)을 넘으면 디스크에 SS테이블 파일로 통째로 기록. 읽기는 멤테이블 → 최신 세그먼트 → 그다음 세그먼트 순으로 찾는다. 멤테이블이 고장 때 날아가니 디스크에 별도 로그(WAL)를 남겨 복구한다.

이 구조를 쓰는 게 LevelDB, RocksDB, 카산드라, HBase, 그리고 전문 검색의 Lucene이다. 정렬 파일 병합 + 컴팩션을 기반으로 하는 이 엔진을 통틀어 **LSM 트리(Log-Structured Merge-Tree)** 라 부른다.

성능 최적화 포인트:

- **블룸 필터(Bloom filter)**: 존재하지 않는 키를 찾을 때 LSM은 모든 세그먼트를 뒤져야 해서 느린데, 블룸 필터(집합 내용을 근사하는 자료구조)가 "이 키 없음"을 빠르게 알려줘 헛디스크 읽기를 줄인다.
- **컴팩션 전략**: 크기 계층(size-tiered) vs 레벨(leveled). 레벨DB·록스DB는 레벨, HBase는 크기 계층, 카산드라는 둘 다.

### B 트리

로그 구조가 뜨고 있지만, 여전히 제일 널리 쓰이는 색인은 **B 트리(B-tree)** 다. 1970년대에 나와서 거의 모든 관계형 DB의 표준 색인이 됐다. SS테이블처럼 키로 정렬돼 있어 범위 질의에 강한 건 같은데, 설계 철학이 정반대다.

로그 구조가 가변 크기 세그먼트를 순차 기록하는 반면, B 트리는 고정 크기 **페이지/블록(보통 4KB)** 단위로 한 번에 한 페이지를 읽고 쓴다. 디스크가 고정 크기 블록으로 배열되니 하드웨어랑 잘 맞는다.

각 페이지는 다른 페이지를 참조할 수 있고(디스크판 포인터), 이게 페이지 트리를 이룬다.

<img width="660" height="322" alt="image" src="https://github.com/user-attachments/assets/dfc61d3f-a5bb-4075-ac68-dbe03a3d61ff" />

> B 트리 색인을 이용한 키 검색. 루트에서 시작해 범위를 좁혀가며 리프 페이지까지 내려간다.

루트에서 시작해 키 범위를 따라 내려가다 리프 페이지에 닿는다. 한 페이지가 하위 페이지를 참조하는 수를 **분기 계수(branching factor)** 라 하고 보통 수백이다. 키를 추가할 때 페이지에 자리가 없으면 반씩 나눠 두 페이지로 쪼개고 상위를 갱신한다.

<img width="593" height="323" alt="image" src="https://github.com/user-attachments/assets/dd6bd8b3-4cac-4b68-97bd-edf198836446" />

> 페이지 분리로 커진 B 트리. 키 334를 넣으면서 페이지가 둘로 나뉜다.

깊이는 O(log n)이고 보통 3~4단계면 충분하다(분기 계수 500, 4KB 페이지의 4단계 트리면 256TB까지 커버).

**신뢰성**: B 트리는 제자리를 **덮어쓴다(update-in-place)**. 페이지 분리처럼 여러 페이지를 한꺼번에 바꾸다 죽으면 색인이 깨질 수 있어서(고아 페이지 orphan page), **쓰기 전 로그(write-ahead log, WAL, = redo log)** 에 변경을 먼저 기록한 뒤 적용한다. 다중 스레드 동시 접근은 **래치(latch, 가벼운 잠금)** 로 막는다.

최적화: copy-on-write(LMDB), 키 축약, 리프 페이지 인접 배치, 형제 포인터, 프랙탈 트리 등.

### B 트리 vs LSM 트리

| | LSM 트리 | B 트리 |
|---|----------|--------|
| 쓰기 | 빠름 (순차 기록) | 상대적으로 느림 (제자리 덮어쓰기 + WAL) |
| 읽기 | 느릴 수 있음 (여러 세그먼트·SS테이블 확인) | 빠름 |
| 쓰기 증폭 | 낮음 | 높음 (WAL + 페이지) |
| 디스크 공간 | 압축률 좋고 단편화 적음 | 페이지 단편화로 빈 공간 생김 |
| 같은 키 | 여러 세그먼트에 존재 가능 | 한 곳에만 → 트랜잭션 격리에 유리 |

**쓰기 증폭(write amplification)**: DB에 한 번 쓴 게 디스크에는 여러 번 쓰이는 효과. SSD는 덮어쓰기 횟수가 제한돼 있어서 쓰기 증폭이 특히 중요한데, 이 점에서 LSM이 유리하다.

LSM 단점도 있다. 컴팩션이 진행 중인 읽기·쓰기 성능을 갉아먹어서 높은 백분위 응답 시간이 가끔 튄다. 쓰기 처리량이 아주 높으면 컴팩션이 유입 속도를 못 따라가기도 한다(이때는 모니터링 필요). B 트리는 키가 색인 한 곳에만 있어서 강력한 트랜잭션 격리를 구현하기 쉽다.

> 일하는 PostgreSQL은 B 트리, 카산드라/RocksDB 쪽은 LSM이라는 걸 이제야 구조로 이해했다. "쓰기 많고 SSD면 LSM, 읽기·트랜잭션 격리 중요하면 B 트리" 정도로 기억해두면 될 듯. 어느 쪽이 정답은 아니고 작업부하 보고 고르는 거. 빠른 규칙은 없으니 실제 부하로 테스트해보는 게 맞다.

### 기타 색인 구조

- **기본키 색인 vs 보조 색인(secondary index)**: 기본키는 로우를 고유 식별. 보조 색인은 키가 고유하지 않아도 됨(같은 키에 여러 로우). 조인할 때 결정적인 역할. `CREATE INDEX`로 만든다.
- **색인 안에 값 저장하기**: 색인의 값이 가리키는 대상이 두 종류다.
  - **힙 파일(heap file)** 참조: 실제 로우는 한 곳(힙)에 두고 색인은 위치만 가리킴. 보조 색인이 여러 개여도 데이터 중복을 피함.
  - **클러스터드 색인(clustered index)**: 색인 안에 로우 데이터를 직접 저장 (MySQL InnoDB의 기본키)
  - **커버링 색인(covering index)**: 일부 칼럼만 색인 안에 저장해서 색인만으로 질의 응답
- **다중 칼럼 색인**:
  - **결합 색인(concatenated index)**: 여러 칼럼을 단순히 이어붙임(예: (성, 이름)). 순서가 중요해서 (성)만으로는 찾아도 (이름)만으로는 못 찾음.
  - **다차원 색인**: 위경도 같은 공간 데이터용. 공간 채움 곡선(space-filling curve)으로 1차원 변환 후 B 트리, 또는 R 트리(PostGIS).
- **전문 검색과 퍼지 색인**: 오타·유사어까지 찾는 fuzzy 질의. Lucene은 편집 거리(edit distance) 내 단어를 찾으려고 SS테이블 비슷한 구조 + 레벤슈타인 오토마톤(유한 상태 오토마톤)을 쓴다.

### 모든 것을 메모리에 보관

램이 싸지면서 데이터셋 전체를 메모리에 두는 **인메모리 DB**도 현실적이 됐다. VoltDB, MemSQL, Oracle TimesTen, RAMCloud, Redis, Couchbase 등.

> 인메모리가 빠른 진짜 이유가 의외였다. "디스크를 안 읽어서"가 아니다. 디스크 기반 엔진도 OS가 블록을 메모리에 캐싱해서 결국 메모리에서 읽으니까. 진짜 이유는 디스크에 기록하려고 자료구조를 인코딩하는 오버헤드를 피할 수 있어서라고 이해했다. Redis가 우선순위 큐·셋 같은 걸 쉽게 제공하는 것도 메모리에 다 들고 있어서 구현이 단순하기 때문.

메모리보다 데이터셋이 커지면 **anti-caching**: 가장 오래 안 쓴 데이터를 디스크로 내보내고 다시 접근하면 메모리에 올린다(OS 스왑이랑 비슷하지만 레코드 단위라 더 효율적). 앞으로 NVM(비휘발성 메모리)이 퍼지면 저장소 설계가 또 바뀔 것.

## 3.2 트랜잭션 처리나 분석?

DB가 다루는 작업부하는 크게 둘로 갈린다.

| 특성 | OLTP (트랜잭션 처리) | OLAP (분석) |
|------|---------------------|-------------|
| 읽기 패턴 | 질의당 적은 레코드, 키 기준 | 많은 레코드에 대한 집계 |
| 쓰기 패턴 | 임의 접근, 사용자 입력 저장 | 대량 불러오기(bulk import, ETL) / 이벤트 스트림 |
| 주 사용자 | 웹 앱을 통한 최종 사용자 | 의사결정 지원용 내부 분석가 |
| 데이터 표현 | 최신 상태(현재 시점) | 시간 지나며 쌓인 이벤트 이력 |
| 데이터셋 크기 | GB ~ TB | TB ~ PB |

**OLTP(online transaction processing)**: 사용자 대면이라 대량 요청이 오고, 키로 적은 레코드만 만진다. **OLAP(online analytic processing)**: 분석가가 원시 데이터를 반환받는 게 아니라 수많은 레코드를 스캔해 집계(카운트·합·평균)한다. "1월 각 매장 총 수익은?" 같은 비즈니스 인텔리전스 질의.

### 데이터 웨어하우징

처음엔 둘 다 같은 DB로 했는데, 분석 질의가 OLTP 성능을 갉아먹어서 분리하게 됐다. **데이터 웨어하우스(data warehouse)** = 분석 전용 별도 DB. 회사 내 여러 OLTP 시스템의 읽기 전용 복사본이다. OLTP에서 데이터를 추출(Extract)하고 분석 친화적 스키마로 변환(Transform)해 적재(Load)하는 과정이 **ETL**.

<img width="621" height="379" alt="image" src="https://github.com/user-attachments/assets/ea1db6db-9196-4335-b1d6-53f9c62ff897" />

> 데이터 웨어하우스에 대한 ETL의 간략한 개요. 여러 OLTP DB에서 추출·변환·적재해 웨어하우스로 모은다.

제품으로는 Teradata, Vertica, SAP HANA, ParAccel, Amazon RedShift, 그리고 SQL-on-Hadoop 계열(Hive, Spark SQL, Impala, Presto, Tajo, Drill).

> ETL이 회사에서 하던 배치/적재 작업이랑 정확히 같은 그림이었다. 증분 커서(incremental cursor) 잡아서 변경분만 퍼오는 것도 결국 이 Extract 단계 최적화인 셈. OLTP를 직접 분석으로 두드리면 운영 DB가 느려지니까 읽기 전용 복사본으로 빼는 거고.

### 분석용 스키마: 별 모양 vs 눈꽃송이

분석 쪽은 데이터 모델 다양성이 적고 보통 **별 모양 스키마(star schema, 차원 모델링)** 를 쓴다. 중심에 **사실 테이블(fact table)** 이 있고, 각 로우가 특정 시각의 이벤트 하나(예: 고객의 제품 구매)다. 사실 테이블 칼럼은 속성값이거나, **차원 테이블(dimension table)** 을 가리키는 외래 키다. 차원 = 이벤트의 누가/언제/어디서/무엇을/어떻게/왜.

<img width="624" height="522" alt="image" src="https://github.com/user-attachments/assets/53bd0a1e-5813-4b36-849c-e18218a263eb" />

> 데이터 웨어하우스의 별 모양 스키마 예제. 중앙 fact_sales 테이블이 dim_product / dim_store / dim_date / dim_customer / dim_promotion을 외래 키로 참조.

테이블 관계를 그리면 사실 테이블이 가운데 있고 차원들이 별처럼 둘러싸서 "별 모양". 차원을 더 잘게 정규화한 변형이 **눈꽃송이 스키마(snowflake schema)** 인데, 별 모양이 분석가가 다루기 더 쉬워서 보통 별 모양을 선호한다. 사실 테이블은 칼럼이 100개 넘는 경우도 흔하다.

## 3.3 칼럼 지향 저장소

사실 테이블이 페타바이트급이면 저장·질의가 골치다. 분석 질의는 보통 칼럼 4~5개만 건드리는데(`SELECT *`은 거의 안 씀), 로우 지향 저장소는 한 로우의 모든 칼럼(100개+)을 디스크에서 통째로 읽어야 해서 낭비가 크다.

**칼럼 지향 저장소(column-oriented storage)** 의 발상은 단순하다. 한 로우의 값들을 같이 두지 말고, **각 칼럼의 모든 값을 함께** 저장한다. 그러면 질의에 쓰는 칼럼 파일만 읽으면 된다.

<img width="700" height="411" alt="image" src="https://github.com/user-attachments/assets/c7ce38af-494a-48b5-9aae-ace5a6b3964a" />

> 관계형 데이터를 로우가 아닌 칼럼 단위로 저장. 칼럼마다 별도 파일, 같은 순서로 정렬돼 있어 N번째 항목끼리 같은 로우.

배치 전제는 "각 칼럼 파일의 로우 순서가 모두 같다"는 것. 그래서 23번째 로우를 복원하려면 각 칼럼 파일의 23번째를 모으면 된다. (Parquet은 구글 Dremel 기반으로 문서 모델도 지원하는 칼럼 형식)

### 칼럼 압축

칼럼은 같은 값이 반복되는 경향이 강해서 압축이 잘 먹는다. 대표적인 게 **비트맵 부호화(bitmap encoding)**.

<img width="610" height="395" alt="image" src="https://github.com/user-attachments/assets/4a384bd0-2d4e-4c4a-8255-32b4a0da3903" />

> 압축한 단일 칼럼의 비트맵 색인 저장소. 고유 값마다 비트맵 하나, 값이 듬성하면 런 렝스 부호화(run-length encoding)로 더 압축.

칼럼의 고유 값 수가 로우 수보다 훨씬 적을 때(예: 제품 10만 종) 고유 값마다 비트맵을 만든다. 비트맵이 듬성하면(sparse) 런 렝스 부호화로 더 줄인다. 이런 비트맵 색인은 `WHERE x IN (...)`(비트맵 OR), `WHERE x=a AND y=b`(비트맵 AND) 같은 질의에 아주 잘 맞는다.

**메모리 대역폭과 벡터화 처리**: 디스크→메모리 대역폭만 병목이 아니라, 메모리→CPU 캐시 대역폭도 중요하다. 압축된 칼럼 덩어리를 CPU L1 캐시에 꽉 채워 함수 호출 없는 타이트 루프에서 돌리고, 비트 AND/OR을 압축 상태 그대로 연산하는 걸 **벡터화 처리(vectorized processing)** 라 한다. SIMD 명령도 활용.

### 칼럼 저장소의 순서 정렬과 쓰기

칼럼 저장이라도 로우 순서를 도입해 색인처럼 쓸 수 있다. 자주 쓰는 정렬 키(예: date_key)로 정렬해두면 시간 범위 질의가 빨라지고, 정렬된 칼럼은 같은 값이 연달아 나와 압축도 더 잘 된다. C-Store/Vertica는 같은 데이터를 **여러 정렬 순서로 복제**해서 질의 패턴마다 맞는 버전을 쓴다(로우 지향의 보조 색인 여러 개와 비슷한 발상).

쓰기는 까다롭다. 압축·정렬된 칼럼에 제자리 갱신(update-in-place)은 불가능하다(중간에 끼우면 모든 칼럼 파일을 재작성). 그래서 여기서도 **LSM 트리 방식**을 쓴다. 쓰기는 인메모리 정렬 구조에 모았다가 충분히 쌓이면 디스크 칼럼 파일에 병합.

### 집계: 데이터 큐브와 구체화 뷰

분석 질의는 COUNT/SUM/AVG 같은 집계를 반복한다. 자주 쓰는 집계를 매번 원시 데이터로 계산하면 낭비라, 결과를 캐싱하는 게 **구체화 뷰(materialized view)** 다. 가상 뷰(virtual view)는 단순 질의 단축키지만, 구체화 뷰는 질의 결과를 디스크에 실제로 복사해둔다(원본 바뀌면 갱신 필요해서 쓰기 비싼 OLTP에선 잘 안 씀, 읽기 위주 웨어하우스에선 합리적).

특수한 구체화 뷰가 **데이터 큐브(data cube, OLAP 큐브)** 다. 여러 차원으로 그룹화한 집계 테이블.

<img width="612" height="307" alt="image" src="https://github.com/user-attachments/assets/f7e32428-e3e0-4a2e-a154-f31acb9c0e63" />

> 합으로 데이터를 집계한 2차원 데이터 큐브. 한 축은 날짜, 한 축은 제품. 각 셀이 그 조합의 집계값.

미리 계산해둬서 해당 질의는 매우 빠르지만, 원시 데이터만큼 유연하진 않다(큐브에 없는 차원으로는 못 쪼갬). 그래서 웨어하우스는 원시 데이터를 최대한 유지하고, 큐브는 특정 질의 가속용으로만 쓴다.

## 3.4 요약

저장소 엔진은 크게 두 범주.

- **OLTP (트랜잭션 최적화)**: 사용자 대면, 키로 적은 레코드, 디스크 탐색이 병목. 색인 두 학파가 있다.
  - **로그 구조 (append-only, 절대 제자리 갱신 안 함)**: Bitcask, SS테이블, LSM 트리, LevelDB, 카산드라, HBase, Lucene
  - **제자리 갱신**: B 트리 (대부분 관계형 DB + 많은 비관계형)
  - 로그 구조의 핵심은 임의 쓰기를 순차 쓰기로 바꿔 쓰기 처리량을 끌어올린 것.
- **OLAP (분석 최적화)**: 분석가가 대량 레코드를 스캔해 집계. 디스크 대역폭이 병목. **칼럼 지향 저장소**가 답(필요한 칼럼만 읽고, 압축·벡터화로 가속).
