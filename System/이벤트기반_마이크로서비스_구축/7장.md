
# 7장. 상태 저장 스트리밍

다루는 주제
- 구체화 상태 vs 상태 저장소
- 체인지로그 이벤트 스트림
- 내부 상태 저장소 (전역 구체화, 핫 레플리카, 확장/복구)
- 외부 상태 저장소 (장단점, 확장/복구 3전략)
- 재구성 vs 마이그레이션
- 트랜잭션과 실제로 한 번(effectively once) 처리

## 이 장 핵심

대부분의 애플리케이션은 상태가 필요하므로 상태 저장 스트리밍이 EDM의 가장 중요한 근간이다. 

갈림길은 두 개 — 상태를 처리기와 같은 컨테이너에 두느냐(내부), 네트워크 건너 외부 스토리지에 두느냐(외부). 

그리고 어느 쪽이든 상태의 백업/복구는 체인지로그가 담당한다. 

후반부의 "실제로 한 번 처리"는 결국 오프셋 커밋·상태 업데이트·출력 생산을 어떻게 원자적으로 묶느냐의 문제고, 트랜잭션 브로커가 있으면 쉽고 없으면 멱등적 쓰기 + 중복 제거로 만들어내야 한다.

---

## 7.1 상태 저장소, 이벤트 스트림에서 상태 구체화

용어 정의
- 구체화(된) 상태(materialized state) : 소스 이벤트 스트림의 이벤트를 투영(projection)한 것. **불변**
- 상태 저장소(state store) : 서비스가 비즈니스 상태를 저장하는 곳. **가변**
- 구체화 상태는 공통 비즈니스 엔티티로 사용, 상태 저장소에는 비즈니스 상태와 중간 계산 결과 저장

상태를 저장/접근하는 두 가지 방법
- **①** 처리기와 동일한 컨테이너의 메모리/디스크에 내부적으로 저장 → 내부 상태 저장소
- **②** 처리기 컨테이너 밖의 외부 스토리지 서비스에 네트워크로 저장 → 외부 상태 저장소

> 내부 상태 저장소와 외부 상태 저장소 구성도

- 내외부 선택은 비즈니스 역할과 기술 요건에 따라. 그 전에 체인지로그의 역할부터 이해할 것

## 7.2 체인지로그 이벤트 스트림에 상태 기록

- 체인지로그 : 상태 저장소에 담긴 데이터의 변경 사항을 모두 기록한 것. 테이블-스트림 이원성의 스트림 쪽
- 마이크로서비스 인스턴스 **외부에** 유지되는 영구적인 상태 사본 → 상태 재구성 + 이벤트 처리 진행의 체크포인트 수단

> **TIP)** 체인지로그에는 이전 처리 결과가 저장되어 있어서 실패한 서비스를 재구성하는 작업을 최적화할 수 있다. 복구 처리기가 모든 입력 이벤트를 일일이 재처리할 필요가 없다.

> 체인지로그에서 상태 저장소를 복구

- 여느 스트림처럼 브로커에 저장. 최근 키/값 쌍만 있으면 재구성 가능 → **컴팩션 필수**
- 내부 상태 저장소에서 특히 고성능으로 확장/복구 가능 : 새 인스턴스는 자기에 해당하는 체인지로그 파티션에서 데이터를 로드하기만 하면 됨
- 카프카 스트림즈 같은 프레임워크는 기본 제공, 직접 구현도 가능. **기본 프로듀서/컨슈머 클라이언트는 체인지로그/상태 저장 전혀 미지원**

## 7.3 내부 상태 저장소에 상태 구체화

- 내부 상태 저장소 : 비즈니스 로직과 동일한 컨테이너/VM에 동거. 인스턴스가 존재할 때만 의미 있음
- 각 인스턴스는 할당된 파티션의 이벤트만 구체화, 저장소 내부에서 파티션별로 논리 분리
  - 리밸런스로 회수된 파티션의 상태는 그냥 삭제 가능
  - 구체화 상태는 파티션 소유 인스턴스에만 존재 → 리소스 누수, 진실 공급원 쪼개짐 방지
  - 파티션이 새로 할당되면 스트림/체인지로그에서 재구성
- 주로 RocksDB 같은 고성능 키/값 저장소 사용. 로컬 SSD 최적화 → 메인 메모리 초과 데이터 세트도 신속 처리

### 7.3.1 전역 상태 구체화

- 전역 상태 저장소 : 내부 상태 저장소의 특수 형태. 할당 파티션뿐 아니라 **모든 파티션**을 구체화 → 인스턴스마다 이벤트 데이터 전체 사본
- 유용한 경우 : 전체 데이터 세트가 필요한 경우. 자주 쓰이지만 좀처럼 안 바뀌는 소규모 데이터 세트로 구성
- 각 인스턴스가 전체 사본을 가져서 출력 중복/비확정적 결과 가능 → **이벤트 기반 로직을 일으키는 동인(driver)으로는 비효과적**. 공통 데이터 검색이나 지수(dimension) 테이블 정도만

### 7.3.2 내부 상태 사용 시 장점

- **개발자가 직접 확장할 필요 없음** : 확장 요건을 브로커 + 컴퓨팅 리소스 클러스터에 위임. 인스턴스 수만 조절하면 되니 확장 단위가 단일함. 개발팀은 비즈니스 로직에 전념
  - 단, 클라우드의 로컬 디스크는 물리 부착이 아닐 수 있음(NAS가 로컬 행세) → 성능 요건 확인 필수
- **고성능 디스크 기반 옵션** : 모든 상태를 메모리에 못 두는 경우(예산 문제) 로컬 디스크가 준수한 대안
  - SSD + RocksDB 랜덤 읽기 지연 약 65μs → 스레드당 초당 최대 ~15,400 순차 액세스. 인메모리는 초당 수백만 건
- **NAS를 사용할 정도로 유연** : 가능하지만 읽기/쓰기 지연이 상당히 증가
  - 이벤트는 순서 유지를 위해 한 번에 하나씩 처리 → 단일 스레드가 응답 대기 → 처리량 급감 (RocksDB 15.4k 요청/s가 1ms RTT면 939 요청/s로)
  - 장점 : 상태가 볼륨에 유지되므로 노드 재활성화 시 디스크만 다시 붙이면 중단 지점부터 재개. 체인지로그 재구성 불필요, 온디맨드 노드처럼 유연하게 이동 가능

### 7.3.3 내부 상태의 단점

- **런타임에 정의된 디스크만 사용 가능** : 볼륨 변경엔 서비스 중지→조정→재시작. 볼륨 축소는 대부분 불가(늘리기만 가능)
- **디스크 공간 낭비** : 트래픽 패턴 따라 순환 스토리지 볼륨 필요. 피크 기준으로 상시 확보하면 바이트 단위 과금하는 외부 서비스 대비 낭비

### 7.3.4 내부 상태의 확장 및 복구

- 확장(새 인스턴스)과 복구(실패 인스턴스 재생성)는 상태 복구 관점에서 동일한 프로세스 : 새 이벤트 처리 전에 토폴로지에 정의된 상태를 전부 구체화해야 함. 가장 빠른 방법 = 체인지로그 토픽 재로드

**핫 레플리카 사용**
- 구체화 상태 레플리카는 보통 파티션당 1개지만, 더 추가 가능 (카프카 스트림즈에 내장, 간단한 설정)
- 복제 계수 2면 각 파티션이 리더 1회 + 레플리카 1회, 총 2회 구체화. 레플리카는 자체 오프셋을 리더와 동기화
- 리더가 갑자기 종료되면 → 파티션 어사이너가 **핫 레플리카 보유 인스턴스에 소유권 우선 부여** → 즉시 처리 재개 (무중단 운영)
- 재개 후 최소 레플리카 수 유지를 위해 체인지로그에서 새 핫 레플리카를 생성해 나머지 인스턴스에 추가

**체인지로그에서 복구 및 확장**
- 새 인스턴스가 그룹에 조인하면 할당된 상태 저장 파티션을 체인지로그에서 그대로 재로드
- 로드 동안 새 이벤트를 처리하면 잘못된 비확정적 결과 → 처리 금지

**입력 이벤트 스트림에서 복구 및 확장**
- 체인지로그가 없으면 할당된 입력 파티션 맨 처음부터 전부 재소비해서 복구. 정확히 순서대로 소비/처리 + 후속 출력 생산

> **WARNING** 완전 재처리 중에 생산된 이벤트가 어떤 영향을 미칠지 확인할 것. 다운스트림 컨슈머가 멱등 처리하거나 중복으로 보고 제거해야 할 수도 있다.

- 체인지로그 복구보다 훨씬 오래 걸림 → 입력 스트림 보존 기간이 짧고, 중복 출력이 문제 안 되고, 엔티티 스트림이 흡수된 단순 토폴로지에서만 권장

## 7.4 외부 상태 저장소에 상태 구체화

- 컨테이너/VM 외부, 대개 동일 로컬 네트워크에 위치. RDB, 문서형 DB, 루씬 기반 검색, 고가용성 분산 키/값 저장소 등
- 공통 스토리지 플랫폼에 둘 수는 있지만 **데이터 세트 자체는 다른 구현체와 논리적으로 분리**
- 마이크로서비스끼리 구체화 상태를 공유하는 건 흔한 안티패턴 : 상관없는 제품·특성이 단단히 결합됨

> **WARNING** 다른 마이크로서비스가 상태에 직접 접근하도록 공유하지 말 것. 모든 마이크로서비스는 자신의 상태 사본을 반드시 구체화해야 한다. 데이터 용량과 처리 비용이 더 드는 건 감수해야 한다.

> 이 안티패턴이 우리 회사에선 "서비스 간 DB 직접 조회"라는 이름으로 산다. MSA인데 남의 스키마를 조인하는 코드가 남아 있으면 결국 이 장에서 말하는 결합이 그대로 생긴다.

### 7.4.1 외부 상태 저장소의 장점

- **완전한 데이터 지역성** : 모든 인스턴스가 전체 구체화 데이터에 접근 가능 (구체화는 각자 할당 파티션 기준)
  - 검색, 외래 키 관계형 쿼리, 지리공간 쿼리에 파티션 지역성 불필요
- **기술** : 이미 조직에 익숙한 기술 → 프로덕션 배포 시간/노력 절약. FaaS(9장)와 기본 프로듀서/컨슈머 패턴(10장)에 좋은 후보

> **TIP** 여러 인스턴스에서 일관된 결과를 유지하려면 '쓰기 후 읽기(read-after-write)' 보장이 강력한 상태 저장소를 이용할 것.

### 7.4.2 외부 상태의 단점

- **여러 기술 관리 부담** : 비즈니스 로직과 독립적으로 관리/확장됨 → 소유자가 리소스 배정, 확장 정책, 모니터링을 직접. 관리형 서비스로 분산 가능

> **NOTE** 각 팀은 외부 상태 저장소를 완전히 관리해야 한다. 책임을 다른 팀에 전가하면 기술적인 상호 의존성이 생기므로 절대 금물. 수용 가능한 외부 데이터 서비스 목록과 관리/확장 방법을 정리해두면 팀마다 자체 솔루션을 발굴할 필요가 없다.

- **네트워크 지연으로 인한 성능 저하** : 로컬 메모리/디스크보다 지연이 김. 캐싱/병렬화로 줄일 수 있지만 복잡도 + 메모리/CPU 비용 증가. 단순히 스레드 블로킹하고 응답을 기다리는 경우도 많음
- **서비스 이용료** : 비슷한 용량이면 외부가 더 비쌈. 트랜잭션 수/페이로드 크기/보존 기간 과금. 부하 급증 대비 오버-프로비저닝 필요할 수도
- **완전한 데이터 지역성의 역설** : 처리량이 제각각인 여러 처리기/파티션에서 데이터가 비롯되므로, 어느 인스턴스가 집합적 공유 상태에 어떻게 관여했는지 추론/디버깅이 대단히 어려움
  - 각 인스턴스가 독립적인 스트림 시간으로 작동 → 경합 조건, 비확정적 동작 주의
  - ex) 다른 인스턴스가 아직 채우지 않은 외래 키로 조인하는 인스턴스 → 재처리하면 조인이 성공할 수도. 결과가 비확정적이고 재연 불가능

### 7.4.3 외부 상태 저장소의 확장 및 복구

- 마이크로서비스 자체의 확장/복구는 쉬움 : 새 인스턴스에 인증정보만 추가
- 하부 상태 저장소의 확장/복구는 기술에 완전히 종속 → 지침서 + 수용 가능한 서비스 목록 필요. 일반화하면 3가지 전략

| 전략 | 방법 | 특징 |
|---|---|---|
| 소스 스트림 사용 | 모든 입력 스트림의 오프셋을 초기 시점으로 되돌려 재소비 | 중단 시간 최장, 재연이 가장 쉬움, 브로커 영구 스토리지에만 의존. 사실상 풀 리셋 → 출력 이벤트도 모두 재생성됨을 유의 |
| 체인지로그 사용 | 외부 저장소도 체인지로그를 두고 재구성 | 대부분은 브로커 체인지로그에 의존하지 않지만 못 쓸 건 없음. 컨슈머는 처리 재개 전에 전체 상태 재구성 필요 |
| 스냅샷 사용 | 저장소 자체 백업/복구(원클릭) 활용 | 상태가 멱등적이면 오프셋을 스냅샷 몇 분 전으로 세팅해 유실 방지(at-least-once 보장). 멱등이 아니면 컨슈머 오프셋을 데이터에 넣어 함께 보관 → 스냅샷 생성 시점의 오프셋으로 복구 |

> **WARNING** 소스 스트림이나 체인지로그에서 외부 저장소를 재구성하는 작업은 네트워크 지연 때문에 아주 오래 걸릴 수 있다. 이 상황도 SLA에 문제가 없는지 꼭 확인할 것.

## 7.5 재구성 대 상태 저장소 마이그레이션

- 새 비즈니스 요건 반영으로 상태 저장소 데이터 구조를 바꿔야 하는 경우 : 재구성 또는 마이그레이션

### 7.5.1 재구성

- 가장 일반적인 방법. 절차 : 서비스 중지 → 컨슈머 오프셋을 초기 시점으로 리셋 → 체인지로그/외부 저장소의 중간 상태 삭제 → 새 버전 시작해 입력 스트림에서 상태 재구성
- 새 로직에 따라 상태가 정확히 구성되고 새 출력 이벤트도 다운스트림에 전파됨 (비즈니스 로직/포맷이 바뀌었으니 중복이 아님)
- 전제 : 필요한 입력 스트림의 **모든 이벤트가 존재**해야 함. 입력 데이터 세트에 전적으로 의존한다면 소스 데이터를 언제라도 구현체 외부에서 쓸 수 있게 만들어야 함
- 입력 이벤트에만 존재하는 필드를 새로 추출해야 하는 요건은 재구성만이 유일한 길

> **TIP** 재구성 시간이 꽤 오래 걸릴 수 있으니 SLA 문제를 확인할 것. 재구성의 가장 큰 장점은 서비스 실패로 상태가 전부 유실된 경우에 필요한 복구 프로세스, 즉 재해 복구 대비 상태를 테스트해볼 수 있다는 점.

### 7.5.2 마이그레이션

- 거대한 상태 저장소는 재구성 시간이 길고 데이터 전송 비용이 비쌈 → 변경이 단순하면(기본값 null인 널 허용 컬럼 추가 등) 마이그레이션으로 처리하고 재배포
- 니즈와 변경 데이터가 복잡할수록 리스크 증가 : DB 마이그레이션은 비즈니스 로직의 일부가 아니므로 완전 재구성에는 없는 **비정합성이 스며들 수 있음**. 테스트로 못 잡으면 정합성 안 맞는 데이터가 축적
- 마이그레이션하기로 했다면 실제 업무에 가까운 테스트 데이터 세트로 철저히 검증하고 재구성과 비교할 것

## 7.6 트랜잭션과 실제로 한 번 처리

- 실제로 한 번 처리(effectively once processing) : 프로듀서/컨슈머/브로커 실패와 무관하게 단일 진실 공급원에 반영된 모든 업데이트를 일관되게 적용
- "정확히 한 번(exactly once)"이라 부르기도 하지만 정확한 표현이 아님 — 동일 데이터를 여러 번 처리하되(컨슈머 실패, 복구 등으로 오프셋 커밋 없이 스트림 시간만 증가) 결과가 한 번 반영된 것과 같게 만드는 것. 처리 과정에서 외부 엔드포인트 발행 등 부수 효과 코드는 여러 번 실행될 수 있음
- 구성 요소
  - **멱등적 쓰기(idempotent writes)** : 이벤트를 스트림에 한 번만 쓰는 기능. Kafka/Pulsar 등에서 지원 → 쓰기 도중 실패 후 재시도해도 중복 이벤트 없음
  - **트랜잭션** : 카프카는 완전한 트랜잭션 지원(집필 시점 펄사는 개발 중). RDB처럼 다수의 이벤트를 다수의 스트림에 원자적으로 쓰기 가능

> **TIP** 트랜잭션은 아주 강력한 기능이라서 아파치 카프카가 경쟁자들보다 중요한 강점을 지니게 됐다. 트랜잭션이 없다면 원자적 이벤트 생산을 위해 복잡한 리팩터링이 불가피하다.

### 7.6.1 예제: 재고 회계 서비스

- 품목 재고가 부족하면 알림 이벤트를 발행하는 서비스. 입/출고 수량으로 현재 가용 재고 산출
- 판매/손실은 재고 차감 이벤트, 수취/반품은 재고 증가 이벤트 → 동일 스트림에 기록
- 각 입력 이벤트가 한 번 이상 적용되거나 누락되면 계산이 틀어짐 → **실제로 한 번 적용해서 집계**해야 하는 전형적 케이스

### 7.6.2 클라이언트-브로커 트랜잭션으로 실제로 한 번 처리

- 트랜잭션 지원 브로커면 어렵지 않음 : **출력 이벤트 + 체인지로그 기반 내부 상태 업데이트 + 컨슈머 오프셋 증가**를 하나의 원자적 트랜잭션으로
  - 단, 세 업데이트가 전부 브로커의 이벤트 스트림 안에 저장될 경우에만 가능
- 프로듀서에 치명적 장애 발생 시 브로커는 트랜잭션의 이벤트를 일체 커밋하지 않고, 컨슈머는 커밋 안 된 이벤트를 처리하지 않음 (오프셋 순서를 따르므로 트랜잭션 완료까지 블로킹 후 재개)
- 일시적 오류면 프로듀서가 트랜잭션을 단순 재시도 (멱등적 작업)
- 치명적 예외면 다른 인스턴스로 대체하고 체인지로그에서 복구. 컨슈머 그룹 오프셋도 마지막 정상 위치로 리셋
- 프로듀서 복구 시 새 트랜잭션 시작, 브로커는 이전 미완료 트랜잭션을 실패 처리 후 정리. 메커니즘은 브로커 구현체마다 상이하므로 제품 특성 숙지

### 7.6.3 클라이언트-브로커 트랜잭션 없이 실제로 한 번 처리

- 트랜잭션 없는 브로커에서도 가능하지만 작업이 늘어남
  - **①** 업스트림이 실제로 한 번을 보장 못 하면 중복 레코드를 찾아 걸러내야 함
  - **②** 이벤트 처리가 시스템 상태에 한 번만 반영되도록 상태 + 오프셋을 하나의 로컬 트랜잭션으로 업데이트

> **WARNING** 사후에 중복 제거(deduplication)를 하려고 애쓰지 말고 멱등적 쓰기를 지원하는 브로커/클라이언트를 이용하는 편이 낫다. 후자는 모든 컨슈머에 쉽게 적용되지만 전자는 비용도 많이 들고 사용하기도 까다롭다.

**중복 이벤트 생성 시나리오**
- 프로듀서가 브로커의 ACK를 받지 못해 재시도 : 타임스탬프·데이터는 동일하지만 오프셋은 새로 할당된 이벤트 생성
- 프로듀서가 발행한 이후, 컨슈머 오프셋 업데이트 전에 실패 : 재가동되면 이전 작업 반복 → 논리적으로 동일하지만 타임스탬프는 새로 찍힌 사본 생성

> **NOTE** 멱등적 생산은 위 두 가지 실패/재시도 장애를 어느 정도 해결한다. 하지만 비즈니스 로직 오류 때문에 발생한 중복은 어쩔 도리가 없다.

**중복 이벤트 식별**
- 중복은 영향도가 작아 무시해도 좋은 경우가 대부분. 아니라면 식별 방법 필요
- 방법 : 중복 이벤트의 해시값이 동일하게 계산되도록 프로듀서가 이벤트마다 고유 ID 생성
  - 해시 함수는 키/값/생성 시간 등 내부 속성으로 계산 → 대규모 데이터 도메인엔 잘 맞지만 논리적으로 동등한 이벤트엔 부적합
- 고유 ID 생성 예 : 계좌·금액·일시가 명시된 은행 이체 / 제품·구매자·결제 금액·PG가 명시된 전자상거래 주문 / orderId가 있는 재고 차감
  - 공통점 : **카디널리티(고유성)가 아주 높은 요소들의 조합** → ID 중복 가능성 거의 없음
- 중복 제거 ID(dedupe ID)는 이벤트와 함께 생성하는 편이 컨슈머 소비 시점 생성보다 나음 (모든 컨슈머에게 배포 용이)

> **WARNING** 파티션 지역성이 보장되지 않기 때문에 키 없이 생성된 이벤트는 중복을 방지하기가 매우 어렵다. 가능한 한 이벤트를 키로 생성해서 파티션 지역성을 추구하고 멱등적으로 기록할 것.

**중복 방지**
- 실제로 한 번 소비하는 컨슈머는 중복을 찾아 폐기 + 멱등 작업 수행, 또는 멱등적 프로듀서의 스트림에서 소비해야 함
- 각 컨슈머가 이미 처리한 dedupe ID의 상태 저장소를 관리해야 하므로 비용 큼. 완벽 제거는 무기한 색인이 필요 → 실제로는 **특정 시간대/오프셋 구역에 한해** 최후의 수단으로 적용

> **TIP** 중복 제거 저장소는 TTL이나 최대 캐시 크기 설정, 주기적 삭제로 가급적 작게 유지할 것. 구체적인 설정은 중복 이벤트에 대한 애플리케이션의 민감도와 영향도에 따라 다르다.

- 파티션 간 중복 제거는 비용이 터무니없이 비쌈 → **단일 파티션 내에서만** 수행 권장. 키 있는 이벤트는 동일 파티션에 일관 분산되므로 유리

<img width="617" height="341" alt="image" src="https://github.com/user-attachments/assets/0a31e123-d462-4ad1-be94-e17a9828d15d" />

> 저장된 상태에 따라 중복 제거. 소비 → 중복 필터링 → 누락 시 dedupe 테이블에 추가(TTL) → 비즈니스 로직에 전파

> **TIP** 중복 제거 저장소는 (특히 재처리 동안) 유지할 이벤트 개수를 제한하기 위해 최대 캐시 크기를 사용한다.

- 중복 제거 테이블의 백업 관리도 사용자 몫. 장애 시 새 이벤트 처리 재개 전에 테이블 재구성 필수

**일관된 상태 유지**
- 브로커 대신 **상태 저장소의 트랜잭션 기능**으로도 실제로 한 번 처리 가능
- 컨슈머 그룹 오프셋 관리 주체를 브로커 → 데이터 서비스로 변경 : 상태 + 입력 오프셋을 하나의 상태 저장 트랜잭션으로 원자적 업데이트
- 커밋 타임아웃 등으로 실패하면 트랜잭션 폐기 후 마지막 정상 상태로 복귀. 데이터 서비스 복구까지 소비 중단, 이후 마지막 정상 오프셋부터 재개

> 상태 복구 처리 중 오프셋 복구

- 단, 이건 실제로 한 번 **"처리"**이지 **"생산"**이 아님 : 비트랜잭셔널 클라이언트-브로커 구조에서 출력 이벤트는 중복될 수밖에 없음 → 이 서비스가 생산하는 모든 이벤트는 **적어도 한 번 이상** 생산 보장
- 상태 저장소 업데이트와 동시에 이벤트도 트랜잭셔널하게 생성해야 한다면 → 4장의 변경-데이터 테이블(아웃박스) 활용. at-least-once 생산 + 실제로 한 번 상태 업데이트로 최종 일관성 보장

> "오프셋을 DB 트랜잭션에 넣는다"는 발상이 이 절의 백미. 우리처럼 트랜잭션 없는 브로커(SQS) + MySQL 조합이면 사실상 이 패턴 + dedupe ID 멱등 처리가 정답 조합이다. 인박스 패턴이 정확히 이 구현이라고 이해했다.

## 7.7 마치며

- 데이터 지역성을 활용하면 부하가 많은 시간에 시스템 규모 확장 가능. 내부 상태 저장소는 고성능 처리, 외부 상태 저장소는 다양하고 유연한 옵션 제공
- 체인지로그는 상태 저장소 백업/복구의 핵심. 트랜잭션 DB나 정기 스냅샷도 대안
- 트랜잭션 지원 브로커는 강력한 '실제로 한 번 처리' 메커니즘 제공 → 컨슈머의 중복 방지 책임 경감. 미지원 시스템은 중복 제거 작업으로 동등한 효과 달성
