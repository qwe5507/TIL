# 4장. 기존 시스템에 이벤트 기반 아키텍처 통합

## 이 장 핵심

레거시 시스템의 도메인 데이터를 이벤트 스트림으로 꺼내는 게 데이터 해방이고, EDM 전환의 첫 관문이다. 

방법은 셋 — 쿼리로 긁거나, DB 변경 로그(CDC)를 파싱하거나, 아웃박스 테이블에 발행 대기 이벤트를 쌓거나. 

각각 트레이드오프가 뚜렷한데, 공통 원칙은 내부 데이터 모델을 노출하지 말고 퍼블릭 데이터 규약으로 격리하라는 것. 
- 그리고 CDC는 이벤트 기반으로 가는 출발 장치일 뿐 최종 목적지가 아니다.

---

## 4.1 데이터 해방이란?

배경
- 조직 전환 시 기존 시스템(관계형 DB 모놀리스 + 점대점 연결)을 새 체제에 통합해야 함
- 어떤 비즈니스 도메인이든 여러 하위 도메인에 공통으로 필요한 엔티티/이벤트가 있음 (ex. 소매업자의 제품 정보, 단가, 재고)
- EDM 전환의 선행 조건 : 이벤트 브로커에 있는 비즈니스 도메인 데이터를 이벤트 스트림으로 소비할 수 있게 만들기

데이터 해방 : 교차 도메인 데이터 세트를 식별해서 각 이벤트 스트림에 발행하는, 이벤트 기반 아키텍처 마이그레이션 전략의 일부분
- 기존 서비스 ↔ 데이터 저장소 간 점대점 디펜던시를 분석하면 해방시켜야 할 교차 도메인 데이터가 분명해짐

<img width="597" height="199" alt="image" src="https://github.com/user-attachments/assets/f33b55da-021c-426a-a5a7-4e29f03edf3f" />

> 하부 서비스에 있는 데이터를 직접 쿼리하면 점대점 디펜던시가 유발된다

데이터를 해방하면
- 이벤트 기반 아키텍처의 두 가지 중요한 특징 적용 : 단일 진실 공급원 제공 + 시스템 간 직접 결합 방지
- 시스템은 하부 데이터 저장소/애플리케이션과 직접 결합하지 않고 이벤트 스트림의 데이터 규약만 바라보면 됨
- 조직 전체의 데이터 접근 방식 표준화

<img width="570" height="213" alt="image" src="https://github.com/user-attachments/assets/3adc7f0b-10a8-4504-a3f6-1b2d7650d6ee" />

> 데이터 해방 이후 워크플로. 레거시 → 데이터 소싱 메커니즘 → 이벤트 스트림 → 각 시스템이 소비

### 4.1.1 데이터 해방 시 고려 사항

- 데이터 세트와 해방된 이벤트 스트림은 완전히 동기화돼야 함
  - 전파 지연은 불가피 → 동기화 요건은 **최종 일관성(eventual consistency)**으로 한정
- 해방된 스트림은 반드시 똑같이 복제한 소스 테이블의 레플리카로 다시 구체화 가능해야 함
- 자체 백업/복구가 있는 레거시는 스트림에서 데이터를 재구성하지 않음 → 실제로는 해방된 스트림에서 아무것도 다시 읽어들이지 않는 **단방향** 아키텍처

<img width="607" height="272" alt="image" src="https://github.com/user-attachments/assets/2e8adc45-d046-49b2-a61b-3e10196cf33d" />

> 구체화하기 전에 스트림에 발행 (이상적인 케이스)

- 이상적 : 모든 상태를 이벤트 스트림에서 완벽하게 생성/유지/관리/복구. 공유 상태는 빠짐없이 브로커에 먼저 발행하고 필요한 모든 서비스에서 다시 구체화
- 현실 : 모든 애플리케이션이 그럴 필요도 없고 실용적이지도 않음. CDC로 한 번 통합하면 이후 변경할 일이 거의 없는 서비스도 존재
- 레거시 리팩터링이 어려운 이유
  - 진흙잡탕(big ball of mud) : 복잡한데도 다른 새 시스템이 내부 데이터에 접근해야 할 일은 많음
  - 개발자 지원 제약 : 적은 공수로 해방 가능한 솔루션 필요
  - 리팩터링 비용 : 비동기 이벤트 기반 MVC + 동기식 MVC 혼합 방식으로 재작업하려면 엄청난 비용
  - 레거시 지원 리스크 : 기술 부채 + 식별 안 된 점대점 접속 때문에 변경 시 예기치 않은 결과

타협안 : 데이터 해방 패턴으로 데이터만 꺼내 단방향 이벤트 스트림 생성
- 레거시가 해방된 스트림을 읽어들일 필요는 없음
- 기본 목표 : 이벤트 데이터 발행을 엄격하게 통제해서 내부 데이터 세트와 외부 이벤트 스트림을 계속 동기화

<img width="573" height="223" alt="image" src="https://github.com/user-attachments/assets/fa3e9753-4af9-41ce-a56f-7ce312a788ad" />

> 두 서비스 간에 상태를 해방하고 구체화

### 4.1.2 해방된 데이터를 이벤트로 변환

- 해방된 데이터도 3장과 동일한 스키마화 권장 사항을 따라야 함 (명시적 이벤트 정의, 호환성 보장 스키마, 진화 규칙에 의해서만 변경)
- 해당 데이터를 명시적 스키마로 정의하지 않으면 → 다운스트림이 비호환 부분을 알아서 해결해야 하고, 컨슈머가 임의로 파싱/해석하면 단일 진실 공급원 측면에서 큰 문제

> **TIP** 해방된 이벤트 데이터, 네이티브 이벤트 데이터 모두 조직 전체적으로 통용되는 동일한 표준 포맷을 적용할 것.

- 우선 해방 대상 : 비즈니스 전반에 걸쳐 가장 연관성이 많고 자주 사용하는 데이터

## 4.2 데이터 해방 패턴

- 해방 = 새로운 단일 진실 공급원을 만들겠다는 의도 → 전체 데이터 세트를 담아야 하고, 이후 삽입/수정/삭제를 반영하며 계속 최신 상태 유지

| 패턴 | 방식 | 조건 |
|---|---|---|
| 쿼리 기반 | 저장소를 쿼리해서 추출 | 어떤 저장소든 가능 |
| 로그 기반 | 변경 내역을 기록한 붙임 전용 로그 기준으로 추출 | 변경 로그를 보관하는 저장소만 |
| 테이블 기반 | 출력 큐용 테이블에 푸시 → 별도 프로세스가 쿼리해 스트림으로 내보내고 삭제 | 트랜잭션 + 출력 큐 메커니즘 지원 필요 |

세 패턴의 공통점 : 소스 레코드의 최근 업데이트 시간(`updated_at`) 순서로 이벤트를 생산해야 함
- 프로듀서가 발행한 시간이 아니라 **이벤트 자체가 발생한 시간**이 타임스탬프로 찍힌 스트림 생성
- 워크플로에서 실제 발생 시간을 정확히 나타내는 게 중요 (타임스탬프 인터리빙은 6장)

## 4.3 데이터 해방 프레임워크

- 중앙화 프레임워크 사용 : Kafka Connect(카프카 전용), Apache Gobblin, Apache NiFi
  - 쿼리 결과를 출력 스트림에 흘리고, 인스턴스 추가로 CDC 용량 확장
  - 스키마 레지스트리와 다양한 수준으로 통합 가능
- 단, 모든 해방 프로세스에 전용 프레임워크가 필수는 아님. 이벤트 스트림 데이터를 직접 생산하는 편이 더 적합한 시스템도 많음
- **프레임워크의 함정** : 내부 데이터 모델을 외부에 노출시켜 결합도가 오히려 증가 → 이벤트 기반의 중요한 이점이 흐려지는 가장 일반적인 안티패턴

## 4.4 쿼리로 데이터 해방

- 클라이언트가 API/SQL/유사 SQL로 원하는 데이터 세트 요청. 최초 1회 벌크 쿼리 후 주기적으로 업데이트해 변경분을 출력 스트림에 생산

쿼리 패턴 4가지
- **벌크 로딩** : 전체 데이터 로드. 증분 업데이트 직전 1회 또는 매 폴링 주기마다 전체 로드
  - 전체를 가져오므로 비용 큼. 수백만~수십억 레코드면 저장소별 모범 사례 확인 필요
- **증분 타임스탬프 로딩** : 이전 쿼리 결과의 최종 타임스탬프 이후 데이터를 쿼리. `updated_at` 컬럼 기준
- **자동증가 ID 로딩** : 마지막 처리 ID보다 큰 데이터만 쿼리. 불변 레코드 테이블(아웃박스 등)에 자주 사용
- **맞춤 쿼리** : 클라이언트 쿼리 언어로 제한. 여러 테이블 조인 + 반정규화, 필드 필터링 등 (ex. 제휴사별 스트림 분리)

증분 업데이트 절차
- **①** 레코드에 타임스탬프나 자동증가 ID 필드 확보 (없으면 추가, 추가 불가면 쿼리 기반 증분 업데이트 불가)
- **②** 폴링 빈도와 업데이트 지연 시간 결정
  - 자주 업데이트 → 다운스트림 지연 감소 but 저장소 부하 증가
  - 앞 쿼리가 로드 중인데 새 쿼리 시작 → 옛 데이터가 새 데이터를 덮는 경합 조건 주의
- **③** 벌크 로드 1회 수행 (막바지 점검)

### 쿼리 기반의 장점

- **맞춤성** : 모든 저장소 쿼리 가능, 쿼리 옵션 자유
- **독립적인 폴링 주기** : SLA 엄격한 쿼리만 빈도를 높이고 나머지는 낮춰 리소스 절약
- **내부 데이터 모델 격리** : 관계형 DB는 구체화 뷰/뷰 객체로 내부 모델과 분리 가능 → 도메인 모델 정보 은닉

> **WARNING** 해방된 데이터는 단일 진실 공급원이라는 사실을 염두에 두고, 은닉/누락된 데이터도 해방시킬지 아니면 소스 데이터 모델 자체를 리팩터링할지 고민해야 함. 비즈니스 데이터와 엔티티 데이터가 뒤엉킨 레거시에서 특히 대두되는 문제.

### 쿼리 기반의 단점

- **최종 업데이트 타임스탬프 필수** : `updated_at`류 컬럼 없으면 증분 불가
- **하드 삭제 추적 불가** : 삭제는 쿼리 결과에 안 드러남 → `is_deleted` 불리언 컬럼 쓰는 플래그 기반 소프트 삭제만 가능
- **데이터 세트 스키마 ↔ 출력 이벤트 스키마 간 취약한 의존** : 저장소 스키마가 이벤트 스키마와 비호환으로 변경될 가능성 상존 (코드베이스와 해방 메커니즘이 분리된 경우 잘 깨짐)
- **간헐적 캡처** : 폴링 주기마다 동기화 → 동일 레코드의 연속 변경들이 각자 개별 이벤트로만 보임 (중간 변경 유실)
- **생산 리소스 낭비** : 쿼리가 하부 시스템 리소스 사용 → 지연 증가. 읽기 레플리카로 완화 가능하지만 비용/복잡도 증가
- **데이터 변경량에 따라 쿼리 성능이 오르락내리락** : 최악엔 전체 데이터가 계속 변경돼 쿼리 미완료 상태 경합

## 4.5 CDC 로그로 데이터 해방

- 저장소에 내장된 CDC 로그(MySQL binlog, PostgreSQL WAL) 활용
- 개별 레코드의 생성/수정/삭제 + 데이터 세트/스키마의 생성/수정/삭제까지 붙임 전용 로그로 기록됨
- 지원 저장소가 제한적 (주로 몇몇 RDB) → 쿼리 캡처보다 기술 선택 폭이 좁음. 커넥터가 없는 경우도
  - 최신 저장소 대부분은 WAL의 프록시 역할을 하는 이벤트 API 표출 (MongoDB Change Streams, Couchbase 복제 프로토콜)
- **부트스트래핑** : 저장소 로그는 처음부터의 전체 변경 기록을 갖고 있지 않음 → CDC 시작 전에 기존 데이터 스냅샷 필요
  - 대용량 쿼리 수반 → 부트스트랩 쿼리 결과와 로그 레코드를 정확히 중첩시켜 누락 방지
- **체크포인트** : 체인지로그에서 캡처하면 체크포인트를 전진시켜야 함 (도구에 내장된 경우도). CDC 장애 시 마지막 인덱스 복구 용도
  - 적어도 한 번 이상(at-least-once) 제공 → 엔티티 기반 해방에 적절 (엔티티 업데이트는 멱등적이라 중복 생산이 문제 안 됨)
- 도구 : RDB에선 **디비지움(Debezium)**이 유명 (간단한 설정으로 Kafka/Pulsar에 생산, 타 브로커는 공수 추가). Maxwell 같은 binlog 리더는 MySQL 전용 + Kafka 전용

<img width="610" height="159" alt="image" src="https://github.com/user-attachments/assets/3536acf0-2f54-4113-8f3a-b3e3998cc7e4" />

> 디비지움 커넥터로 MySQL binlog에서 데이터를 캡처해 카프카 이벤트 스트림에 기록. Kafka Connect 서버가 binlog 소비 → 파싱/변환 → 이벤트 라우터가 소스 테이블별 스트림으로 분배

> DDIA에서 CDC 볼 때도 느꼈지만 결국 "DB 복제 프로토콜을 외부 시스템까지 확장한 것"이라는 관점이 제일 깔끔하다. 레플리카 대신 카프카가 붙는 것.

### 4.5.1 데이터 저장소 로그의 장점

- **삭제 추적** : binlog엔 하드 삭제가 이미 포함 → 소프트 삭제 없이 삭제 이벤트로 변환 가능
- **저장소 성능 영향 최소화** : WAL/binlog 사용 시 성능에 별 영향 없이 CDC 수행 (SQL Server처럼 변경 테이블 방식이면 데이터량만큼 영향)
- **저지연 업데이트** : 로그에 기록되면 곧바로 전파 → 다른 패턴보다 지연이 아주 짧음

### 4.5.2 데이터 저장소 로그의 단점

- **내부 데이터 모델 노출** : 쿼리 기반의 뷰 같은 격리 수단이 없음. 체인지로그에 내부 모델이 완전히 노출 → 신중한 선별/격리 필요
- **저장소 외부에서 반정규화** : 체인지로그엔 이벤트 데이터만. 대부분 저장소 외부에서 반정규화 발생 → 고도로 정규화된 스트림이면 다운스트림이 외래 키 조인/반정규화를 떠안음
- **취약한 스키마 의존** : 쿼리 기반과 마찬가지로 해방 프로세스가 애플리케이션 외부에 존재 → 유효한 저장소 변경이 이벤트 스키마 진화 규칙과 어긋날 수 있음

## 4.6 아웃박스 테이블로 데이터 해방

구조
- 내부 데이터의 중요한 업데이트가 로우 단위로 아웃박스 테이블에 삽입 (CDC 대상 테이블의 삽입/수정/삭제마다 발행)
- 테이블마다 자체 아웃박스를 두거나, 모든 변경분을 하나의 아웃박스에 기록
- **내부 테이블 업데이트 + 아웃박스 업데이트를 단일 트랜잭션으로** 묶음 → 성공 시에만 둘 다 반영
  - 안 그러면 단일 진실 공급원이 여러 갈래로 쪼개짐
- 저장소나 애플리케이션 레이어를 수정해야 하므로 CDC보다 침습적(invasive)인 접근
- 저장소의 보존성을 활용해 발행 대기 이벤트를 선행 기입 로깅하는 기능 제공

> **내장 변경-데이터 테이블 (책 103쪽 박스)** SQL Server 같은 일부 DB는 CDC 로그는 없지만 변경-데이터 테이블(주로 감사 용도)을 제공. Kafka Connect, 디비지움 등이 CDC 로그 대신 이 테이블에 쿼리 기반 패턴으로 접속해 이벤트를 추출할 수 있음.

아웃박스 테이블 설계 포인트
- PK가 동일한 레코드가 짧은 시간에 여러 번 업데이트될 수 있음 → **정렬 식별자**가 명확해야 함
  - 덮어쓰기(같은 PK 최신값만 유지)도 가능하지만 먼저 찾아야 해서 성능 오버헤드 + 덮어쓴 레코드는 다운스트림으로 안 흘러감
- 삽입 시 할당되는 **자동증가 ID**가 발행 순서를 정하는 최적 수단
- 레코드 생성 시간을 가리키는 `created_at` 컬럼도 보관 (발행 시점의 월클럭 시간으로 대용 가능. 6장 이벤트 스케줄러의 인터리빙에 사용)

<img width="571" height="224" alt="image" src="https://github.com/user-attachments/assets/9591fdf0-7709-4606-8e71-ba23a98e030c" />

> 아웃박스 테이블 기반 CDC 솔루션의 전체 워크플로. ① 트랜잭셔널 메시징 → ② 아웃박스 쿼리 → ③ 스트림에 기록 → ④ 기록 확인 대기 → ⑤ 기록된 엔트리 삭제

- 별도 스레드/프로세스가 아웃박스를 폴링해서 스트림에 생산, 성공하면 레코드 삭제
- 저장소/프로듀서/컨슈머/브로커 어디에 장애가 나도 아웃박스 레코드는 보존 → **적어도 한 번 이상 전달 보장**

> 아웃박스 패턴은 인박스 패턴 공부할 때 세트로 봤던 내용인데, 이 책은 "데이터 해방 수단"이라는 다른 각도에서 접근하는 게 흥미롭다. 우리 팀 관점에선 DB 커밋과 SNS 발행 사이의 원자성 구멍(커밋 성공 후 발행 실패)을 막는 정석 해법이기도 하다.

### 4.6.1 성능 고려 사항

- 아웃박스가 있는 저장소 + 처리 애플리케이션의 부하 가중
- 소규모면 미미하지만 대규모 + 캡처 테이블이 많으면 비용 큼 → 케이스별로 CDC 로그 파싱 등 대안과 비용 균형

### 4.6.2 내부 데이터 모델 격리

- 아웃박스를 내부 테이블과 1:1 매핑할 필요 없음. **아웃박스의 중요한 장점 = 내부 데이터 모델 격리**
- 내부 관계형 모델은 다운스트림 소비에 부적합한 고도로 정규화된 테이블들 → 그대로 노출하면 여러 다운스트림 팀이 도메인 모델 재설계 + 관계형 처리를 떠안아 운영 오버헤드 큼

> **WARNING** 내부 데이터 모델을 다운스트림 컨슈머에게 표출하는 것은 안티패턴. 다운스트림 컨슈머는 퍼블릭(공개) 데이터 규약(3장)에 의해 포맷팅된 데이터에만 접근해야 한다.

- 방법 1 : 삽입 시점에 반정규화해서 아웃박스에 기록 (저장 공간/성능 비용 감수)
- 방법 2 : 변경분과 출력 스트림을 1:1로 매핑해두고 전용 다운스트림 이벤트 처리기로 반정규화 = **이벤트화(eventification)**
  - 정규화된 원(raw) 이벤트 스트림은 프라이빗 네임스페이스에 격리 보관, 최종 반정규화 이벤트만 퍼블릭 네임스페이스로 (14.3절 태깅)

<img width="591" height="207" alt="image" src="https://github.com/user-attachments/assets/3a01353c-fe56-4ed4-b931-eb5e3ab9a866" />

> 프라이빗 이벤트 스트림 User, Location, Employer를 통해 User를 퍼블릭 이벤트로 만듦 (User 이벤트화)

- 외래 키로 참조되는 Location/Employer를 조인해서 사용자별 전체 정보를 하나의 이벤트로 제공 → 다운스트림이 각자 구체화+조인하는 것보다 나음
- 내부 모델 격리 수준은 거의 모든 EDM 전환 프로젝트의 논쟁거리
  - 목적 : 서비스 간 결합 차단 + "업스트림 내부 모델 변경"이 아닌 "새 비즈니스 요건"에 의해서만 시스템이 변경되도록 보장

### 4.6.3 스키마 호환성 보장

- 스키마 직렬화(+검증)를 캡처 워크플로에 구현 — 언제 하느냐에 따라 두 방식

**사전 직렬화 (아웃박스에 커밋하기 전 직렬화)**
- 데이터 일관성 측면에서 가장 강력. 직렬화 실패 → 트랜잭션도 실패 → 내부 테이블 변경분 롤백 → 아웃박스와 내부 테이블 동기화 유지
- 내부 상태와 출력 스트림 간 정합성이 안 맞을 가능성이 현저히 감소
- 이벤트 스트림 데이터를 일급 시민으로 취급 : 일관된 내부 상태만큼 정확한 발행도 중요
- 모든 트랜잭션을 하나의 아웃박스로 받을 수 있음 (직렬화된 데이터라 포맷 단순 : id, created_at, serialized_key, serialized_value, output_stream)
- 단점 : 직렬화 오버헤드로 성능 하락 가능 (부하 클 때 문제)

<img width="598" height="192" alt="image" src="https://github.com/user-attachments/assets/f19eae6c-b7e5-4f3e-885c-0f67244314d2" />

> 변경 데이터를 아웃박스 테이블에 기록하기 전에 직렬화

<img width="590" height="162" alt="image" src="https://github.com/user-attachments/assets/6cff093c-520e-4efa-9005-0cfbff600f02" />

> 이미 검증을 마치고 직렬화된 이벤트가 적재된 아웃박스 테이블 (output_stream 컬럼은 라우팅 목적)

**사후 직렬화 (아웃박스에 쓴 다음 발행 시 직렬화)**
- 보통 도메인 모델당 하나씩, 출력 스트림의 퍼블릭 스키마에 매핑된 독립 아웃박스
- 발행기가 미직렬화 이벤트를 읽어 스키마로 직렬화 후 생산
- 단점 : 직렬화 실패 = 발행 불가 이벤트. 이미 완료된 트랜잭션이 비호환 데이터를 푸시했다면 롤백 보장이 없음
  - 실제로는 직렬화 안 되는 이벤트가 쌓임 → 사람 개입, 중단 시간 증가, 발행 완료된 호환 이벤트와 섞여 순서 어긋날 위험

<img width="529" height="185" alt="image" src="https://github.com/user-attachments/assets/1ba5d6f6-6e1a-4869-8a21-c7e36858f755" />

> 변경 데이터를 아웃박스 테이블에 기록한 후 직렬화 (발행 프로세스의 일부)

<img width="617" height="266" alt="image" src="https://github.com/user-attachments/assets/af5e1551-8ee7-4fbe-bc43-9a85fa7661a1" />

> 다중 아웃박스 테이블 (데이터가 직렬화되어 있지 않아 출력 스키마와 비호환일 가능성 존재)

> **TIP** 사전 직렬화는 사후 직렬화보다 비호환 데이터를 더 강력하게 걸러내 규약 위반 이벤트의 전파를 방지. 다만 직렬화 실패 시 반드시 트랜잭션을 롤백해야 하므로 비즈니스 프로세스가 완료되지 못하는 트레이드오프.

아웃박스 방식 장단점 정리

| 장점 | 단점 |
|---|---|
| 다수의 언어 지원 (트랜잭션 되는 클라이언트/프레임워크면 OK) | 애플리케이션 코드 변경 필수 → 개발/테스트 리소스 |
| 사전 스키마 강화 (삽입 전 직렬화로 검증) | 비즈니스 프로세스 성능 영향 (직렬화 검증, 트랜잭션 실패 시 작업 중단) |
| 내부 데이터 모델 격리 (노출 필드 선택 가능) | 데이터 저장소 성능 영향 (대량 레코드 쓰기/읽기/삭제) |
| 반정규화 (쓰기 전에 필요한 만큼) | |

> **NOTE** 성능 영향도는 다른 비용과 균형. CDC 로그를 파싱해 사후 정제를 다운스트림 팀에 넘기는 회사도 있지만, 자체 컴퓨팅 비용 + 사람이 비호환 스키마를 일일이 해석하는 인건비가 들어 프로듀서 쪽 절약이 무색해지는 경우가 많다.

### 4.6.4 변경-데이터를 트리거로 캡처

- 트리거 : binlog/WAL보다 오래된 기술. 구형 RDB는 대부분 감사 테이블 생성 수단으로 사용
- 정해진 조건에서 자동 실행. 트리거 실패 → 트리거를 일으킨 커맨드도 실패 → **원자적 업데이트 보장**
- AFTER 트리거로 INSERT/UPDATE/DELETE 시 변경된 로우를 변경-데이터 테이블에 기록 (삽입 시간 + 자동증가 ID 캡처)

<img width="598" height="295" alt="image" src="https://github.com/user-attachments/assets/d670c154-7c97-4a4c-a92c-fed270bbdfb0" />

> User 테이블에 반영된 변경 데이터를 트리거로 캡처. 트리거는 트랜잭션 일부로 실행됨

- 트리거 실행 중 스키마 검증은 대체로 어려움 (DB 내부 실행이라 지원 언어 한정, PostgreSQL은 사용자 정의 함수 가능하지만 비용 큼)
- → 사후 검증 : 변경-데이터를 검증해 직렬화 후 문제 없는 것만 출력 스트림에 생산. 실패분은 에러 처리 또는 수동 처리

<img width="619" height="379" alt="image" src="https://github.com/user-attachments/assets/b4f39bc5-5902-4b0b-bffb-d544f30d0b45" />

> 사후 검증하고 출력 이벤트 스트림에 이벤트 생산. 검증 실패 시 사람의 개입 없이는 이벤트가 발행되지 않음

- CDC 테이블 스키마 = 내부 테이블 스키마 ↔ 출력 스트림 스키마를 연결하는 징검다리. 셋의 궁합이 맞아야 함
- 출력 스키마는 트리거 실행 중 검증하지 않으므로 변경-데이터 테이블을 출력 스키마 포맷으로 동기화하는 게 최선

> **TIP** 테스트하면서 출력 이벤트 스키마와 변경-데이터 테이블 포맷을 비교해볼 것. 프로덕션 배포 전에 비호환 부분을 밝혀낼 수 있다.

트리거 장단점

| 장점 | 단점 |
|---|---|
| 대부분 RDB가 지원 | 성능 오버헤드 (DB 내부 리소스 차지, SLA에 따라 수용 불가 수준일 수도) |
| 데이터 규모 작으면 오버헤드 낮음, 관리 쉬움 | 변경 관리 복잡 (코드/데이터 정의 변경 시 트리거 수정 누락 → 어긋난 해방. 종합 테스트 필요) |
| 맞춤 로직 (특정 필드 하위 세트만 노출, 격리 수준 지정) | 확장성 나쁨 (캡처 데이터 세트 수만큼 트리거 필요) |
| | 사후 스키마 강화 (발행 불가 이벤트가 아웃박스에 섞임) |

> **TIP** 일부 DB는 출력 스키마 호환성을 검증할 수 있는 언어로 트리거 실행 가능 (ex. PostgreSQL 파이썬 트리거). 복잡도/비용은 늘지만 비호환 위험이 상당히 경감.

> **WARNING** 더 최근 기술로 변경-데이터를 생성/접근할 수 있다면 트리거는 가급적 사용하지 말 것. 성능 오버헤드와 관리 부담을 과소평가하면 안 됨. 연관 테이블/데이터 모델이 수십~수백 개면 특히.

## 4.7 데이터 정의 변경을 캡처 대상 데이터 세트로

- 데이터 정의(DDL) 변경(컬럼 추가/삭제/이름 변경/타입 변경/기본값 추가·삭제)까지 통합하는 건 쉽지 않음

> **NOTE** 데이터 정의 : 데이터 세트의 포맷을 기술한 것. 관계형 DB에서는 DDL로 테이블을 정의. 테이블/컬럼/이름/타입/인덱스 모두 데이터 정의의 구성 요소.

- ex. 양방향 호환이 필요한 경우, 옛 스키마 컨슈머는 필드에 어떤 값이 있으리라 기대 → 기본값 없는 널 금지 컬럼은 뺄 수 없음. 비호환 변경이 불가피하면 프로듀서/컨슈머는 반드시 새 데이터 규약 체결

> **WARNING** 캡처할 데이터 세트를 유효하게 변경해도 해방된 이벤트 스키마 입장에서는 유효하지 않을 수 있다. 이런 비호환성 때문에 중대한 스키마 변경이 발생하고 전체 다운스트림 컨슈머에게 영향을 미친다.

캡처 패턴별 DDL 변경 감지 시점
- **쿼리 패턴, CDC 로그 패턴 : 사후 처리**
  - 쿼리 : 쿼리 시점에 스키마를 가져와 이벤트 스키마 추론 → 호환성 규칙으로 출력 스키마와 비교 (Kafka Connect류)
  - CDC 로그 : 데이터 정의 업데이트가 로그 일부로 캡처됨 → 로그에서 추출해 스키마 표현형 추론 후 비교/검증. 단 기능이 제한적 (디비지움은 MySQL의 데이터 정의 변경만 지원)
- **변경-데이터 테이블 캡처 패턴 : 사전 처리**
  - 소스 시스템 개발 주기와 통합 → 프로덕션 릴리스 전에 변경 내용을 변경-데이터 테이블과 비교/검증해야 함
  - 검증 코드/트리거가 하나라도 짝이 안 맞으면 오류가 쌓이고 기록 안 됨 → 두 단계 구성 덕에 예기치 않은 변경이 프로덕션에 스며들 가능성이 현저히 감소

## 4.8 이벤트 데이터를 데이터 저장소에 싱킹

- 싱킹(sinking) : 이벤트 데이터를 소비해서 데이터 저장소에 삽입 (해방의 역방향)
- 중앙화 프레임워크나 단독형 마이크로서비스로 수행. 어떤 유형의 이벤트든 가능
- 유용한 경우
  - 이벤트 기반으로 개발되지 않은 애플리케이션을 스트림과 통합 (싱크 프로세스는 목적지 시스템에 외부적으로 투명하게 작동, 자체 오프셋 추적)
  - 레거시 시스템 간 직접 점대점 결합 대체 : 소스 데이터를 스트림으로 해방하면 목적지 시스템은 변경 없이 싱크만 하면 됨
  - 배치 기반 빅데이터 분석 (HDFS로 싱크)
- Kafka Connect 같은 공통 플랫폼이면 간단한 설정으로 공유 인프라에서 실행. 단독형 마이크로서비스로 독립 관리도 가능

## 4.9 싱킹과 소싱의 비즈니스 영향도

- 중앙화 프레임워크의 효용 : 한 팀이 대규모로 운영하면 다른 팀은 커넥터 구성/설계만 신경 쓰면 됨 → 여러 팀·여러 저장소의 대규모 조직에서 가장 유용

조심할 것 2가지
- **① 소싱/싱킹 책임이 팀 간에 공유됨**
  - 프레임워크 운영팀 : 프레임워크 + 커넥터 인스턴스의 안정성/확장/헬스 체크 담당
  - 캡처 대상 시스템 운영팀 : 독립적으로 커넥터 성능에 영향 주는 결정(필드 추가/삭제, 데이터량 변경) 가능
  - → 직접적인 의존 관계 성립. 변경 때문에 커넥터가 잘못돼도 관리팀만 감지 → 선형적 확장 + 팀 상호 의존 관계 발생. 변경이 늘수록 관리 난감
- **② 프레임워크/커넥터 과의존 → 시스템 본연의 이벤트 기반 작업을 못 하게 됨**
  - 이벤트 기반 원칙을 일부만 채택한 조직에서 특히 불거짐
  - 데이터가 스트림에 발행되면 그것으로 만족 → 마이크로서비스 전진에 무관심
  - 팀이 커넥터 프레임워크에 의존해 자기 애플리케이션을 이벤트 기반 본연의 애플리케이션으로 리팩터링하지 않으려 함

> **WARNING** CDC는 이벤트 기반 아키텍처로 향하는 최종 목적지가 아니라 그 프로세스를 개시하는 데 도움을 주는 장치다. 이벤트 브로커의 진가는 구현 레이어에서 분리된 탄탄하고 미덥고 진실된 이벤트 데이터의 원천(단일 진실 공급원) 제공에 있다. 데이터의 품질과 신뢰도가 낮으면 이벤트 브로커는 무용지물.

해결 방향
- 가능한 한 CDC 프레임워크를 덜 사용하고 팀 스스로 (아웃박스 패턴 적용 등으로) CDC를 구현하도록 유도
  - 팀 간 의존 + 취약한 커넥터 기반 CDC를 없애고, 팀이 맡은 시스템의 이벤트 발행에만 최선을 다하게 함
  - 프레임워크 운영팀의 일은 최소화되고 진짜 필요한 곳에 기술 지원 집중
- **이벤트 우선(event-first) 마음가짐** 확산 : 스트림을 모놀리스끼리 데이터 주고받는 수단으로 보지 않고, 각 시스템을 이벤트를 직접 발행/구독하는 프로듀서/컨슈머로 바라보기
  - "여기 안에 담긴(in here)" 데이터가 아니라 "저밖에 널려 있는(out there)" 데이터를 생각하게 됨 — 성공적 도입의 중요한 문화적 변이
- 유지보수만 하는 제품 → 중앙화 커넥터로 큰 혜택. 개발이 한창인 복잡한 제품 → 커넥터 관리가 지속적으로 어려우니 이벤트 기반 본연의 애플리케이션으로 리팩터링할 일정 수립 권장
- 팀마다 단일 진실 공급원 제공 책임을 두고 논쟁이 생기기 쉬움 → 조직 구성원 모두 본인이 해방한 데이터의 영향을 예상하고 스키마/데이터 모델/순서/지연/정확성에 관한 SLA를 명확하게 도출해야 함

## 4.10 마치며

- 데이터 해방 = 접근성 좋은 성숙한 데이터 통신 레이어를 만들기 위한 중요한 단계. 레거시에 갇힌 코어 도메인 데이터를 해방시켜 분리된 제품/서비스 구성
- 추출/변환 프레임워크·도구·전략은 다양하고 각각 트레이드오프 존재. 유스 케이스마다 선택이 달라지고 직접 만들어야 할 수도
- 해방의 목표 : 깨끗하고 일관된 단일 진실 공급원. 데이터 접근 행위와 생산/저장 행위가 분리 → 둘을 모두 수행하는 통신 구조가 불필요
- 전략은 풀 스펙트럼
  - 한쪽 끝 : 소스 시스템과 가깝게 통합 (구현체 저장 + 브로커 방출, 프로듀서가 좋은 데이터를 생산하는 시민으로서 역할 인식, 컨슈머와 협력해 고품질 스트림 보장)
  - 반대쪽 끝 : 고도로 리액티브한 전략 (소스 소유자가 브로커 생산을 거의/전혀 모름, 프레임워크가 직접 가져가거나 CDC 로그 파싱) → 스키마 깨짐/내부 모델 노출이 잦아 장기 유지 어려움
- 성공 여부는 조직 문화에 달림 : 데이터 소유자가 깨끗하고 신뢰할 만한 스트림 생산 필요성을 진지하게 받아들이고, **데이터 캡처 메커니즘이 최종 목적지로는 불충분하다는 사실을 이해해야 함**
