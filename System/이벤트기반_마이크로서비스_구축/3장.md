# 3장. 통신 및 데이터 규약

## 이 장 핵심

프로듀서가 생산한 메시지를 컨슈머가 정확히 되살리려면 둘이 메시지를 똑같이 이해해야 한다. 

그 "공통 언어"가 명시적 스키마이고, 동기식 세계의 API 정의에 해당하는 게 이벤트 세계의 데이터 규약이다. 

스키마 진화 규칙을 정해두면 프로듀서/컨슈머가 서로 독립적으로 업데이트할 수 있다. 

이벤트 설계의 대원칙은 하나 — 이벤트는 하나의 비즈니스 액션만, 필요한 모든 정보를 담아서.

---

## 3.1 이벤트 기반 데이터 규약

> 통신의 근본적인 문제는 어느 지점에서 선택한 메시지를 다른 지점에서 정확하게 또는 대략적이나마 재생산하는 것이다. — 클로드 섀넌

- 데이터 규약(data contract) : 주고받을 데이터의 포맷과 그 생성 로직을 정의. 프로듀서/컨슈머가 모두 준수하는 계약서
- 잘 정의된 데이터 규약의 두 요소
  - 데이터 정의 : 생산할 것들 (필드, 타입, 자료 구조)
  - 트리거 로직 : 생산한 이유 (이벤트 생성을 일으킨 비즈니스 로직)
- 변경할 때는 다운스트림 컨슈머가 쓰는 필드를 삭제/변경하지 않도록 주의
  - 트리거 로직을 바꾸면 원래 이벤트 정의의 의미가 깨지는 경우가 많음 → 데이터 정의를 변경하는 게 더 일반적

### 3.1.1 명시적인 스키마를 규약으로 활용

- 데이터 규약을 강제하는 가장 좋은 방법 : 이벤트마다 스키마 정의
- 프로듀서가 데이터 정의 + 트리거 로직이 상술된 스키마를 명시적으로 정의 → 동일 타입 이벤트는 모두 해당 포맷을 따름
- 미래의 모든 컨슈머에게 이벤트 포맷이 전달되고, 컨슈머는 비즈니스 로직을 명확하게 구현 가능

> **WARNING ** 명시적 스키마가 없으면 프로듀서/컨슈머는 암묵적 스키마에 의존할 수밖에 없다. 암묵적 데이터 규약은 기반이 취약해서 언제 어떻게 바뀔지 알 수 없고 다운스트림 컨슈머에게 지나친 부담을 지운다.

암묵적 스키마의 문제
- 컨슈머 입장 : 필요한 데이터 스펙을 부족 지식(tribal knowledge)과 팀 간 소통만으로 해결해야 함 → 스트림/팀이 늘면 감당 불가
- 컨슈머마다 해석 방식이 달라짐 → 일관성 없이 단일 진실 공급원을 바라보게 됨
- 프로듀서 입장 : 자신의 데이터 정의가 변경됐다는 사실조차 모를 수 있음 (단위 테스트로도 안 드러남). 다운스트림이 실패할 때까지 모르기도 함
- 명시적 스키마 = 프로듀서/컨슈머 모두에게 보안과 안정성

> **WARNING ** "모든 서비스의 어떤 이벤트라도 해석 가능한 공통 라이브러리"를 만들고 싶겠지만, 다수의 언어 포맷 + 이벤트 진화 + 독립 릴리스 과정에서 문제가 생긴다. 가급적 피할 것.

### 3.1.2 스키마 정의 주석

- 스키마 정의에 통합된 주석/메타데이터는 이벤트 의미 전달에 필수
- 생산/소비에 관한 지식은 가능한 한 이벤트 정의와 가깝게 붙어 있는 게 좋음
- 특히 진가가 발휘되는 영역
  - 트리거 논리 명시 : 스키마 맨 앞 블록 헤더에 이벤트가 생성된 이유를 명확히
  - 특정 필드의 콘텍스트 부여 : ex. datetime 필드가 UTC/ISO/유닉스 타임 중 무엇인지

### 3.1.3 완전한 스키마 진화

- 스키마 포맷은 스키마 진화 규칙의 전체 범위를 지원해야 함
- 스키마 진화 없이는 서비스 업데이트 비용이 너무 비쌈
  - 프로듀서가 스키마 변경할 때마다 컨슈머가 서비스 업데이트 → 말이 안 됨. "모든 서비스는 독립적으로 릴리스"라는 MSA 핵심 가치에도 반함
- 진화 규칙을 정해두면 프로듀서/컨슈머 모두 자기 일정에 따라 업데이트 가능

호환성 종류 3가지

| 종류 | 의미 | 유용한 경우 |
|---|---|---|
| 정방향 호환성 | 새 스키마로 생성한 데이터를 옛 스키마인 것처럼 읽음 | 프로듀서가 먼저 업데이트하는 일반적 흐름. 이벤트 기반에서 특히 유용. 컨슈머는 새 필드가 필요할 때만 업데이트 |
| 역방향 호환성 | 옛 스키마로 생성한 데이터를 새 스키마인 것처럼 읽음 | 새 스키마가 미리 정의돼 있으면 컨슈머가 프로듀서보다 먼저 릴리스 가능 / 고객 하드웨어(휴대폰 앱)에서 옛 버전 데이터 수신 / 옛 스키마 이벤트 재처리 |
| 양방향 호환성 | 정방향 + 역방향 조합 | 가장 강력한 보증. 호환성 요건은 나중에 완화는 쉬워도 높이는 건 어려움 → **가능한 한 항상 양방향 적용 권장** |

### 3.1.4 코드 생성기 지원

- 코드 생성기 : 이벤트 스키마 → 프로그래밍 언어의 클래스 정의(또는 동등한 구조)로 변환
- 생산 워크플로 : 비즈니스 로직 출력 → 클래스 객체 생성 → 시리얼라이저 → 스키마 지정 포맷으로 직렬화 → 브로커에 전달
  - 널 금지(non-nullable) 필드 값이 모두 채워졌는지 등 원래 스키마의 데이터 타입 준수

> 코드 생성기를 이용한 프로듀서의 이벤트 생산 워크플로

- 소비 워크플로 : 이벤트 소비 → 인코딩된 스키마 버전으로 역직렬화 → 진화 규칙 적용해 컨슈머가 지원하는 버전으로 변환 (누락 필드는 기본값, 미사용 필드는 제거) → 클래스 생성자 → 객체 → 비즈니스 로직
  - 컨슈머의 스키마 버전은 프로듀서보다 낮거나 높을 수 있음
  - 이벤트 포맷을 메시지 안에 넣으면 비용이 커서 보통 스키마 레지스트리에 저장하거나 온디맨드 접근 (14.5절)

> 코드 생성기를 이용한 컨슈머의 이벤트 소비/변환 워크플로. V2 스키마로 생성된 이벤트를 V1 포맷으로 변환해 사용

- 컴파일 언어면 이벤트 타입 오처리/널 필드 누락을 컴파일러가 체크 → 스키마 위배 코드는 컴파일 자체가 안 됨
- 객체 키/값 맵 같은 일반 포맷은 잘못 넘겨도 알림받을 방법이 없음
- 데이터 오처리 위험 감소 = 전체 데이터 품질 보장

### 3.1.5 중대한 스키마 변경

- 진화 흐름을 깨뜨리는 변경(breaking change)이 불가피한 경우 : 도메인 모델을 통째로 바꾸는 비즈니스 요건 변화, 도메인 범위 부적절, 스키마 정의 실수 등
- 프로듀서는 새 스키마로 쉽게 갈아끼울 수 있지만 다운스트림 컨슈머가 문제

> **TIP ** 중대한 스키마 변경이 일어나면 가급적 이른 시기에 다운스트림 컨슈머측과 명확하게 소통하는 것이 가장 중요. 어떤 마이그레이션 계획이든 관련자 모두가 이해하고 수용할 수 있어야 한다.

엔티티의 중대한 스키마 변경 : 데이터 정의를 두 갈래로 분기하는 방법 2가지

- **① 옛 스키마와 새 스키마를 함께 둠**
  - 프로듀서는 제일 쉽지만, 상이한 엔티티 정의를 컨슈머가 알아서 해석하도록 방치하는 셈
  - 컨슈머가 잘못 해석하면 서비스 간 처리 일관성 결여, 시스템 관리 복잡
- **② 모든 엔티티를 새 스키마 포맷으로 재생성** (마이그레이션 또는 소스에서 재생성)
  - 프로듀서에겐 더 어렵지만 옛/새 엔티티 모두 일관성 있게 재정의됨
  - 단, 엔티티의 의미와 사용법을 조직 전체적으로 강제하지 않으면 소용 없음

> **WARNING ** 별의별 스키마 정의를 컨슈머가 프로듀서보다 더 잘 해석하리라 기대할 수는 없다. 컨슈머에게 책임을 전가하는 건 나쁜 습관.

> **TIP ** 옛 엔티티는 나중에 재처리 검증이나 증빙 자료로 필요할 수 있으니 원래 스트림에 옛 스키마 상태로 놔두고, 새 스키마로 업데이트된 엔티티와 새로 생성된 엔티티를 **새 스트림**에 생산할 것.

이벤트(비엔티티)의 중대한 스키마 변경
- 더 간단 : 새 이벤트 스트림을 만들어 새 이벤트를 생산
- 옛 스트림 컨슈머가 새 스트림에 스스로 등록할 수 있게 미리 알리고, 각 컨슈머는 두 이벤트 정의 간 분기된 로직에 대응
- 옛 스트림에 생산이 끊기면 컨슈머들이 최근 레코드를 따라잡음 → 보존 기간이 지나 이벤트가 완전 삭제되면 구독 취소 + 스트림 삭제

> **WARNING ** 하나의 이벤트 스트림에 여러 종류의 이벤트 타입(특히 스키마 진화 측면에서 더 이상 호환되지 않는 타입)은 절대로 섞어 쓰지 말 것. 스트림 오버헤드는 저렴하니 논리적으로 분리해서 컨슈머가 완전한 정보와 명시적인 정의를 갖고 처리하게 만들 것.

## 3.2 이벤트 포맷 선택

- 데이터 규약은 Avro, Thrift, Protobuf처럼 엄격하게 정의된 포맷 사용 권장
- 잘 알려진 브로커 프레임워크(Kafka, Pulsar)는 JSON/Protobuf/Avro 모두 지원 — 스키마 레지스트리 덕분
- "그냥 평범한 키/값 텍스트가 더 유연하지 않나?" → 명시적 스키마/진화 프레임워크가 없어서 팀 간 소통이 더 필요해지고, 강력한 데이터 규약으로 격리 상태를 유지하는 마이크로서비스 본연의 가치가 훼손됨

> **TIP ** 비구조 일반 텍스트 이벤트는 시간이 지날수록 용도와 데이터가 달라져 프로듀서/컨슈머 모두 부담. 저자는 Avro, Protobuf처럼 통제 가능한 스키마 진화를 지원하는 강력하고 명시적인 스키마 포맷을 권장. **JSON은 스키마 진화를 완벽하게 지원하지 못하므로 비권장.**

> 회사 SNS/SQS 메시지가 대부분 JSON인데, 스키마 레지스트리 없이 굴러가는 건 사실 여기서 말하는 암묵적 규약에 가깝다. 지금은 팀이 작아서 소통으로 커버되지만 컨슈머 팀이 늘면 이 장에서 경고하는 문제가 그대로 올 듯.

## 3.3 이벤트 설계

- 이벤트 정의 생성의 모범 사례와 안티패턴. 아키텍처가 늘수록 이벤트 정의도 많아짐 → 잘 설계해야 프로듀서/컨슈머 모두 덜 고통스러움
- 절대 규칙은 아니고, 문제 공간의 의미와 트레이드오프를 심사숙고한 뒤 적용할 것

### 3.3.1 오직 진실만을 말할지어다

- 잘 정의된 이벤트는 "뭔가(something) 일어났다"가 아니라 그 동안의 "모든 일들(everything)"을 빠짐없이 기술
- 비즈니스 용어로 : 입력 데이터에 비즈니스 로직을 적용해 만들어낸 결과 데이터
- 출력 이벤트는 단일 진실 공급원으로서 다운스트림이 소비할 불변의 팩트로 기록
- 컨슈머는 그 이벤트의 발생 사실을 다른 데이터 출처로 확인할 필요가 없어야 함

### 3.3.2 스트림당 이벤트 정의는 하나만 사용

- 이벤트 스트림에는 하나의 논리적 이벤트를 나타내는 이벤트만
- 종류가 다른 이벤트를 섞으면 이벤트 실체/스트림 정체성에 혼란 + 동적으로 추가되는 스키마의 유효성 검증 곤란
- 특수한 예외 상황은 있지만, 대부분의 스트림은 각자 하나의 엄격한 정의를 가져야 함

### 3.3.3 가장 좁은 범위의 데이터 타입 사용

- 좁은 타입을 써야 코드 생성기, 언어 타입 체크, 직렬화 단위 테스트로 데이터 경계를 체크 가능

피해야 할 사례

| 사례 | 문제 |
|---|---|
| 문자열에 숫자 값 저장 | 파싱 과정에서 널/공백 문자열 전달이 잦아 오류 가능성 높음 |
| 정수를 불리언으로 사용 | 0=거짓, 1=참이라면 2는? -1은? |
| 문자열을 이늄으로 사용 | 의사 이늄(pseudo-enum) 리스트 보장 문제. 오탈자/부정확한 값 유입. 컨슈머는 유효값 범위를 알아야 하고 사전 협의 불가피 → 암묵적 정의 |

- 이늄 자체는 보통 잘 안 씀 (컨슈머 스키마에 없는 새 토큰 걱정)
  - 하지만 알 수 없는 토큰을 기본값 처리할지, 예외 던지고 중단할지는 컨슈머가 결정할 책임
  - Protobuf와 Avro는 알 수 없는 이늄 토큰을 우아하게 처리하는 방법 제공 → 이벤트 포맷으로 둘 중 하나 권장

### 3.3.4 이벤트는 하나의 목적만 갖도록

- 타입 필드를 추가해서 하위 속성을 두는 건 흔한 안티패턴 ("비슷하지만 다른" 데이터 처리)
- 타입 매개변숫값은 기술적 표현형은 비슷해도 비즈니스 의미가 근본적으로 다름
  - 의미가 시간이 지나며 바뀌고 커버 영역도 달라짐 → 스키마만 같은 전혀 다른 이벤트가 공존 → 나중엔 의미 짐작조차 어려움
- 컨슈머 부담 : 자기가 관심 있는 데이터만 가져와야 하고, 상관없는 이벤트를 제거하는 부가 로직을 반드시 수행. 별의별 타입의 의미를 다 이해할 수 없으니 논리적으로 틀린 코드 실행 위험

> **WARNING ** 타입 필드를 추가해도 데이터에 내재된 근본적 복잡성은 줄지 않는다. 다수의 스트림에서 명확했을 스키마들이 하나로 병합되며 옮겨진 것뿐. 이벤트 생산 코드 관리도 버거운데 미래의 스키마 진화 관리는 더 어렵다.

- 다양한 타입 매개변수를 지닌 제네릭한 이벤트만 있어도 된다면 → 문제 공간과 경계 콘텍스트가 제대로 정의되지 않았다는 방증

예제 : 이벤트 정의 오버로딩
- 도서 열람 + 영화 감상이 가능한 웹사이트. 최초 이용 시 백엔드가 `ProductEngagement` 이벤트 발행

```
TypeEnum: Book, Movie
ActionEnum: Click

ProductEngagement {
  productId: Long,
  productType: TypeEnum,
  actionType: ActionEnum
}
```

- 신규 요건 1 : 영화 보기 전 예고편 시청 추적 → 도서엔 예고편 개념이 없어서 null 허용 필드 추가
- 신규 요건 2 : 도서 책갈피 추적 → `Bookmark` 액션 + null 허용 `pageId` 추가

```
ProductEngagement {
  productId: Long,
  productType: TypeEnum,
  actionType: ActionEnum,
  //productType=Movie인 이벤트에만 적용
  watchedPreview: {null, Boolean},
  //productType=Book,actionType=Bookmark인 이벤트에만 적용
  pageId: {null, Int}
}
```

- 요건이 조금만 달라져도 스키마가 폭발적으로 복잡해짐. 단일 책임 원칙에 따라 분리하면:

```
MovieClick {
  movieId: Long,
  watchedPreview: Boolean
}

BookClick {
  bookId: Long
}

BookBookmark {
  bookId: Long,
  pageId: Int
}
```

- 이늄 2개 제거, 스키마 평평해짐. 이벤트 정의는 3개로 늘었지만 내부 복잡도는 크게 감소
- '스트림 : 이벤트 정의 = 1:1' 원칙 → 이벤트 타입이 새로 생길 때마다 새 스트림
- 원작성자가 실수한 게 아님. 당시엔 "모든 제품의 이용 현황"이 요건이었음 → 요건이 바뀌었을 때 이벤트 정의가 한 가지 목적인지 재검토했어야 함

> **WARNING ** 이벤트의 의미를 오버로드하는 타입 필드는 절대로 추가하지 말 것. 이벤트 포맷을 진화시키고 관리하기가 상당히 어려워진다.

- 스키마가 앞으로 어떻게 진화할지 시간을 들여 생각할 것. 스키마가 비즈니스 관심사를 정확하게 반영하는지 철저히 검증
- 비즈니스 요건에 따라 이벤트 정의를 재검토한 결과, 스키마 수정 이상(이벤트를 나눠 재정의)이 필요할 수도 있음

### 3.3.5 이벤트 크기 최소화

- 이벤트는 작고, 잘 정의되고, 쉽게 처리할 수 있어야 함
- 덩치 큰 이벤트를 설계할 때 확인할 것
  - 데이터가 이벤트와 직접 관련이 있는가? 만일을 위해 붙인 부가 데이터는 컨슈머가 거의 안 쓸 수도
  - 모든 데이터가 정말 직접 연관이라면 → 한 걸음 물러나 문제 공간 재검토 (서비스가 하는 일이 너무 많은가? 경계 콘텍스트 재검토? 부가 기능을 별도 서비스로?)
- 정말 어쩔 수 없는 경우 (ex. 고해상도 이미지 같은 큰 출력 파일)
  - 실데이터를 포인터로 가리키는 방법이 있긴 하지만, 진실 공급원이 여럿 생기고 페이로드가 가변적이면 불변 장부로 데이터를 지킬 수 없음 → 가급적 삼갈 것

### 3.3.6 미래의 컨슈머도 이벤트 설계에 반영

- 새 이벤트 설계 시 데이터를 소비할 것으로 예상되는 컨슈머 부서와도 협의
- 컨슈머 니즈, 앞으로 필요한 비즈니스 기능, 인입될 데이터는 프로듀서보다 그쪽이 더 잘 앎 → 요건을 명확히 정하는 데 도움
- 협의체 구성해 회의/토론 → 데이터 규약 이슈를 어느 정도 예방

### 3.3.7 이벤트를 세마포어나 시그널로 사용하지 않는다

- 세마포어/시그널용 이벤트 : 어떤 결과의 단일 진실 공급원이 아니라 "뭔가 일어났음"만 알림
- ex. 작업 완료를 나타내는 이벤트만 출력하는 시스템 → 완료 사실은 알지만 실제 작업 결과가 없어서 다른 곳을 찾아야 함
- 데이터 조각 하나에 진실 공급원이 2개 → 일관성 문제

> 회사에서 종종 보이는 패턴이다. "처리 완료" 알림만 보내고 결과는 API로 다시 조회하게 만드는 구조. 3.3.1(모든 일들을 빠짐없이)이랑 정확히 반대라서, 이벤트에 결과 데이터를 실어 보내는 쪽으로 설계 검토할 때 근거로 쓰기 좋겠다.
