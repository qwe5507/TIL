# 5장. 이벤트 기반 처리 기본

## 이 장 핵심

상태 비저장 마이크로서비스의 기본 루프는 단순하다 — 소비하고, 처리하고, 생산한다. 

이 장의 진짜 주제는 파티션이다. 

키가 같은 이벤트를 같은 파티션에 모으는 게 리파티션, 두 스트림의 파티션 수·키·파티셔너를 맞춰 같은 인스턴스에서 처리되게 하는 게 코파티션. 

---

## 이벤트 기반 마이크로서비스의 기본 실행 구조

대부분의 EDM은 적어도 세 단계를 거침
- **①** 입력 이벤트 스트림에서 이벤트 소비
- **②** 이벤트 처리
- **③** 필요한 출력 이벤트 생산

- 인스턴스는 프로듀서/컨슈머 클라이언트를 생성하거나 컨슈머 그룹에 조인 → 새 이벤트 폴링 → 처리 → 출력 생산을 무한 반복

```java
Consumer consumerClient = new consumerClient(consumerGroupName, ...);
Producer producerClient = new producerClient(...);
while (true) {
    InputEvent event = consumerClient.pollOneEvent(inputEventStream);
    OutputEvent output = processEvent(event);
    producerClient.produceEventToStream(outputEventStream, output);
    // 적어도 한 번 이상 처리
    consumerClient.commitOffsets();
}
```

- `processEvent`가 마이크로서비스 처리 토폴로지의 진입점. 모든 이벤트 처리 로직(비즈니스 로직 적용 + 출력 이벤트 방출)은 여기에 구현
- 출력을 생산한 **뒤에** 오프셋을 커밋하는 순서라서 적어도 한 번 이상(at-least-once) 처리가 됨

## 5.1 상태 비저장 토폴로지 구성

- 토폴로지 설계 = 사고 방식을 이벤트 기반으로 전환하는 일. 이벤트가 들어오면 그에 **반응해서** 코드가 실행되는 구조
- 토폴로지는 본질적으로 이벤트에 수행하는 일련의 작업들 : 필터, 라우터, 변환, 구체화, 취합 중 비즈니스 로직에 필요한 것을 선택
- 함수형 프로그래밍이나 빅데이터 프레임워크 경험자에겐 익숙한 개념

<img width="704" height="180" alt="image" src="https://github.com/user-attachments/assets/00d2dc44-822b-4092-b7ad-30a7a963e146" />

> 간단한 이벤트 처리 토폴로지. 이벤트가 한 번에 하나씩 소비되며 2단계 변환(값 > 10.0 필터 → 소수점 절사)을 거침. 기준에 안 맞는 이벤트는 1단계에서 걸러짐

### 5.1.1 변환

변환 : 하나의 이벤트를 처리해서 필요시 출력 이벤트를 내는 과정. 작업에 따라 리파티션이 필요할 수 있음

| 변환 | 동작 | 리파티션 |
|---|---|---|
| 필터(filter) | 기준을 충족하면 이벤트 전파. 0개 이상 방출 | 불필요 |
| 맵(map) | 키, 값, 또는 둘 다 변경. 정확히 1개 방출 | 키 변경 시 데이터 지역성 보장 위해 필요할 수 있음 |
| 맵밸류(mapValue) | 키는 그대로, 값만 변경. 정확히 1개 방출 | 불필요 |
| 맞춤 변환(custom transform) | 맞춤 로직 적용. 상태 조회, 다른 시스템과 동기 통신 등 | 경우에 따라 |

### 5.1.2 스트림 분기 및 병합

분기
- 이벤트에 논리 연산을 적용한 결과에 따라 새로운 스트림으로 출력
- 특정 속성(국가, 표준 시간대, 출처, 제품 등)에 따라 라우팅하는 경우가 많음
- 처리 중 에러 발생 시 이벤트를 삭제하지 않고 **데드-레터 스트림**에 출력하는 패턴도 분기의 일종

병합
- 여러 입력 스트림의 이벤트를 소비해 유의미하게 처리한 뒤 하나의 출력 스트림으로
- 병합이 중요한 시나리오는 많지 않음 — 마이크로서비스는 그냥 여러 입력 스트림에서 소비해 비즈니스 로직을 수행하는 게 더 일반적
- 다수 입력 스트림을 일관되고 재생산 가능한 순서로 소비하는 방법은 6장

> **WARNING** 이벤트 스트림을 병합할 때에는 병합된 이벤트 스트림 도메인을 나타내는 새로운 통합 스키마를 정의할 것. 이런 도메인이 별 의미가 없다면 스트림을 그대로 둔 상태로 전체 시스템 설계를 다시 고민해보는 편이 좋다.

## 5.2 이벤트 스트림 리파티션

- 이벤트 스트림은 이벤트 키 + 이벤트 파티셔너(분할기) 로직에 의해 파티셔닝됨
- 리파티션 : 다음 중 하나 이상의 속성을 바꿔 새 이벤트 스트림을 생산하는 행위
  - **상이한 파티션 수** : 다운스트림 병렬도를 높이거나, 코파티션을 위해 다른 스트림과 수를 맞춤
  - **상이한 이벤트 키** : 같은 키의 이벤트가 동일 파티션에 배치되도록 키를 변경
  - **상이한 이벤트 파티셔너** : 파티션 선택 로직 변경
- 순수 상태 저장 처리기가 리파티션하는 건 드묾 (병렬도 확장 목적 제외)
- 대신 **상태 비저장 마이크로서비스가 다운스트림 상태 저장 처리기를 위해 이벤트를 리파티션해주는** 용도로 활용

> **TIP** 일반적으로 파티셔너 알고리즘은 해시 함수로 이벤트 키를 특정 파티션에 확정적으로 매핑한다. 그래서 키가 동일한 이벤트는 모두 동일한 파티션으로 들어간다.

### 5.2.1 예제: 이벤트 스트림 리파티션

- 웹 URL로 인입되는 사용자 데이터 스트림. 사용자 액션이 이벤트로 변환돼 사용자 ID + 관련 데이터가 페이로드에 실림
- 소스 스트림이 어떻게 파티셔닝됐든, 특정 사용자의 데이터는 모두 같은 파티션에 넣고 싶음 → 사용자 ID를 키로 리파티션

<img width="745" height="396" alt="image" src="https://github.com/user-attachments/assets/89d977d6-a225-4ee2-a5be-9773d0afe0d8" />

> 이벤트 스트림 리파티션. 사용자 ID 값에 기본 해시 파티셔너를 적용해 파티션에 할당

- 주어진 키의 모든 이벤트를 단일 파티션에 몰아넣음 = **데이터 지역성**의 토대
- 컨슈머는 한 파티션만 소비해도 해당 키 이벤트의 전체 그림 완성 → 인스턴스가 파티션을 하나씩 맡아 수평 확장 가능
- 리파티션 + 데이터 지역성 = 대규모 상태 저장 처리의 필수 불가결한 요소

## 5.3 이벤트 스트림 코파티션

- 코파티션 : 어떤 스트림을 **파티션 수 + 파티션 어사이너 로직이 동일한** 새 스트림으로 리파티션하는 것
- 한 스트림의 키 있는 이벤트를 다른 스트림의 이벤트와 같은 장소에 배치(코로케이션)할 때 필요
- 스트리밍 조인 같은 키 기반 상태 저장 작업 : 출처 스트림과 무관하게 **같은 키는 같은 노드에서** 처리해야 함 → 상태 저장 스트림 처리의 핵심 개념 (7장 상세)

### 5.3.1 예제: 이벤트 스트림 코파티션

- 리파티션한 사용자 이벤트 스트림과 사용자 엔티티 스트림을 키별로 조인
- 두 스트림의 파티션 수 동일 + 파티셔너 알고리즘 동일 → 파티션별 키 분포가 일치 → 각 컨슈머 인스턴스가 자기 파티션 쌍만 조인하면 됨

## 5.4 컨슈머 인스턴스에 파티션 할당

- 마이크로서비스는 각자 고유한 컨슈머 그룹을 유지 → 입력 스트림의 오프셋을 집합적으로 나타냄
- 첫 컨슈머 인스턴스가 그룹명으로 브로커에 등록 → 브로커가 인스턴스당 파티션 할당
- 카프카 : 컨슈머 그룹에 가장 첫 번째로 등록된 클라이언트에게 파티션 할당 책임을 위임 → 이 인스턴스가 **컨슈머 그룹 리더**로서 파티션 어사이너 역할 (새 인스턴스 조인 시마다 파티션 할당)
  - 브로커 쪽에서 이를 담당하는 프로세스는 컨슈머 그룹 코디네이터. 코디네이터(브로커 중 하나) ≠ 그룹 리더(컨슈머 인스턴스 중 하나) — 용어 혼동 주의
- 펄사처럼 브로커 내부에서 파티션 할당을 중앙화 관리하는 브로커도 있음. 할당/리밸런스는 브로커가 해도 컨슈머 그룹 식별 메커니즘은 동일
- 파티션이 할당되면 가장 최근에 소비한 오프셋부터 처리 시작 (그룹 오프셋이 없으면 auto.offset.reset으로 시작 위치 조절, 기본값 latest)
- **재할당 시에는 경합 방지를 위해 모든 처리를 잠시 중단** → 파티션을 회수해 새 인스턴스에 넘기기 직전에 다른 인스턴스가 처리하지 못하게 막아 중복 출력 방지

### 5.4.1 파티션 어사이너로 파티션 배정

- 대량 데이터 처리 = 컨슈머 마이크로서비스를 여러 인스턴스로 병렬 실행
- 파티션 어사이너 : 공평하고 안정된 방법으로 파티션을 인스턴스들에 골고루 분배
- 인스턴스 추가/삭제 때마다 재할당도 담당. 어사이너 컴포넌트는 브로커 종류에 따라 컨슈머 클라이언트에 탑재되거나 브로커 내부에서 관리

### 5.4.2 코파티션된 파티션 할당

- 어사이너는 코파티션 요건 충족도 책임짐 : 코파티션으로 표시된 모든 파티션은 **동일한 하나의 컨슈머 인스턴스에** 할당돼야 함
- 그래야 비즈니스 로직 수행에 필요한 이벤트 데이터의 하위 집합이 정확하게 할당됨
- 여러 스트림의 파티션 수가 같은지 체크해서 다르면 예외를 던지는 로직을 어사이너 코드에 두는 게 좋음

### 5.4.3 파티션 할당 전략

할당 알고리즘의 목표
- **①** 인스턴스 처리 능력이 동등하다는 전제 하에 파티션을 전체에 고루 분배
- **②** 리밸런스 중 재할당되는 파티션 수 최소화
  - 여러 저장소 인스턴스에 샤딩된 구체화 상태를 다룰 때 특히 중요 — 재할당되면 이후 업데이트가 엉뚱한 샤드로 향할 수 있음 (7장)

**라운드-로빈 할당**
- 전체 파티션 리스트를 만들어 인스턴스마다 하나씩 순서대로 할당. 코파티션된 스트림은 별도 리스트로 관리해 적절히 할당

<img width="506" height="369" alt="image" src="https://github.com/user-attachments/assets/6070878b-48c8-4b89-934a-a4867be75447" />

 라운드-로빈 방식으로 두 컨슈머 인스턴스에 파티션 할당. 코파티션된 세트는 c0이 2세트, c1이 1세트

<img width="732" height="351" alt="image" src="https://github.com/user-attachments/assets/976af937-f9fd-4447-b084-559e504dc5da" />

> 라운드-로빈 방식으로 네 컨슈머 인스턴스에 파티션 할당. c3는 추가로 할당할 코파티션 세트가 없어 단독 파티션만 받음

- 코파티션 세트 수보다 인스턴스를 늘려도 병렬도는 더 이상 증가하지 않음

**정적 할당**
- 특정 파티션을 특정 컨슈머에 고정. 내부 상태 저장소에서 대용량 상태를 구체화할 때 아주 유용
- 인스턴스가 그룹을 떠나도 재할당하지 않고 복귀를 기다림 (제한 시간 내 복귀 실패 시 동적 재할당하도록 설정 가능)

**맞춤 할당**
- 외부 신호나 다른 도구를 이용해 클라이언트 요건에 최적화된 할당 로직을 직접 작성
- ex. 입력 스트림의 현재 랙 상태에 따라 파티션을 할당해 작업 부하를 고루 분산

> 정적 할당의 존재 이유가 처음엔 갸웃했는데, 상태 저장 처리 관점에서 보니 이해된다. 인스턴스가 잠깐 죽었다 살아나는 경우 로컬에 구체화해둔 상태를 버리고 딴 데서 다시 만드는 것보다 그냥 기다리는 게 싸다는 계산. ECS 태스크 재기동 시간을 아는 입장에선 꽤 현실적인 전략.

## 5.5 상태 비저장 처리 인스턴스 실패 복구

- 상태 비저장 처리의 실패 복구 = 그냥 컨슈머 그룹에 새 인스턴스를 추가하는 것과 동일
- 복구할 상태가 없으므로 파티션 할당 + 오프셋 확보 즉시 곧바로 이벤트 처리 가능

## 5.6 마치며

- 기본 상태 비저장 EDM : 이벤트를 소비/처리하고 후속 이벤트를 방출. 각 이벤트는 다른 이벤트와 독립적으로 처리됨
- 기본 변환만으로도 이벤트를 더 유용한 포맷으로 변경 가능. 파티션 수를 달리하고 키를 새로 할당하는 리파티션도 가능
- 코파티션 = 키 + 파티셔너 알고리즘 + 파티션 수가 동일한 스트림들. 코파티션해야 컨슈머 인스턴스에서 데이터 지역성 확보
- 파티션 어사이너는 인스턴스 간 균등 분배 + 코파티션 스트림의 올바른 할당 담당
- 코파티션과 파티션 할당은 상태 저장 처리(7장)의 토대
