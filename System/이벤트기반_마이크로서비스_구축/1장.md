# 1장. 왜 이벤트 기반 마이크로서비스인가?

## 이 장 핵심

- 소프트웨어는 조직의 통신 구조를 따라간다(콘웨이의 법칙). 
- 문제는 시스템 간 데이터를 주고받는 데이터 통신 구조가 대부분 애드혹으로 굴러간다는 것. 
- 이벤트 기반 아키텍처는 데이터의 생산과 접근을 분리해서 이 취약한 데이터 통신 구조를 정규화한다.
  - 이벤트 스트림이 단일 진실 공급원이 되고, 컨슈머가 알아서 가져다 쓰는 구조.

---

## 1.1 이벤트 기반 마이크로서비스란?

- 이벤트 기반 통신 자체는 새로운 게 아님 (SOA, 메시지 전달 아키텍처에서 예전부터 사용)
- 달라진 것 : 대규모 확장 + 실시간 처리 요건, 그리고 이걸 감당하는 최신 이벤트 브로커의 등장

현대 EDM 아키텍처의 특징
- 시스템끼리 이벤트를 생산/소비하는 식으로 통신
- **이벤트는 소비돼도 사라지지 않음** → 같은 이벤트를 다른 컨슈머도 가져갈 수 있게 보존
  - 이게 이 책에서 다루는 강력한 패턴들을 가능하게 하는 핵심 차이점

> SQS 같은 메시지 큐랑 결정적으로 다른 부분. 큐는 컨슈머가 가져가면 메시지가 사라지는데 이벤트 스트림은 로그로 남는다. 회사에서 SNS 팬아웃으로 큐 여러 개에 뿌리는 것도 결국 "여러 컨슈머" 문제를 큐 방식으로 푸는 우회로였다고 이해.

서비스의 단위
- "작게" = 개발 기간 2주 이내, 개념적으로 머릿속에 다 들어올 정도
- 하는 일 : 입력 이벤트 스트림 소비 → 비즈니스 로직 적용 → 출력 이벤트 발행 / 요청-응답용 데이터 제공 / 서드파티 API 호출
- 상태 저장(stateful) / 상태 비저장(stateless)으로 분류, FaaS 형태 구현도 가능

이벤트 스트림 + 마이크로서비스 = 조직 전반에 걸친 연결된 활동 그래프. 모놀리스 간 통신이 무거운 전통 아키텍처에도 구조가 비슷한 그래프는 존재함.

## 1.2 도메인 주도 설계와 경계 콘텍스트

에릭 에반스의 DDD 개념 중 EDM 구축에 필요한 것만.

| 개념 | 정리 |
|---|---|
| 도메인 | 비즈니스가 차지하는 문제 공간. 규칙, 프로세스, 용어 전부 포함 |
| 하위 도메인 | 메인 도메인의 컴포넌트. 보통 조직 구조(창고, 영업 등) 반영. 역시 문제 공간 |
| 도메인 모델 | 실제 도메인을 비즈니스 용도에 맞게 추상화한 것. 솔루션 공간 |
| 경계 콘텍스트 | 하위 도메인과 연관된 입력/출력/이벤트/데이터 모델의 논리적 경계 |

- 경계 콘텍스트 = 하위 도메인이면 이상적이지만, 레거시·기술 부채·서드파티 연계 때문에 예외가 많음
- 경계 콘텍스트의 2원칙
  - **강한 응집** : 내부 기능은 깊이 연관, 통신은 대부분 경계 안에서만 → 설계 범위가 좁아지고 구현 단순해짐
  - **느슨한 결합** : 한 콘텍스트의 변경이 이웃 콘텍스트에 주는 영향 최소화 → 각자 독립적으로 움직임

### 1.2.1 도메인 모델과 경계 콘텍스트 활용

- 모든 조직은 하나의 도메인을 형성 → 하위 도메인으로 계속 분할됨
- 하위 도메인 모델은 "작고 독립적인 팀이 서비스로 옮길 수 있을 정도"까지 쪼개짐
- 이 하위 도메인 중심으로 경계 콘텍스트가 형성 → 마이크로서비스 탄생의 기초

### 1.2.2 비즈니스 요건에 따라 경계 콘텍스트 조정

경계 콘텍스트는 기술 요건이 아니라 **비즈니스 요건** 중심으로.
- 근거 : 비즈니스 요건은 계속 바뀌지만, 요건 변경 없이 구현체를 뜯어고치는 일은 거의 없음

| 기준 | 결과 |
|---|---|
| 비즈니스 요건에 맞춤 (각자 소유) | 팀별 느슨한 결합 + 고응집 구현체. 팀 간 의존 감소, 자기 요건에만 전념 |
| 기술 요건에 맞춤 (공동 소유) | 비즈니스 기능 책임이 여러 팀에 분산. 아무도 100% 책임 안 짐. 서비스가 팀/API 경계 넘나들며 결합 → 사소한 변경도 비싸짐 |

<img width="609" height="256" alt="image" src="https://github.com/user-attachments/assets/83a852f8-8e0e-4990-94c6-2e558d330777" />

> 비즈니스 콘텍스트에 맞출 것인가, 기술 콘텍스트에 맞출 것인가

- 트레이드오프 : 코드 중복, 비슷한 데이터 접근 패턴 반복 발생
- 그래도 장기적으로는 "단단한 결합"의 대가가 "중복"보다 훨씬 비쌈
- 대신 팀마다 풀스택 전문성이 필요해지는 부담 → 조직 차원의 지원 필요 (14장)

> 경계 콘텍스트 간 결합은 느슨하게, 상호 의존은 최소로. 그래야 다른 시스템에 피해 없이 콘텍스트 구현체를 변경할 수 있다.

## 1.3 통신 구조

통신 구조 : 조직 안에서 팀/시스템/사람이 소통하며 형성되는 의존 관계의 토폴로지. 3가지가 있음.

### 1.3.1 비즈니스 통신 구조

- 팀과 부서 간의 통신. 팀별 요건과 책임을 배정하는 구조
- 기술팀은 제품 생산, 판매팀은 판매, 지원팀은 고객 만족 담당하는 식

> 비즈니스 통신 구조 예 (판매팀-기술팀-지원팀 요청 흐름)

### 1.3.2 구현 통신 구조

- 하위 도메인 모델에 대해 조직이 규정한 데이터와 로직 → 비즈니스 프로세스, 데이터 구조, 시스템 설계를 정규화한 것
- 전형적 예 : 모놀리식 DB 애플리케이션
- 비즈니스 요건을 다시 정의하면 로직을 다시 짜야 함 → 유연성과 트레이드오프

> 구현 통신 구조 예 (팀별 모놀리스가 각자 DB를 품은 구조)

### 1.3.3 데이터 통신 구조

- 비즈니스 전반에 걸쳐, 특히 구현체 간에 데이터를 주고받는 프로세스
- 소프트웨어 구현에서 대체로 무시돼온 영역
  - 시스템 간 애드혹 통신 정도의 역할만 수행
  - 구현 통신 구조가 데이터 통신까지 **1인 2역** → 기업이 성장할수록 여기서 문제 폭발

### 1.3.4 콘웨이의 법칙과 통신 구조

> 시스템 구조는 그 시스템을 설계하는 조직의 통신 구조를 그대로 따라갈 수밖에 없다. — 멜빈 콘웨이 (1968)

- 비즈니스 통신 구조 → 사람들을 팀으로 조직, 팀 경계에 의해 구분된 제품 생산
- 구현 통신 구조 → 자기 제품의 하위 도메인 데이터 접근은 잘 제공하지만, 데이터 통신 기능이 약해서 다른 제품에서의 접근은 제한적

도메인 데이터는 대부분 다른 경계 콘텍스트에서도 필요함. 그런데 구현 통신 구조가 공유 수단으로 부적절 → 2가지 부작용
- **①** 조직 전체에 도메인 데이터를 전달하는 방식이 비효율적 → 신제품 만들기 어려움
- **②** 기존 데이터에 접근하려고 기존 도메인(모놀리스)을 계속 확장하는 위험 감수 → 모놀리식 설계에 내재된 패턴

기존 해결책들과 한계

| 방식 | 문제 |
|---|---|
| 공유 DB | 안티패턴 발생하기 쉽고, 확장해도 성능 요건 못 맞추는 경우가 태반 |
| 읽기 전용 레플리카 | 내부 데이터 모델이 불필요하게 노출 |
| 배치 덤프 → 파일 저장소 | 진실 공급원이 여러 개 생겨 데이터 일관성 하락 |

→ 셋 다 구현체를 단단히 결합시키고 점대점 통신을 강요하는 경직된 아키텍처의 산물

> 데이터 접근이 어렵거나 데이터가 구현체 하나에 몰려 제품 범위가 제한되고 있다면, 데이터 통신 구조 부실의 대가를 치르고 있는 것. 조직이 성장할수록 심각해진다.

## 1.4 기존 컴퓨팅의 통신 구조

상황 가정 : 단일 데이터 저장소 + 단일 서비스를 운영하던 팀에 신규 비즈니스 요건 접수. 기존 업무와 무관하지도, 같지도 않은 애매한 요건. → 새 서비스를 만들까, 기존 서비스에 붙일까?

### 1.4.1 옵션 1: 서비스를 새로 만듦

- 요건 차이가 크면 신규 서비스가 나을 수 있음. 나중에 팀 분할 시 소유권 나누기도 쉬움
- 문제는 데이터 : 새 기능도 옛 데이터가 필요한데, 그 데이터는 기존 서비스에 묶여 있음
- 감수해야 할 것들
  - 원본 저장소 → 새 저장소로 데이터 복사 방법 강구
  - 데이터 구조 변경이 타 팀에 영향 없도록 + 내부 로직 노출 안 되도록 관리
  - 복사본은 김빠진(stale) 데이터가 됨 → 원본에 쿼리 부하 안 주면서 실시간에 가깝게 복사할 능력 필요
  - 이 과정 전체 모니터링
  - 저장소 2개 + 서비스 2개의 로깅/모니터링/테스트/배포/롤백 프로세스

### 1.4.2 옵션 2: 기존 서비스에 추가

- 장점 : 데이터가 이미 저장소에 있고, 운영 프로세스도 익숙 → 바로 착수 가능
- 리스크는 더 미묘함
  - 여러 모듈이 같은 코드베이스에 엮여 경계가 모호해짐
  - 경계 넘나들며 직접 결합 → 기능 추가는 빠른데 결합도 상승, 응집도/모듈성 하락
  - 계획 잘 세워서 경계를 지킬 수도 있지만, 빠듯한 일정 + 경험 부족으로 실패하는 경우 다수

### 1.4.3 옵션별 장단점

- 많은 팀이 옵션 2 선택. 모놀리스는 여전히 강력하고 가치 있으므로 잘못된 선택은 아님
- 옵션 1이 우선되는 경우
  - 다른 시스템 데이터에 안정적으로 접근하기 어려울 때 (특히 대규모 실시간)
  - 신규 서비스 관리 오버헤드/리스크가 크고, 관리 체계가 조직에 아직 없을 때

핵심 딜레마는 결국 데이터. 로컬 데이터는 쉽고, 남의 저장소에 캡슐화된 데이터는 어려움.

데이터 복사 방식의 문제
- 저장하는 팀 ↔ 복사하는 팀 사이에 끈끈한 의존 발생, 데이터 변경 때마다 동기화 작업
- 복제 쿼리가 소스 시스템에 과부하 → 확장성/성능/가용성 문제
- 동기화 실패를 긴급 상황 전까지 모를 수 있음
- 부족 지식(tribal knowledge) 탓에 복사본을 원본으로 착각하는 해프닝
- 복사가 끝날 즈음이면 이미 김빠진 데이터. 서로 상대가 완벽한 최신 사본을 가졌다고 안심할 때 문제가 커짐
  - ex) 보고 서비스가 시차 때문에 과금 서비스와 다른 값을 보고 → 다운스트림 의사결정 사고

> 회사에서 AML 쪽 데이터 정합성 맞출 때 겪은 상황이랑 거의 똑같다. "복사본인데 원본인 줄 알고 쓰는" 문제는 조직이 커질수록 아무도 모르게 퍼진다.

관점 전환 : 회사 곳곳에 정확한 데이터를 전달 못하는 건 개념의 결함이 아니라 **데이터 통신 구조가 취약하거나 아예 없기 때문**

> 핵심 비즈니스 데이터는 그것을 필요로 하는 모든 서비스가 쉽게 획득/사용할 수 있어야 한다.
> EDM의 기본 교리 중 하나. 애드혹 데이터 통신 구조를 정규 데이터 통신 구조로 바꾸면 데이터 접근의 고질적 문제가 대부분 해소된다.

### 1.4.4 팀 시나리오(계속)

1년 후. 옵션 2를 택한 팀이 성장 → 2개 팀으로 재편.
- 비즈니스 요건은 업무 영역 기준으로 깔끔하게 나눠지는데, 구현 통신 구조는 나누기 어려움
- 두 팀 모두 동일한 데이터가 대량으로 필요
  - 어느 팀이 어떤 데이터를 소유하나?
  - 데이터는 어디에 두나?
  - 두 팀 모두 값을 변경하는 데이터는?
- 결론은 "데이터 대신 서비스 공유" → 팀 간 긴밀한 소통 + 작업 동기화 필요 → 생산성 지연 요소

### 1.4.5 상충되는 압력

- 데이터를 한 서비스 로컬에 두고 기능을 빨리 추가하고 싶다 ↔ 구현 통신 구조 확장 비용을 계속 부담해야 한다
- 팀이 커지면 비즈니스 통신 구조는 분할해야 한다 ↔ 구현 통신 구조는 그 모습대로 재배정이 안 된다
- 모든 문제의 근원 : **구현 통신 구조 간의 데이터 통신 수단이 취약하고 제대로 정의되지 않은 것**

## 1.5 이벤트 기반 통신 구조

- 요청-응답을 전부 대체하는 게 아니라, 완전히 다른 서비스 간 통신 수단을 제시
- 핵심 : **데이터의 생산/소유 ↔ 데이터 접근의 분리**
- 서비스는 직접 요청-응답 API에 얽매이지 않고, 이벤트 스트림에 정의된 이벤트 데이터를 매개로 소통
- 프로듀서는 자기 스트림에 잘 정의된 데이터를 생산하는 일만 책임짐

### 1.5.1 이벤트는 통신의 근간이다

- 공유 데이터를 모조리 이벤트 스트림 세트에 발행 → 조직에서 일어난 모든 일이 지속적으로 정규화된 형태로 기록됨 = 시스템 간 통신 채널
- **이벤트가 곧 데이터**
  - "데이터가 준비됐다"는 신호나 데이터 운반 수단이 아님
  - 이벤트 자체가 데이터 스토리지이면서 동시에 서비스 간 비동기 통신 수단

### 1.5.2 이벤트 스트림은 단일 진실 공급원이다

- 스트림 안의 각 이벤트 = 진술서(statement of fact)
- 이것들을 취합하면 조직 내 모든 시스템이 통신하는 근간인 단일 진실 공급원(single source of truth)이 됨
- 통신 구조는 정보가 정확할 때만 유효 → 팀마다 상충되는 데이터를 제각기 두면 백본 기능이 무너짐
- 조직 차원에서 이벤트 스트림을 진실 공급원으로 채택하는 게 중요

### 1.5.3 컨슈머가 스스로 모델링과 쿼리를 수행한다

- 기존 : 데이터 소유자가 쿼리/검색 기능까지 제공 (과도하게 확장된 구현 통신 구조)
- 이벤트 기반 : 데이터 접근과 모델링 요건이 완전히 컨슈머로 이동
  - 컨슈머가 소스 스트림에서 이벤트 사본을 가져와 스스로 혼합, 쿼리, 비즈니스 로직 적용
  - 모든 비즈니스/애플리케이션 로직은 프로듀서/컨슈머 안에 캡슐화
  - 각자 자기 경계 콘텍스트의 니즈만 책임지면 됨

### 1.5.4 조직 전반적으로 데이터 통신이 원활해진다

- 공유 데이터가 구현 통신 구조 밖으로 노출됨
- 전부 발행할 필요는 없고, 다른 팀/서비스가 관심 있는 데이터만 공용 스트림에 발행
- 데이터 생산과 소유권의 완전한 분리 → 느슨한 결합 + 높은 응집이라는 경계 콘텍스트 원칙을 지키기 쉬워짐
- 점대점 커넥션이나 API 없이 표준 이벤트 스트림에서 데이터를 가져와 자신의 모델과 상태를 생성

### 1.5.5 접근 가능한 데이터 덕분에 비즈니스 통신 변경이 가능하다

- 팀 구조는 계속 바뀌고 프로젝트는 시작하고 끝남
- 하지만 핵심 도메인 이벤트는 구현체에 의존하지 않음 → 모든 신제품에서 언제든 활용 가능
- 조직 재편에 유연해짐

## 1.6 비동기식 이벤트 기반 마이크로서비스

EDM의 이점 7가지
- **세분성** : 서비스가 경계 콘텍스트에 알맞게 매핑, 요건 변경 시 재작성 용이
- **확장성** : 개별 서비스 단위로 규모 조절
- **기술 유연성** : 서비스마다 최적의 언어/기술 선택, 프로토타이핑 용이
- **비즈니스 요건 유연성** : 작은 단위라 소유권 재조정이 쉬움, 요건 변화에 신속 대응
- **느슨한 결합** : 특정 구현 API가 아니라 도메인 데이터와 결합
- **지속적 전달 지원** : 작은 모듈은 배포/롤백이 간편
- **우수한 시험성** : 디펜던시가 적어 모킹과 커버리지 관리 용이

### 1.6.1 이벤트 기반 마이크로서비스 예제

앞의 팀 시나리오를 이벤트 기반으로 다시 풀면
- 예전 고민(데이터 소싱/싱크, 배치 동기화, 동기 API 구현)이 거의 사라짐
  - 새 마이크로서비스가 이벤트 스트림에서 데이터 수신, 필요시 초기 데이터부터 가져옴
- 가져온 데이터의 저장/구성은 전적으로 팀 소관 → 필요한 필드만 취사선택
- 서비스를 잘게 나누면 팀 확장/재구성 때 소유권 재배정이 쉬움
  - 이벤트 데이터 소유권은 생산하는 서비스 쪽으로 이동
- 오버헤드 최소화 → 스파게티 코드와 모놀리스 비대화 예방
  - 확장은 개별 서비스의 CPU/메모리/디스크/인스턴스 수 조절에 집중

전제 조건 : 데이터 통신 구조에 실제로 데이터가 있어야 하고, 마이크로서비스 군단을 배포/관리할 수단이 필요 → 조직 전체 차원의 도입이 필요함

## 1.7 동기식 마이크로서비스

- 마이크로서비스는 비동기 이벤트 방식(책의 권장) 말고 SOA식 동기 요청-응답 방식으로도 구현 가능

### 1.7.1 동기식 마이크로서비스의 단점

- 넷플릭스, 우버 같은 성공 사례가 있다고 동기식이 정답인 건 아님
  - 스파게티 모놀리스로 부를 쌓은 회사도 많음 → 회사의 성공과 아키텍처 품질을 혼동하지 말 것

| 문제 | 내용 |
|---|---|
| 점대점 결합 | 의존이 꼬리에 꼬리를 물면 어떤 서비스가 어떤 로직을 담당하는지 파악 곤란. 연결 수 증가로 통신 구조 고착화 |
| 의존적 확장 | 내 서비스의 확장 가능 여부가 의존하는 모든 서비스의 확장 가능성 + 팬아웃 정도에 좌우됨 |
| 서비스 실패 처리 | 의존 서비스 다운 시 처리/재시도/복구 절차를 전부 정해야 함. 서비스가 많을수록 어려움 |
| API 버저닝 | 여러 API 정의와 서비스 버전 혼재. 클라이언트를 최신 API로 강제 업그레이드시키기 어려움 |
| 데이터 접근이 구현체에 종속 | 외부 데이터 접근 문제가 기존 방식과 동일하게 발생 |
| 분산 모놀리스 | 서비스들이 얽혀 분산 모놀리스처럼 동작. 경계 콘텍스트 경계선이 흐려짐 |
| 테스트 | 의존 서비스가 다 떠 있어야 해서 통합 테스트가 정말 어려움 |

> 분산 모놀리스는 MSA 전환 얘기 나올 때마다 등장하는 단골 실패 패턴. 모놀리스 내부 경계를 그대로 동기 점대점 호출로 흉내내면 기존 코드와 라인 단위로 맞물린다는 표현이 와닿는다.

### 1.7.2 동기식 마이크로서비스의 장점

- 사용자 인증, A/B 테스트처럼 직접 요청-응답이 유리한 데이터 접근 패턴 존재
- 외부 서드파티 연동은 거의 항상 동기식 (언어 무관, HTTP)
- 추적/디버깅 용이 : 어느 함수가 어디서 호출됐는지 로그로 파악 가능, 가시성 좋음
- 웹/모바일 호스팅은 거의 다 요청-응답 기반
- 인력 : 동기식/모놀리스 스타일에 익숙한 개발자가 훨씬 많아 채용이 쉬움

> 사내 아키텍처를 100% 이벤트 기반으로 가져가는 회사는 거의 없다. 동기/비동기 솔루션이 공존하는 하이브리드 아키텍처가 표준이 될 것.
