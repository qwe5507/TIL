# 8장. 마이크로서비스 워크플로 구축

다루는 주제
- 워크플로 구성 시 고려 사항 (생성/수정, 모니터링, 분산 트랜잭션)
- 코레오그래피 패턴
- 오케스트레이션 패턴 (이벤트 기반 / 직접 호출)
- 분산 트랜잭션과 사가 패턴
- 보상 워크플로

## 이 장 핵심

7장까지가 단일 서비스의 내부였다면 이 장부터는 여러 서비스가 모여 하나의 비즈니스 워크플로를 이루는 방법이다. 

축은 두 개 — 각자 알아서 반응하는 코레오그래피(무용수)와 중앙에서 명령을 내리는 오케스트레이션(지휘자). 

결합도와 유연성은 코레오그래피가, 가시성과 변경 용이성은 오케스트레이션이 이긴다. 

분산 트랜잭션(사가)은 가능한 한 피하되, 필요하면 이 두 패턴 위에 롤백 로직을 얹어 구현한다. 

그리고 모든 실패를 롤백으로 풀 필요는 없다 — 비즈니스로 무마하는 보상 워크플로도 있다.

---

## 도입 : 워크플로 구성 시 고려 사항

- 워크플로 : 논리적 분기, 보상 액션 등 비즈니스 프로세스를 구성하는 특정 작업들. 여러 마이크로서비스가 각자 경계 콘텍스트를 가지고 태스크 수행 후 다운스트림에 새 이벤트를 전달하는 식으로 흘러감

주요 고려 항목 3가지
- **워크플로 생성 및 수정** : 서비스들이 서로 어떻게 연관되나? 수정 시 진행 중 작업 중단, 다수 서비스 변경, 모니터링/가시성 붕괴를 어떻게 피하나?
- **워크플로 모니터링** : 어떤 이벤트의 워크플로가 언제 완료됐는지, 어디서 실패/교착됐는지, 전체 상태는 어떻게 보나?
- **분산 트랜잭션 구현** : 여러 액션이 함께 일어나거나 아무것도 일어나지 않아야 할 때 어떻게 구현하고 어떻게 롤백하나?

## 8.1 코레오그래피 패턴

- 코레오그래피 아키텍처 (= 리액티브 아키텍처) : 고도로 분리된(decoupled) 마이크로서비스 아키텍처
- 서비스는 업스트림 프로듀서/다운스트림 컨슈머와 완전히 독립적으로, 차단·대기 없이 입력 이벤트가 도착하는 대로 반응
  - 무용수가 공연 중 누구의 지시도 받지 않고 자기 분량의 춤을 알아서 소화하는 것
- 프로듀서는 자신의 데이터를 누가 소비할지, 무슨 로직을 적용할지 모름 → 업스트림 로직과 다운스트림 컨슈머의 완전한 분리
- 효과 : 느슨한 결합 → 팀 간 조정 요건 감소. 새 서비스 추가/기존 서비스 삭제가 쉬움
- 코레오그래피 워크플로 = 개별 서비스 + 그들 간 관계까지 포함하는 **창발적 행위(emergent behavior)**의 한 형태

> **NOTE** 직접 호출 아키텍처는 재사용 가능한 "서비스"를 워크플로 구성 요소로 활용하는 데 초점을 두고, 이벤트 기반 아키텍처는 다운스트림 소비를 전혀 모르는 상태에서 재사용 가능한 "이벤트"를 제공하는 데 집중한다. 이 덕분에 고도로 분리된 코레오그래피가 가능해진다.

- 대비 : 직접 호출 아키텍처에서는 호출하는 서비스가 "어느 서비스를 호출해야 하나 + 왜 호출해야 하나(비즈니스 기대치)"를 알아야 함 → 단단히 결합, 기존 경계 콘텍스트에 종속

- 서비스 A → 스트림1 → 서비스 B → 스트림2 → 서비스 C → 출력. C의 출력이 전체 워크플로의 결과

<img width="610" height="119" alt="image" src="https://github.com/user-attachments/assets/342091a9-28df-4d8d-af30-2ac307d41910" />

> 간단한 이벤트 기반 코레오그래피 워크플로 (A → B → C)

- 요건 변경 : C를 B보다 먼저 처리하도록 재조정한다면?
  - B는 스트림2에서, C는 스트림1에서 소비하도록 프로듀서/컨슈머 관계 수정
  - 스트림 내부 데이터 포맷이 새 워크플로 요건에 안 맞을 수 있음 → 다른 컨슈머에게 영향 주는 **중대한 스키마 변경 불가피**. 아예 새 스키마를 만들어야 할 수도
  - 토폴로지 교체 전, A·B·C의 모든 출력 이벤트가 처리 완료됐는지 확인 필수 (일관되지 않은 상태로 방치된 이벤트 금지)

### 8.1.2 코레오그래피 워크플로의 생성과 수정

- 워크플로 끝에 새 단계 추가는 간단. **중간 삽입이나 순서 변경이 문제**
- 서비스 간 관계는 워크플로 콘텍스트 외부에서 이해하기 어려움 → 서비스 수가 늘수록 악화
- 비즈니스 기능이 여러 인스턴스에 걸쳐 있으면 더 취약 → 경계 콘텍스트를 침해하지 않는 선에서 전체 비즈니스 기능을 하나의 서비스로 로컬화하면 어느 정도 해결
- 그래도 비즈니스 로직이 조금만 바뀌면 순서가 바뀌는 서비스 + 다수의 서비스를 수정/뜯어고쳐야 할 수 있음

### 8.1.3 코레오그래피 워크플로 모니터링

- 개별적으로 분산돼 있어 특정 이벤트의 진행 상황 파악이 어려움
- 중요한 워크플로는 처리 중 교착/실패 가능성을 고려해 **각 출력 이벤트 스트림을 받아 상태 저장소로 구체화**할 필요
- 워크플로를 바꾸면 가시성 체계도 함께 변경해야 함
- 가시성 요건은 관찰자마다 천차만별
  - ex) 대형 온라인 소매업체 주문 이행 : 관여 서비스 수십~수백 개
  - 고객은 자기 주문의 진행 상황(결제/이행/배송 알림)만 관심 → 세 스트림에서만 꺼내 모니터링하면 충분 (퍼블릭 속성 + 스트림 수가 적어 변화에 탄력적)
  - 종단간 워크플로 전체를 보려면 수십 개 스트림 소비 필요. 워크플로가 자주 바뀌면 더 까다로움

> **TIP** 코레오그래피 워크플로에서 무엇을 가시화하려는지 확신이 있어야 한다. 관찰자마다 요건이 다르고 워크플로의 모든 단계를 드러내야 할 필요는 없다.

## 8.2 오케스트레이션 패턴

- 중앙의 오케스트레이터 마이크로서비스가 하위 워커 마이크로서비스에게 명령을 내린 뒤 응답을 기다림 (지휘자-오케스트라)
- 오케스트레이터는 비즈니스 프로세스의 전체 워크플로 로직을 알고 있고, 워커에게 특정 이벤트를 전달해 무슨 일을 할지 알림

> **TIP** 오케스트레이터는 명령을 수신한 서비스가 응답할 때까지 기다렸다가 워크플로 로직에 따라 결과를 처리한다. 중앙 조정 서비스가 없는 코레오그래피와 다른 점이다.

- 워크플로를 **하나의 마이크로서비스 안에서** 유연하게 정의. 어느 파트가 완료/진행 중/시작 전인지 계속 추적
- 경계 콘텍스트 주의 : ex) "결제 3회 시도 후 실패 처리"라면 3회 재시도 로직은 **결제 서비스 내부에** 둬야 함
  - 1회 실패마다 오케스트레이터에 알리고 재시도 명령을 하달받는 게 아님. 시도 횟수 등 결제 처리 방법은 결제 서비스 경계 콘텍스트의 일부
  - 오케스트레이터는 결제가 완전히 성공/실패했는지만 알면 됨

> **TIP** 오케스트레이터의 경계 콘텍스트에는 최소한의 비즈니스 수행 로직만 포함시킬 것. 대부분의 비즈니스 로직은 대상 서비스에 구현하고 오케스트레이터는 워크플로 로직만 갖는다.

- 비오케스트레이터(워커) 마이크로서비스의 비즈니스 역할은 코레오그래피 패턴의 서비스와 정확히 동일

### 8.2.1 예제: 이벤트 기반 오케스트레이션

- 오케스트레이터가 각 서비스와 명령 스트림/응답 스트림 쌍으로 통신

<img width="582" height="281" alt="image" src="https://github.com/user-attachments/assets/77fef866-a9dc-4e50-b914-f0e7b3c9b411" />

> 이벤트 기반 오케스트레이션 워크플로. 오케스트레이터 ↔ 서비스 A/B/C가 각각 스트림-응답 스트림 쌍으로 연결

- 오케스트레이터는 A, B, C에 발행한 이벤트를 계속 구체화하면서 워커가 반환한 결과에 따라 내부 상태 업데이트

표 8-1 : 발행된 이벤트를 구체화한 내부 상태 예

| 입력 이벤트 ID | 서비스 A | 서비스 B | 서비스 C | 서비스 D |
|---|---|---|---|---|
| 100 | <결과> | <결과> | <결과> | 완료 |
| 101 | <결과> | <결과> | 전달됨 | 처리 중 |
| 102 | 전달됨 | null | null | 처리 중 |

- 이 결과를 바탕으로 워크플로 로직상 다음 단계를 선택, 완료되면 각 결과에서 필요한 데이터를 꺼내 최종 출력 조합
- A, B, C 작업이 서로 독립적이면 이벤트 전달 순서만 바꿔도 워크플로 변경 가능

```java
while (true) {
    Event[] events = consumer.consume(streams);
    for (Event event : events) {
        if (event.source == "Input Stream") {
            // 이벤트 처리, 구체화 상태 업데이트
            producer.send("Stream 1", ...)
        } else if (event.source == "Stream 1-Response") {
            producer.send("Stream 2", ...)
        } else if (event.source == "Stream 2-Response") {
            producer.send("Stream 3", ...)
        } else if (event.source == "Stream 3-Response") {
            // 결과 빌드
            producer.send("Output", ...)
        }
    }
    consumer.commitOffsets()
}
```

### 8.2.3 직접 호출 및 이벤트 기반 오케스트레이션 비교

이벤트 기반 워크플로
- 다른 이벤트 기반 서비스와 동일한 I/O 모니터링 도구 + 랙 기반 확장 기능 사용 가능
- 오케스트레이션 외부 서비스를 포함한 다른 서비스도 이벤트 스트림을 계속 소비 가능
- 보존성 우수 : 브로커를 통해 통신하므로 다른 서비스의 간헐적 실패에 영향 없음
- 재시도 장치 내장 : 실패 시 재시도할 이벤트가 스트림에 그대로 남아 있음

직접 호출 워크플로
- 스트림 생산/소비 오버헤드가 없어 일반적으로 빠름
- 간헐적 접속 문제를 오케스트레이터가 알아서 관리해야 함

정리
- 모든 종속 서비스가 SLA 범위 내에서 작동하면 직접 호출이 더 빠름 (실시간 등 신속 응답에 적합)
- 이벤트 기반은 보존성 좋은 I/O + 상대적으로 느리지만 안정적, 간헐적 실패에 강함
- 실제로는 혼용이 흔함 : **메인은 이벤트 기반 오케스트레이션 + 외부 API/기존 서비스는 직접 요청-응답**. 혼용 시 각 서비스가 실패 시 예상대로 처리되는지 꼼꼼히 확인

### 8.2.4 오케스트레이션 워크플로의 생성과 수정

- 오케스트레이터는 입출력 스트림과 요청-응답 결과를 구체화해 워크플로 이벤트 추적
- 워크플로가 오케스트레이션 서비스 내부에만 정의 → **한 군데서만 변경**, 부분 처리된 이벤트를 중단시키지 않고 변경 가능한 경우가 많음
- 오케스트레이션은 결과적으로 서비스를 단단하게 결합시킴 → 오케스트레이터와 워커 간 관계를 명확하게 정의
- **"유일신(single God)" 서비스 = 전형적 안티패턴** : 힘 없는 하위 서비스들에게 세부 명령을 내리는 구조
  - 워크플로 비즈니스 로직이 여기저기 흩어져 캡슐화 실패, 경계 콘텍스트 오정의, 소유권 확장 곤란
  - 오케스트레이터는 워커에게 완전히 책임을 위임하고 자신의 비즈니스 로직은 최소화

### 8.2.5 오케스트레이션 워크플로 모니터링

- 구체화 상태를 쿼리하면 워크플로 가시화 가능 → 특정 이벤트의 진행 상황과 이슈 파악 용이
- 오케스트레이터 레벨에서 모니터링/로깅 구현 → 장애 유발 이벤트 탐지

## 8.3 분산 트랜잭션

- 분산 트랜잭션 : 둘 이상의 마이크로서비스에 걸쳐 있는 트랜잭션
- 각 서비스는 자신의 분량을 처리하되, 중단되어 되돌아갈 경우 처리한 내용을 되돌림
- **이행(fulfillment)/역전(reversal) 로직은 반드시 동일한 마이크로서비스 안에** : 롤백 불가 시 새 트랜잭션 개시를 막고 관리 목적으로도 필요

> **WARNING** 분산 트랜잭션은 워크플로에 적잖은 리스크와 복잡도를 가중시키므로 가능한 한 삼가는 것이 좋다. 시스템 간 작업 동기화, 롤백 간소화, 일시적 인스턴스 장애 관리, 네트워크 연결 등 신경 써야 할 관심사가 한두 가지가 아니다.

- 가급적 구현하지 않는 게 최선이지만, 분산 트랜잭션이 없으면 오히려 리스크·복잡도가 커지는 경우엔 꼭 필요
- 이벤트 기반에서 분산 트랜잭션 = 보통 **사가(saga)**. 코레오그래피 또는 오케스트레이터 패턴으로 구현
- 참여 서비스는 자기가 처리한 분량을 알아서 되돌릴 수 있어야 하며, **정상 처리 액션과 복구 액션 모두 멱등적**이어야 함 (간헐적 실패에도 비일관 상태로 방치되지 않도록)

### 8.3.1 코레오그래피 트랜잭션: 사가 패턴

- 처리 중 장애 시 각 서비스가 자신의 변경 내용을 롤백할 수 있어야 함 → 느슨했던 서비스들이 단단히 결합되고 무관하던 서비스와 강한 의존이 생길 수 있음
- 적합한 곳 : **단순한 분산 트랜잭션, 특히 시간이 지나도 변경될 일이 거의 없는 강력한 워크플로**
- 진행 상황 모니터링이 어려움 (참여하는 각각의 스트림을 완전히 구체화해야 함)

코레오그래피 사가 예시 (A → B → C)
- A의 입력 스트림으로 트랜잭션 개시 → 세 서비스 작업이 모두 완료되거나, 도중 실패 시 전부 롤백
- C가 자기 분량을 소화 못 하면 → 이벤트를 발행하거나 이전 서비스 요청에 응답하는 식으로 **워크플로를 역전** → B, A가 처리한 부분을 차례로 되돌림
- A는 원래 컨슈머로서 실패한 트랜잭션 결과의 처분을 결정 (실패한 트랜잭션 스트림에 기록)
- 성공 상태는 C의 출력에서, 중단 상태는 A에서 나옴 → 컨슈머가 최종 상태를 완전히 파악하려면 **C의 출력 + A의 실패 트랜잭션 스트림을 모두 리스닝**해야 함

> **WARNING** 단일 작성자 원칙을 상기할 것. 두 개 이상의 서비스가 한 이벤트 스트림에 이벤트를 발행하면 안 된다.

- 진행 중/교착된 트랜잭션의 상태는 출력 스트림들만 봐서는 알 수 없음 → 각 스트림을 구체화하거나 서비스 내부 상태를 API로 표출해야 함
- 비트랜잭션형 워크플로만큼 변경이 어렵고 + 이전 서비스의 변경분 롤백 오버헤드까지 가중
- 순서가 매우 중요하고, 모니터링 어렵고, 취약한 편 → **워크플로 변경이 거의 없고 순서가 중요한 2~3개 서비스** 정도에 가장 적합

### 8.3.2 오케스트레이션 트랜잭션

- 워크플로의 어디서건 그 지점부터 트랜잭션을 되돌릴 수 있는 로직 추가 : 워크플로 역전 시 각 워커가 그에 따른 복구 액션을 제공
- 다양한 신호 지원 : 타임아웃(로컬 구체화 상태를 주기 체크해 처리 시간 파악), REST API를 통한 사람의 입력(취소 명령) 등
- 본질적으로 중앙 집중식 → 어떤 트랜잭션이라도 진행 상황·현재 상태를 자세히 모니터링 가능
- 워커의 값 반환, 타임아웃, 운영자 인터럽트로 어느 지점에서든 트랜잭션 중단 가능

- 롤백된 이벤트의 최종 처분(재시도, 폐기, 종료, 오류 이벤트 출력)은 오케스트레이터의 몫
- 오케스트레이터도 하나의 프로듀서로서 트랜잭션 실패 이벤트를 출력 스트림에 발행 → 다운스트림이 알아서 처리
  - 단일 작성자 원칙을 위배하지 않으면서 모든 출력을 소비할 수 있는 단일 스트림이 생김 (코레오그래피와의 차이)

> **WARNING** 각 마이크로서비스는 자신의 상태 변화도 전적으로 책임지며 롤백 이후 상태를 일관되게 맞추는 작업도 담당한다. 오케스트레이터가 할 일은 롤백 명령을 내리고 하위 워커의 확답을 기다리는 것이 전부다.

- 동일한 출력 스트림에 진행 중인 트랜잭션 상태를 표출해 워커가 결과 반환 시 트랜잭션 엔티티 업데이트 → 하부 트랜잭션 상태를 자세히 볼 수 있는 스트림 기반 모니터링
- 오케스트레이션 트랜잭션 : 워크플로 변경이 더 유연, 의존 관계가 잘 드러남 → 코레오그래피보다 명쾌한 모니터링. 인스턴스 자체는 추가 오버헤드지만 복잡한 워크플로에도 명확한 체계 제공

## 8.4 보상 워크플로

- 모든 워크플로를 완벽하게 되돌리고 트랜잭션 제약을 걸어야 하는 건 아님. 예측 불가한 이슈는 최선을 다해 완성도를 높이고, 실패하면 사후 조치로 타개
- 티켓 예약, 재고 기반 시스템에서 많이 쓰임
- ex) 수많은 동시 트랜잭션을 처리하는 판매 사이트 : 결제 후 재고 확인 시점에 물건이 품절
  - 엄격한 트랜잭션 처리 : 최근 트랜잭션 롤백 → PG 환불 + 품절 취소 통보 → 기술적으론 문제 없지만 기업 이미지·신뢰에 금
  - **보상 워크플로** : 새 재고를 주문하고 + 배송 지연을 알리고 + 사과의 뜻으로 할인 쿠폰 제공 → 고객이 취소할지 기다릴지 선택
- 공연 티켓, 항공사, 여행사가 흔히 쓰는 방식. 언제나 가능한 건 아니지만 **고객 대면 제품**의 분산 워크플로 처리에 유용할 때가 많음

> 보상이냐 엄격 롤백이냐는 결국 도메인이 정한다는 얘기. 커스터디처럼 자산이 걸린 트랜잭션은 쿠폰으로 무마가 안 되니 롤백/사가 쪽 설계가 강제되고, 알림·리포트류 워크플로는 보상으로 충분. 같은 회사 안에서도 워크플로마다 다르게 가져가야 한다는 게 포인트인 듯.

## 8.5 마치며

- 코레오그래피 : 비즈니스 단위와 워크플로 간 결합을 느슨하게. 서비스 수가 적고 작업 순서가 거의 안 바뀌는 단순한 (비)트랜잭션 워크플로에 적합
- 오케스트레이션 : 가시성·모니터링 우수, 더 복잡한 분산 트랜잭션 처리 가능, 한 곳에서 수정. 변경 가능성이 크고 독립적인 서비스가 많은 워크플로에 어울림
- 모든 시스템에 분산 트랜잭션이 필요한 건 아님. 실패 시 보상 액션이 필요할 수 있지만 그 처리 방법은 기술과 무관하게 고객 대면 이슈를 해결하는 비즈니스 성격에 따라 달라짐
