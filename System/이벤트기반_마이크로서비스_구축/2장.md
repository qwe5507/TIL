# 2장. 이벤트 기반 마이크로서비스 기초

## 이 장 핵심

이벤트 브로커가 데이터 통신의 메인 메커니즘이다. 브로커는 불변 로그로 이벤트를 보관해서 단일 진실 공급원 역할을 하고, 컨슈머는 오프셋 기반으로 각자 독립적으로 소비한다. 

메시지 브로커(소비하면 삭제)로는 이걸 대체할 수 없다. 

엔티티 이벤트 스트림을 순서대로 적용하면 테이블이 되고, 테이블 변경을 발행하면 스트림이 된다(테이블-스트림 이원성) — 이게 이벤트 기반에서 상태를 만드는 기본 원리.

---

## 2.1 토폴로지 구성

들어가기 전에, EDM의 기본 구성부터
- 이벤트 기반 마이크로서비스 : 특정한 경계 콘텍스트를 구현하기 위해 개발된 작은 애플리케이션
- 컨슈머 마이크로서비스 : 하나 이상의 입력 이벤트 스트림에서 이벤트를 소비/처리
- 프로듀서 마이크로서비스 : 다른 서비스가 소비할 수 있게 이벤트 스트림에 이벤트를 생산
- 일반적으로 하나의 서비스가 컨슈머이자 프로듀서 역할을 동시에 수행
- 상태 비저장(5장) / 상태 저장(7장) / 동기식 요청-응답 API 포함(13장) 서비스로 구분
- 이벤트 브로커 : 이벤트 스트림을 제공. 의미 있는 규모로 운영하려면 배포 파이프라인 + 컨테이너 관리 시스템(CMS)이 필수

토폴로지 : 문맥에 따라 두 가지 의미로 쓰임

### 2.1.1 마이크로서비스 토폴로지

- 마이크로서비스 **내부**의 이벤트 기반 토폴로지
- 인입된 이벤트에 수행할 데이터 주도 연산(변환, 저장, 방출 등)을 정의

<img width="588" height="222" alt="image" src="https://github.com/user-attachments/assets/7697cad1-fa4b-4c6a-b51e-dcca15e6e196" />

> 간단한 마이크로서비스 토폴로지. 스트림 A는 상태 저장소에 구체화하고, 스트림 B는 필터 → 변환 → 저장된 상태와 조인 → 출력 스트림으로 내보냄

### 2.1.2 비즈니스 토폴로지

- 복잡한 비즈니스 로직을 처리하는 마이크로서비스 + 이벤트 스트림 + API의 **집합**
- 서비스를 임의로 그룹핑한 것. 한 팀/부서가 소유한 서비스나 비즈니스 기능의 상위 집합을 나타냄
- 1장의 비즈니스 통신 구조가 비즈니스 토폴로지를 구성하는 요소
- 서비스는 비즈니스 경계 콘텍스트를 구현하고, 이벤트 스트림은 콘텍스트 간 도메인 데이터 공유를 위한 데이터 통신 수단

> **TIP (책 53쪽)** 마이크로서비스 토폴로지는 단일 마이크로서비스의 내부 작업에 초점, 비즈니스 토폴로지는 서비스 사이의 관계를 상술.

<img width="574" height="227" alt="image" src="https://github.com/user-attachments/assets/0f03ba0e-324a-460c-a25a-8d0ac13062f9" />

> 간단한 비즈니스 토폴로지. 서비스 1이 스트림 A를 소비/변환해 스트림 B로 발행, 서비스 2는 소비만 하면서 REST API 제공, 서비스 3은 변환 결과를 스트림 C로 발행

## 2.2 이벤트 콘텐츠

- 이벤트 = 비즈니스 통신 구조 범위에서 발생한 무엇이든 (송장 접수, 회의실 예약, 신입 채용...)
- 비즈니스에 중요한 일이라면 어떤 것이라도 이벤트가 될 수 있음
- 이벤트는 발생한 사건의 **기록물**
  - 애플리케이션 로그와 비슷하지만, 로그와 달리 기록물이면서 단일 진실 공급원
  - 발생한 사건을 정확하게 나타내는 데 필요한 모든 정보를 담아야 함

## 2.3 이벤트 구조

- 보통 키/값 포맷으로 표현
  - 값 : 이벤트의 전체 세부 정보 보관
  - 키 : 식별, 라우팅, 같은 키를 가진 이벤트의 집계에 사용. **필수 필드는 아님**

이 책에서 계속 쓸 이벤트 3종류

### 2.3.1 키 없는 이벤트

- 하나의 사실을 진술한 형태 (ex. 전자책 고객이 어떤 도서를 펼쳐봤다)

| 키 | 값 |
|---|---|
| N/A | ISBN: 372719, Timestamp: 1538913600 |

### 2.3.2 엔티티 이벤트

- 엔티티 = 유일한 것. 유일한 ID가 키로 부여됨
- 어느 시점의 엔티티 속성/상태를 기술 (비즈니스 콘텍스트에서 가장 일반적인 객체)
- 유일한 엔티티에 관한 모든 필요한 정보는 값 필드에

| 키 | 값 |
|---|---|
| ISBN: 372719 | Author: Adam Bellemare |

- 이벤트 기반 아키텍처에서 특히 중요
  - 엔티티 상태의 연속된 이력 제공 + 상태 구체화 용도
  - **마지막 엔티티 이벤트만 있어도 현재 상태를 알 수 있음**

### 2.3.3 키 있는 이벤트

- 키는 있지만 엔티티를 나타내지는 않는 이벤트
- 주로 이벤트 스트림 파티셔닝 → 한 파티션 내 데이터 지역성(data locality) 보장 용도

| 키 | 값 |
|---|---|
| ISBN: 372719 | UserId: A537FE |
| ISBN: 372719 | UserId: BB0012 |

- 키별로 집계하면 ISBN별 사용자 리스트 → 결국 키가 ISBN인 하나의 엔티티 이벤트로 귀결

## 2.4 엔티티 이벤트에서 상태를 구체화

**테이블-스트림 이원성(table-stream duality)** : 이벤트 기반에서 상태를 생성하는 기본 원리
- 엔티티 이벤트 스트림을 순서대로 적용 → 상태 저장 테이블 구체화(materialize)
  - 각 엔티티 이벤트는 키/값 테이블에 업서트(upsert)됨 → 키별로 가장 최근 이벤트를 알 수 있음
- 반대로 테이블의 각 업데이트를 이벤트 스트림에 발행 → 테이블을 엔티티 이벤트 스트림으로 변환

<img width="593" height="168" alt="image" src="https://github.com/user-attachments/assets/89e358c2-05a3-4e94-91a3-50f21beb4333" />

> 이벤트 스트림을 테이블로 구체화. AA, CC 모두 최근 값만 테이블에 남음

<img width="598" height="164" alt="image" src="https://github.com/user-attachments/assets/1613660c-3c1e-4159-b898-e694b47dca52" />

> 테이블에 적용한 변경에서 이벤트 스트림을 생성. BB 2회 + DD 1회 업서트 → 출력 스트림에 이벤트 3개

- 관계형 DB도 같은 원리
  - 생성/수정/삭제 커맨드를 로컬 붙임 전용(append-only) 파일에 기록 (ex. MySQL binlog)
  - 전체 로그를 재생하면 테이블과 데이터를 정확하게 되살릴 수 있음

> MySQL 복제 공부할 때 봤던 binlog가 여기서 다시 나온다. DB 복제나 CDC나 이벤트 소싱이나 결국 "변경 로그를 재생하면 상태가 복원된다"는 같은 원리를 다른 층위에서 쓰는 것.

> **TIP ** 테이블-스트림 이원성은 마이크로서비스 간의 상태 전달에 활용된다. 어떤 컨슈머라도 키 있는 이벤트 스트림을 읽어 자신의 로컬 상태 저장소에 구체화할 수 있음 → 프로듀서/컨슈머 서비스와 직접 결합하지 않고도 상태 공유 가능.

삭제와 컴팩션
- **툼스톤 이벤트** : 값을 null로 설정한 키 있는 이벤트. 키 있는 이벤트의 삭제 방법
  - "이 키는 삭제 대상"이라고 업스트림 프로듀서가 선언 → 다운스트림 컨슈머가 구체화한 저장소에서 삭제하라는 관례
- **컴팩션(compaction)** : 붙임 전용 불변 로그는 방치하면 무한정 커짐 → 브로커가 키별로 가장 최근 이벤트 하나만 보관하는 작업
  - 같은 키의 옛 이벤트 삭제, 살아남은 이벤트는 더 작고 새로운 파일들로 압착
  - 오프셋은 컨슈머가 따로 안 바꿔도 문제없게 관리됨
  - 이력은 포기하지만 디스크 사용량 감소 + 현재 상태 도달까지 처리할 이벤트 수 감소

<img width="580" height="227" alt="image" src="https://github.com/user-attachments/assets/638552f3-2d6f-41b2-b6db-6ef2bde669b3" />

> 컴팩션이 끝나면 키별 최근 레코드만 유지. 툼스톤 레코드와 그 이전에 쌓인 레코드는 모두 삭제

- 비즈니스 로직 처리를 위한 상태 유지는 이벤트 기반 아키텍처에서 지극히 일반적인 패턴
  - 과거의 비즈니스 결정은 항상 현재의 결정에 영향을 미침 (재고 수준, 매입 채무/매출 채권 추적 등)
  - 이벤트 스트림을 구체화해서 현재 상태를 나타낼 수 있어야 가능한 일들

## 2.5 이벤트 데이터 정의와 스키마

- 이벤트 데이터 = 통신 수단 + 구현체와 무관한 장기 데이터 보관소
- 프로듀서/컨슈머가 데이터의 의미를 똑같이 이해하는 게 중요
  - 이상적 : 컨슈머가 프로듀서에게 따로 물어보지 않고도 콘텐츠와 의미를 해석
  - 공통 언어가 필요 → 동기식 요청-응답 서비스의 API 정의와 비슷한 역할
- 스키마화 기술 (Apache Avro, Protobuf)이 제공하는 두 가지
  - **①** 진화 프레임워크 : 다운스트림 컨슈머가 코드 변경 없이도 스키마 변경을 안전하게 처리
  - **②** 정형 클래스(typed class) 생성 : 스키마화 데이터를 선택한 언어의 일반 객체로 변환 → 비즈니스 로직이 단순/투명해짐 (3장에서 상세)

## 2.6 마이크로서비스 단일 작성자 원칙

- 이벤트 스트림은 **정확히 하나의** 생산 마이크로서비스를 가짐 (그 스트림 이벤트의 소유자)
- 효과 : 어떤 이벤트라도 데이터 계통(lineage)을 따라가면 진실 공급원을 파악할 수 있음

## 2.7 마이크로서비스를 이벤트 브로커로 강화

- 이벤트 브로커 = 프로덕션에서 바로 서비스 가능한 EDM 플랫폼의 핵심
- 이벤트를 받아 큐 또는 파티션된 이벤트 스트림에 저장, 다른 프로세스가 소비할 수 있게 제공
- 이벤트는 논리적 의미에 따라 여러 스트림으로 나눠 발행 (DB에서 타입별로 테이블을 분리하는 것과 유사)
- 대기업용 이벤트 브로커는 거의 동일한 모델 : 분산 브로커 다수가 한 클러스터로 동작

클러스터 모델이 제공하는 필수 기능

| 기능 | 내용 |
|---|---|
| 확장성 | 브로커 인스턴스 추가로 생산/소비/스토리지 용량 증설 |
| 보존성 | 노드 간 데이터 복제 → 한 브로커 장애에도 데이터 보존 |
| 고가용성 | 클러스터링 → 장애 시 클라이언트가 다른 노드에 접속, 풀 가동 유지 |
| 고성능 | 여러 노드가 부하 분담. 초당 수십만 회 쓰기/읽기 처리 |

### 2.7.1 이벤트 보관 및 처리

브로커 하부 데이터 스토리지의 최소 요건

- **파티셔닝** : 스트림을 하위 스트림(파티션)으로 분할 → 여러 컨슈머 인스턴스가 병렬 처리해 처리량 확보. 큐는 파티셔닝이 필수는 아니지만 성능상 유리할 수 있음
- **순서 보장** : 파티션 내에서 데이터 순서는 반드시 보장. 발행된 순서대로 제공
- **불변성** : 발행된 이벤트는 수정 불가. 바꾸려면 새 이벤트를 발행
- **인덱싱** : 기록 시점에 오프셋 할당. 컨슈머는 다음 읽을 위치를 오프셋으로 특정
  - 컨슈머 랙(consumer lag) : 현재 인덱스와 마지막 인덱스의 간격 → 랙에 따라 컨슈머 수를 조절하거나 FaaS 로직 호출에 활용
- **무기한 보존** : 스트림에서 상태를 관리하려면 꼭 필요한 속성
- **재연성** : 어떤 컨슈머라도 필요한 데이터를 골라 읽을 수 있어야 함. 단일 진실 공급원의 근간이자 상태 공유의 기반

> 컨슈머 랙 기반 스케일링은 회사에서 SQS 지표(ApproximateNumberOfMessagesVisible) 보고 ECS 오토스케일링 거는 거랑 완전히 같은 발상. 브로커가 바뀌어도 운영 감각은 이어지는 듯.

### 2.7.2 추가 고려 사항

이벤트 브로커 선택 시 따져볼 것들

- **지원 도구** : 이벤트/스키마 조회, 쿼터·접근 제어·토픽 관리, 모니터링·처리량·컨슈머 랙 측정
- **호스티드 서비스** : 브로커 생성/관리 아웃소싱 가능 (Confluent Cloud, AWS MSK 등)
  - 모니터링/확장/DR/복제/멀티존을 호스팅 쪽이 제공하나? 벤더 종속은? 기술 지원은?
- **클라이언트 라이브러리와 처리 프레임워크** : 내가 쓰는 언어/도구를 무리 없이 지원하는지
- **커뮤니티 지원** : 기술 성숙도, 프로덕션 운영 가능 여부, 보편화 정도. 대표적 오픈소스는 아파치 카프카
- **장기 계층형 스토리지** : 오래된 세그먼트는 저렴한 스토리지(S3 등)로 → 계층 간 이동과 끊김 없는 조회가 지원되는지

## 2.8 이벤트 브로커 대 메시지 브로커

- 이벤트 브로커는 메시지 브로커 대신 쓸 수 있지만, 역은 성립하지 않음
- 메시지 브로커 : 발행/구독 메시지 큐로 네트워크 전체가 통신. 컨슈머가 처리하고 ACK되면 메시지는 즉시(또는 짧은 시간 내) 삭제
- 이벤트 브로커 : 순서대로 쌓은 사실 로그를 제공할 목적으로 설계

메시지 브로커로 불가능한 것 2가지
- **①** 메시지는 큐 단위로만 처리 → 여러 컨슈머가 같은 큐를 소비하면 각자 레코드의 하위 집합만 받음
  - 모든 이벤트의 전체 사본을 얻을 수 없음 → 상태를 정확하게 통신 불가
  - 이벤트 브로커는 레코드 장부를 딱 하나만 보관하고 인덱스로 개별 액세스 관리 → 독립적인 여러 컨슈머가 각자 필요한 이벤트를 마음대로 꺼냄
- **②** 소비 직후 삭제 → 무기한 보관 + 전역 접근 + 재연 가능한 단일 진실 공급원 제공 불가

> **TIP ** 이벤트 브로커는 순서가 보장되고 변경되지 않는 붙임 전용 사실 로그를 관리한다. 컨슈머는 필요시 로그의 특정 위치부터 소비해서 재처리할 수 있음. EDM 구축에 반드시 필요한 기능이지만 메시지 브로커로는 불가능.

- 물론 큐 방식도 EDM에서 중요한 역할 (파티션된 스트림으로는 구현하기 곤란한 접근 패턴 제공)
- 이 책의 나머지는 이벤트 브로커 사용법에 초점

### 2.8.1 불변 로그에서 소비

- 이벤트 브로커는 일반적으로 붙임 전용 불변 로그 사용
- 이벤트는 로그 끝에 추가되고 자동증가 인덱스 ID 부여
- 컨슈머는 인덱스 위치부터 접근해서, 요건에 따라 이벤트 스트림 또는 큐로 소비

이벤트 스트림으로 소비
- 각 컨슈머는 이전에 읽은 인덱스(= 오프셋)를 가리키는 자신만의 위치를 알아서 업데이트
- 오프셋 덕분에 여러 컨슈머가 같은 스트림에 접속해도 독립적으로 소비 + 진행 상황 추적

<img width="570" height="263" alt="image" src="https://github.com/user-attachments/assets/37a522a4-b9b1-413b-90d9-32b9f62e53eb" />

> 컨슈머 그룹과 파티션별 오프셋. 그룹0과 그룹1이 같은 스트림을 서로 다른 오프셋으로 독립 소비

- **컨슈머 그룹** : 여러 컨슈머를 하나의 동일한 엔티티로 나타낸 논리 단위 → 소비의 수평 확장
  - 새 컨슈머 합류 시 파티션 재할당, 각자 할당된 파티션의 이벤트만 소비
  - 특정 파티션은 주어진 컨슈머 인스턴스가 독점 소비
  - 그룹 내 활성 컨슈머 수 ≤ 파티션 수

큐로 소비
- 각 이벤트는 오직 하나의 마이크로서비스 인스턴스만 소비. 소비 완료된 이벤트는 '소비됨' 표시 후 다른 컨슈머에게 미제공
- 파티션 수 무관, 컨슈머 인스턴스 몇 개든 소비 가능
- 모든 이벤트 브로커가 큐를 지원하는 건 아님 (Pulsar 지원, Kafka 미지원)

<img width="562" height="229" alt="image" src="https://github.com/user-attachments/assets/b9810fd3-cd0b-4fc9-8aab-ec769e7df5e2" />

> 불변 로그를 마치 큐처럼 소비. 개별 오프셋 ACK로 구현

> **WARNING ** 큐에서 받은 이벤트는 순서가 보장되지 않는다. 병렬 소비 중 어떤 컨슈머가 처리 도중 실패하면 큐에 반환하고 다음 이벤트로 넘어갈 수 있기 때문.

### 2.8.2 단일 진실 공급원 제공

- 불변 로그는 단일 진실 공급원에 적합한 저장 메커니즘
- 브로커가 데이터 생산/소비의 유일한 장소 → 모든 컨슈머에게 반드시 똑같은 데이터 사본 전달
- **조직 문화도 달라져야 함**
  - 예전 : 팀마다 직접 SQL 쿼리로 모놀리스 DB 접근
  - 이제 : 모놀리스 데이터도 반드시 이벤트 브로커로 발행
  - 스트림과 모놀리스 DB 간 불일치 = 데이터를 생산한 팀의 과실 → 운영 개발자가 정합성 확인 책임
- EDM이 정착되면 브로커만 있어도 데이터 저장/조회가 가능한 서비스 개발 가능. 마이크로서비스는 이벤트 사본을 받아 로컬에서 비즈니스 처리

## 2.9 대규모 마이크로서비스 관리

- 서비스가 늘수록 관리가 어려워짐 : 서비스별 컴퓨팅 리소스, 데이터 스토리지, 구성, 환경 변수가 제각각 + 소유 팀별로 알아서 관리/배포 가능해야 함
- → 대부분 컨테이너화/가상화 기술을 관리 시스템과 함께 사용, 팀마다 단일 배포 단위로 커스터마이징

### 2.9.1 마이크로서비스를 컨테이너에 넣기

- 컨테이너 : 공유 커널 모델로 호스트 OS 활용, 환경 변수/라이브러리/디펜던시는 각자 설정
- 장점 : 빠른 시동, 작은 리소스 오버헤드 → 적은 비용으로 VM의 장점
- 단점 : OS 공유의 일장일단
  - 컨테이너형 앱은 호스트 OS에서 실행 가능해야 함 (특별한 OS가 필요하면 독립 호스트 필요)
  - 여러 컨테이너가 호스트 OS 액세스를 공유 → 커널이 뚫리면 전체 컨테이너가 위험 (공유 테넌시 모델의 보안 이슈)

### 2.9.2 마이크로서비스를 가상 머신에 넣기

- VM : 자기 완비형 OS + 하드웨어 가상화로 인스턴스를 완벽 격리 → 보안은 컨테이너보다 우수
- 단점 : 비용이 훨씬 비쌈, VM별 오버헤드 큼, 시동 느림, 설치 공간 큼. 사용 사례는 감소 추세

> **TIP ** gVisor, AWS Firecracker, Kata Containers 등 더 저렴하고 효율적인 VM 프로젝트가 진행 중. 기술이 발전하면 컨테이너보다 VM이 경쟁력 있는 대안이 될 수 있고, 보안이 중요한 환경이라면 주시할 분야.

### 2.9.3 컨테이너와 가상 머신 관리

- CMS(컨테이너 관리 시스템) : 컨테이너 배포, 리소스 할당, 하부 컴퓨팅 리소스 통합 담당
  - 쿠버네티스, 도커 엔진, 메소스 마라톤, 아마존 ECS, 노매드 등
- 마이크로서비스는 워크로드/SLA/성능 요건에 따라 규모 조절이 가능해야 함
  - 수직 확장(스케일 업) : CPU/메모리/디스크 조절
  - 수평 확장(스케일 아웃) : 인스턴스 추가/삭제
- 배포는 서비스당 하나의 단위로. 대부분 단일 컨테이너면 충분하지만, 여러 컨테이너를 한 차례 조작으로 배포/회수하는 장치(쿠버네티스 파드 등)도 필요
- VM 관리 도구는 아직 컨테이너보다 제한적. 컨테이너/VM 구분은 점점 모호해질 전망 → 필요한 기능을 CMS가 지원하는지 확인 필수

## 2.10 마이크로서비스 세금 납부

- 마이크로서비스 세금 : 아키텍처 도구/컴포넌트 구현에 드는 금전, 인력, 기회 비용 전부
  - 이벤트 브로커, CMS, 배포 파이프라인, 모니터링, 로깅 서비스, 배포/운영 비용 포함
- 지불 방식 2가지
  - 회사 상위 부서에서 전체 부담 → 확장성 있고 단순하고 일관된 프레임워크 확보
  - 개발팀마다 독립 지불 → 과도한 오버헤드, 솔루션 중복 도입, 도구 파편화, 지속 불가능한 성장
- 세금 납부는 사소한 문제가 아님. EDM 도입의 가장 큰 걸림돌이 될 때가 많음
  - 소규모 조직 : 모듈화한 모놀리스 등 요건에 더 알맞은 아키텍처가 최선일 수 있음
  - 대규모 조직 : 플랫폼 구축/유지보수 전체 비용을 장기 로드맵 대비 기대 효과로 따져봐야 함
- 그나마 최근엔 오픈소스/호스티드 서비스가 쉬워지고 도구들이 통합되면서 세금은 감소 추세

> "팀마다 독립 지불 → 도구 파편화" 부분은 남 얘기가 아니다. 큐 난립해서 eventType 라우팅으로 통합했던 것도 결국 세금을 뒤늦게 몰아서 낸 셈.
