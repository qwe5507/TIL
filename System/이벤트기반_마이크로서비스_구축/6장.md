# 6장. 확정적 스트림 처리

## 이 장 핵심

오프셋을 처음으로 되감고 재실행했을 때 처음과 똑같은 결과가 나오는가 — 이게 확정성이고, 이 장 전체를 관통하는 질문이다. 

파티션 하나 안에서는 오프셋 순서가 있지만 여러 스트림/파티션을 소비하는 순간 "다음에 뭘 처리할지"는 타임스탬프 기반 이벤트 스케줄링으로 정해야 한다. 

그리고 시간 진행을 추적하는 두 방식이 워터마크(플링크/스파크/빔)와 스트림 시간(카프카 스트림즈). 

무한 스트림에서 완벽한 확정성은 불가능하므로, 결국 지연 vs 정합성 트레이드오프를 비즈니스 요건으로 정하는 문제로 귀결된다.

---

## 도입 : 이 장이 답하려는 세 가지 질문

- **①** 여러 파티션에서 이벤트를 소비할 경우 처리 순서는 어떻게 정하는가?
- **②** 비순차 이벤트, 지각 이벤트는 어떻게 처리할까?
- **③** 준실시간 처리와 스트림 맨 처음부터의 재처리, 두 경우 모두 어떻게 확정적인 결과를 낼 수 있는가?

- 기존 서비스는 준실시간 처리 + 신규 서비스는 이력 데이터로 오프셋 캐치업, 이 혼합이 흔한 운영 형태 → 두 모드에서 결과가 같아야 함

## 6.1 이벤트 기반 워크플로의 확정성

- EDM의 두 가지 처리 상태
  - 실시간에 가까운 처리 : 실행 시간이 긴(long-running) 서비스
  - 과거부터 처리해 현재를 따라잡는(catch-up) 처리 : 신규 서비스
- 확정적 처리의 목표 : 오프셋을 최초 시점으로 되돌리고 재시작해도 **최초 실행과 똑같은 출력**
- 명백히 비확정적인 워크플로도 있음
  - 현재 월클럭 시간에 기반한 서비스
  - 외부 서비스를 쿼리하는 서비스 → 쿼리 시점마다 결과가 달라질 수 있고, 외부 상태가 독립적으로 업데이트되면 확정성 보장 불가
- 이상적 조건(모든 이벤트 제때 도착, 지연 0, 장애 없음)은 현실에 없음 → 확정적인 결과를 내도록 "최선을 다하는" 것. 그것만으로도 대부분의 요건은 충족됨

## 6.2 타임스탬프

- 스트림에 저장된 이벤트는 오프셋 + 타임스탬프를 둘 다 가짐
  - 오프셋 : 컨슈머가 어디까지 읽었는지
  - 타임스탬프 : 이벤트가 언제 생성됐는지 → 처리 시점의 선후 관계 파악

| 시간 | 정의 |
|---|---|
| 이벤트 시간(event time) | 이벤트 발생 시점에 프로듀서가 부여한 로컬 타임스탬프 |
| 브로커 인입 시간(broker ingestion time) | 브로커가 부여. 대부분 이벤트 시간을 쓰지만, 프로듀서 시간을 신뢰하기 어려우면 대용 가능 |
| 컨슈머 인입 시간(consumer ingestion time) | 이벤트가 컨슈머에 인입된 시간 |
| 처리 시간(processing time) | 컨슈머가 처리를 완료한 월클럭 시간 |

- 카프카 기준 `log.message.timestamp.type` = CreateTime(기본) / LogAppendTime 두 값으로 조절

<img width="599" height="294" alt="image" src="https://github.com/user-attachments/assets/756585ba-c92f-4c43-9db3-1a4f7cea51db" />

> 프로듀서 → 브로커 → 컨슈머로 흐르며 각 시점(이벤트 시간, 브로커 인입, 컨슈머 인입, 처리 시간)이 찍히는 위치

### 6.2.1 분산 타임스탬프 동기화

- 독립된 두 시스템의 클럭을 정확히 맞추는 건 물리적으로 불가능 (소자 공차, 온도 편차, 가변적인 네트워크 지연)
- 그래도 "거의" 동기화는 가능하고 대부분의 컴퓨팅 목적엔 충분
- 주로 NTP 서버와 동기화. 클라우드 벤더는 위성 연결된 원자 시계 활용
  - LAN에서 오차 15분당 수 ms 수준. 개방형 인터넷에선 ±100ms까지 왜곡
  - NTP 동기화는 곧잘 실패함 : 네트워크 장애, 설정 오류, NTP 서버 무응답, VM 멀티테넌시 영향
- 자주 동기화하면 소소한 순서 꼬임은 남아도 생성/인입 시간의 일관성은 아주 높아짐

### 6.2.2 타임스탬프 찍힌 이벤트 처리

- 오프셋으로 순서 비교는 **단일 파티션 내에서만** 가능. 실제로는 여러 스트림에서 받아 처리하는 게 일반적 → 타임스탬프 필요

예제 : 은행 예금/인출 스트림
- 잔고가 $0 미만이면 초과 인출 수수료 부과. 예금 스트림과 인출 스트림이 분리돼 있음
- 라운드 로빈처럼 단순하게 소비하면 $10 예금 → $25 인출(수수료 발생!) → $20 예금 순으로 잘못 처리될 수 있음
- 실제 발생 순서($10 예금 → $20 예금 → $25 인출)면 수수료 없이 잔고 $5

## 6.3 이벤트 스케줄링과 확정적 처리

- 이벤트 스케줄링 : 여러 입력 파티션에서 소비할 때 **다음에 처리할 이벤트를 선택**하는 프로세스
- 파티션 내에서는 오프셋 순서가 원칙이지만, 파티션끼리는 이벤트 시간 기준으로 정확히 인터리빙해야 함

> **TIP** 할당된 전체 입력 파티션에서 타임스탬프가 가장 오래된 이벤트부터 하나씩 다운스트림 처리 토폴로지에 전달하는 것이 가장 일반적인 이벤트 스케줄링 구현 로직.

- 스케줄링은 스트림 처리 프레임워크의 기능이고, 기본 컨슈머 구현체엔 보통 없음

> **WARNING** 비즈니스 로직에서 이벤트 소비/처리 순서가 중요하다면 마이크로서비스에 이벤트 스케줄링 코드를 직접 구현해야 한다.

### 6.3.1 맞춤 이벤트 스케줄러

- 아파치 삼자(Samza)의 MessageChooser 인터페이스 : 스트림 간 우선순위, 월클럭/이벤트 시간, 메타데이터, 콘텐츠 등으로 선택 로직 구현 가능
- 단, 맞춤 스케줄러 대부분은 속성 자체가 비확정적 → 재처리 시 재연 가능한 결과를 못 만들 수 있음. 직접 구현 시 주의

### 6.3.2 이벤트 시간, 처리 시간, 인입 시간에 따라 처리

- 타임스탬프로 쓸 시점 선택 : 로컬 이벤트 시간 vs 브로커 인입 시간 (둘 다 워크플로에서 한 번씩만 발생. 월클럭/컨슈머 인입 시간은 실행 시점마다 달라짐)
- 정상 상태면 네 시점의 차이는 길어야 수 초. 과거 이벤트를 처리 중이면 이벤트 시간과 컨슈머 인입 시간은 완전히 벌어짐
- 저자 경험 : **로컬 시스템이 할당한 이벤트 시간이 가장 정확**. 프로듀서 타임스탬프를 신뢰할 수 없고 해결도 안 되면 브로커 인입 시간이 차선

### 6.3.3 컨슈머의 타임스탬프 추출

- 타임스탬프 추출기(timestamp extractor) : 소비한 이벤트에서 타임스탬프를 꺼냄 (페이로드의 키/값/메타데이터에서 획득)
- 추출기가 세팅한 이벤트 시간을 컨슈머 프레임워크가 처리 내내 사용

### 6.3.4 외부 시스템에 요청-응답 호출

- 이벤트 기반 토폴로지에서 외부 시스템에 비이벤트 요청을 하면 비확정적 결과 가능
- 외부 시스템은 관리 주체가 밖에 있어 내부 상태와 응답이 얼마든지 바뀔 수 있음. 중요한지는 비즈니스 요건에 따라 평가

## 6.4 워터마크

- 워터마크 : 처리 토폴로지를 흐르면서 이벤트 시간의 진행 상황을 추적, "시간 t 이전의 모든 데이터는 처리 완료됐다"고 선언하는 신호
- Spark, Flink, Samza, Beam 등에서 통용 (더 깊게는 구글 백서 참고)
- 워터마크를 수신한 노드는 내부 이벤트 시간을 업데이트하고 의존 노드에 차례로 전파

<img width="582" height="163" alt="image" src="https://github.com/user-attachments/assets/530e85c8-1dd3-4b6b-bb7d-ccd5eaca490f" />

> 노드 간 워터마크 전파. 시간 t 이전의 모든 이벤트가 처리됐음을 다운스트림에 알림

### 6.4.1 병렬 처리 시 워터마크

- 여러 독립 컨슈머 인스턴스 간의 이벤트 시간 조정 수단
- 흐름 : 소스 함수에서 워터마크 생성(파티션 소비 지점) → 증가하는 이벤트 시간을 기록해 다운스트림으로 → 수신 노드는 시간 업데이트 후 새 워터마크를 재생성해 전파
- 여러 입력을 받는 노드(aggregate 등)의 이벤트 시간 = 추적 중인 **모든 입력 시간 중 최솟값**
- 키가 같은 이벤트를 같은 다운스트림 인스턴스로 보내는 셔플 작업 수반
- 워터마크는 "그보다 과거인 이벤트는 지각으로 간주하라"는 사실만 알림. 노드의 이벤트 스케줄링에는 영향 없음

<img width="602" height="369" alt="image" src="https://github.com/user-attachments/assets/490cbb98-a3cb-41d3-ae0c-76c51c63aa02" />

> 여러 처리기로 구성된 토폴로지의 노드 간 워터마크 전파 (groupByKey → aggregate, 셔플 포함)

> **TIP** 스파크/플링크/빔 같은 대용량 프레임워크는 전용 리소스 클러스터를 구성한다. 이 경우 리파티션(셔플)은 이벤트 브로커의 스트림이 아니라 클러스터 내부 통신을 사용할 것.

## 6.5 스트림 시간

- 카프카 스트림즈가 쓰는 방식. 컨슈머 애플리케이션이 토폴로지의 **스트림 시간 = 처리된 이벤트 중 가장 높은(최근) 타임스탬프**를 유지
- 할당된 각 파티션에서 이벤트를 버퍼링 → 스케줄링 알고리즘으로 다음 이벤트 선택 → 스트림 시간보다 크면 업데이트. **절대 줄어들지 않음**
- 각 이벤트를 완전히 처리한 뒤 다음 이벤트 처리 (깊이 우선, 하위 토폴로지당 한 번에 하나)
  - 각 노드가 독립적으로 버퍼링하며 시간을 갱신하는 워터마크 방식과의 근본적 차이

<img width="565" height="265" alt="image" src="https://github.com/user-attachments/assets/9f766ab8-c0ec-4442-b031-f6bc06f213dc" />

> 여러 입력 스트림에서 소비할 경우의 스트림 시간. 두 입력 버퍼 중 이벤트 시간이 가장 작은 것부터 처리

### 6.5.1 병렬 처리 시 스트림 시간

- 워터마크 방식과 가장 큰 차이 : 리파티션된 이벤트를 **내부 이벤트 스트림을 통해 브로커에 회송** → 다시 소비
  - 대용량 클러스터의 셔플과 기능은 같지만 전용 클러스터가 필요 없음 → 카프카 스트림즈가 마이크로서비스 친화적인 이유
- 리파티션 시 이벤트 시간은 현재 월클럭으로 덮어쓰지 않고 **그대로 유지**
  - 리파티션은 기존 이벤트의 논리적 이동일 뿐. 시간을 다시 쓰면 원래 순서가 완전히 파괴됨
- 리파티션 스트림이 있으면 토폴로지가 둘로 쪼개져 하위 토폴로지마다 자체 스트림 시간을 유지, 병렬 처리 가능

<img width="584" height="325" alt="image" src="https://github.com/user-attachments/assets/f6ab9021-cf7c-40c1-9146-754d30da709c" />

> 리파티션 이벤트 스트림을 통한 이벤트 셔플링. 하위 토폴로지 0/2가 리파티션 이벤트를 생산하는 동안 1/3이 소비하며 취합

> **TIP** 워터마크 방식에서도 리파티션 이벤트 스트림을 쓸 수 있다. 아파치 삼자는 카프카 스트림즈와 유사한 단독형 모드를 제공하되 스트림 시간 대신 워터마크를 사용.

## 6.6 비순차 이벤트와 지각 이벤트

- 비순차 이벤트 : 스트림에서 자기 앞의 이벤트보다 타임스탬프가 **작은** 이벤트
- 유한 데이터 세트(배치) : 전체 배치를 하나의 큰 윈도로 간주 → 비순차에 유연, 거의 확정적. 대신 지연이 큼 (전통적 야간 배치)
- 무한 데이터 세트(스트림) : 설계 단계에서 지연 vs 확정성 요건을 고려해야 함
  - "내 마이크로서비스가 비즈니스 요건상 비순차/지각 이벤트를 처리해야 하나?"를 반드시 자문
  - 비순차 처리는 비즈니스 수준에서 구체화하고, 지연/확정성 중 우선순위 결정

> 이벤트 스트림 파티션에 인입된 비순차 이벤트

> **TIP** 하나의 파티션에 있는 이벤트는 타임스탬프와 관계없이 항상 오프셋 순서대로 처리해야 한다. 따라서 언제라도 비순차 이벤트가 발생할 수 있다.

- 지각 여부는 **소비하는 마이크로서비스의 관점에서만** 판단 가능. 같은 비순차 이벤트도 서비스마다 지각 판정이 다를 수 있음 (몇 시간 지나야 지각으로 보는 관대한 서비스도 존재)

### 6.6.1 워터마크와 스트림 시간이 늦은 이벤트

- 워터마크 방식 : 이벤트 t'가 워터마크 W(t) 이후 도착하면 지각 → 해당 노드가 알아서 처리
- 스트림 시간 방식 : 이벤트 t'가 스트림 시간이 t로 증가한 이후 도착하면 지각 → 하위 토폴로지의 각 처리기가 알아서 처리
- 요약 : **이벤트는 컨슈머가 정한 데드라인을 지키지 못했을 경우에만 늦은 것**

### 6.6.2 비순차 이벤트의 원인과 영향

- **비순차 데이터에서 소싱** : 이미 순서가 어긋난 스트림이나 타임스탬프가 안 맞는 외부 시스템에서 소싱
- **여러 프로듀서 → 여러 파티션** : 여러 프로듀서가 여러 출력 파티션에 쓰면 발생. **기존 스트림을 리파티션할 때도 발생**
  - 예 : 제품 조회 이벤트를 사용자 ID로 키 재지정(세션 분석용) → 두 인스턴스가 각자 스트림 시간을 유지하며 서로 동기화하지 않음 → 시간 왜곡(skew) → 출력 스트림에 비순차 이벤트 포함
  - 파티션 크기 불균형, 처리율 차이, 백로그가 클수록 심해짐 → 이전엔 순서가 맞던 데이터도 어긋남

### 6.6.3 시간에 민감한 함수와 윈도잉

- 기간별 취합, 시간 경과 트리거 등 시간 기반 비즈니스 로직에서 지각 이벤트는 중요한 관심사
- 지각 이벤트 = 어느 기간의 비즈니스 로직 처리가 완료된 **이후에** 도착한 이벤트
- 윈도잉 : 이벤트를 시간에 따라 그룹핑. 무한 스트림에 연산을 하려면 논리적 컴포넌트(윈도)로 분할 필요

> **TIP** 윈도잉은 이벤트 시간, 처리 시간 둘 중 하나로 할 수 있지만 비즈니스 애플리케이션은 이벤트 시간을 더 많이 사용한다.

| 윈도 | 특징 | 답할 수 있는 질문 |
|---|---|---|
| 텀블링(tumbling) | 크기 고정, 이전/이후 윈도와 겹치지 않음 | "사용자가 제품을 가장 많이 이용하는 시간대는?" |
| 슬라이딩(sliding) | 크기 고정 + 윈도 슬라이드라는 증분 단계만큼 서로 겹침 | "지난 한 시간 동안 내 제품을 클릭한 사용자 수는?" |
| 세션(session) | 크기가 동적. 활동 없으면 타임아웃 시 종료, 재개되면 새 세션 | "이 브라우저 세션 동안 사용자가 무엇을 보았나?" |

- 윈도 사용 시 비순차 이벤트를 반드시 고려 : 얼마나 기다려야 "너무 늦었다"고 볼지 정해야 함
- **모든 이벤트를 빠짐없이 수신했다고 단정할 수 없는 것이 스트림 처리의 근본적 한계** → 어느 시점에서는 포기가 필요
- 고려 사항 : 상태를 얼마나 저장할지, 지각 발생 가능성, 지각 이벤트 미사용 시 비즈니스 영향

## 6.7 지각 이벤트 처리

- 처리 전략은 데이터 중요도에 따라 다름 → 기술 솔루션 전에 **비즈니스 수준에서 결정**
  - 금융 거래, 시스템 장애 : 어디에 위치하든 반드시 처리
  - 단순 측정 지표 : 폐기해도 그만
- 기다릴수록 확정성↑ 지연↑ → SLA 빡빡한 애플리케이션엔 부정적. 마이크로서비스는 서비스별로 이 특성을 따로 조율할 수 있는 유연성 제공

| 전략 | 동작 |
|---|---|
| 이벤트 폐기(drop) | 그냥 버림. 윈도가 닫히면 모든 시간 기반 집계 완료 |
| 대기(wait) | 일정 시간 윈도 결과 출력을 유예. 지연을 늘려 확정성을 높임. 정해진 시간까지 이전 윈도를 업데이트 가능하게 유지 |
| 유예 기간(grace period) | 윈도 완료 즉시 결과를 출력하되, 유예 기간 동안 윈도를 열어둠. 지각 이벤트가 도착할 때마다 집계를 업데이트해 새 값을 출력 |

지각 이벤트 가이드라인을 정할 때 던져볼 질문
- 지각 이벤트 발생 가능성은? / 얼마나 기다려야 하나? / 누락 시 비즈니스 영향은? / 오래 기다리면 비즈니스에 뭐가 이로운가? / 상태 유지에 디스크·메모리가 얼마나 필요한가? / 기다리는 비용이 혜택을 능가하나?

## 6.8 재처리 대 준실시간 처리

- 재처리 : 컨슈머 그룹 오프셋을 되감아 임의 시점부터 처리를 재연. 불변 스트림이 제공하는 기능이자 모든 EDM 설계의 중요 항목
- 이벤트 시간 기반 서비스에서만 수행. 월클럭 시간 기반 집계/윈도잉 서비스엔 안 씀
- 이벤트 스케줄링이 준실시간 처리와 동일한 순서를 보장하는 핵심. 브로커를 통한 리파티션은 순서가 어긋날 수 있어 비순차 처리도 재처리의 중요한 부분

재처리 절차 5단계
- **① 시작점 결정** : 상태 저장 컨슈머는 각 스트림의 맨 처음부터 재처리하는 게 모범 사례. 특히 엔티티 스트림엔 중요한 팩트가 들어 있음
- **② 리셋할 컨슈머 오프셋 결정** : 엉뚱한 위치에서 시작하면 정확한 상태 보장 불가. 상태 저장 처리에 쓸 스트림은 맨 처음으로 (은행 잔고 재처리 중 이전 수표를 누락하면?)
- **③ 데이터량 확인** : 소요 시간, 병목 지점 확인. 브로커 I/O 독점 방지용 쿼터 할당, 대량 출력 시 다운스트림에 사전 통보, 오토스케일링 꺼져 있으면 수동 확장
- **④ 재처리 시간 고려** : 중단 시간 미리 계산. 재처리 동안 다운스트림에 김빠진 데이터가 흘러가도 되는지 확인. 인스턴스를 늘려 병렬도 최대화 → 끝나면 다시 축소
- **⑤ 영향도 검토** : 재처리 중 하지 말아야 할 일 확인. ex) 배송 완료 이메일 서비스가 재처리하면서 메일을 한 번 더 보내면 끔찍한 사용자 경험

> ⑤번은 뼈 때리는 항목. 알림/이메일 같은 부수 효과가 있는 컨슈머는 재처리 = 재발송이 돼버린다. 멱등 처리나 "재처리 모드에서 부수 효과 스킵" 같은 장치를 설계 단계에서 넣어야지, 재처리하기로 한 날 발견하면 늦다.

## 6.9 간헐적 실패와 지각 이벤트

- 준실시간 처리 중에는 지각으로 판정될 이벤트가, **재처리 시점에는 스트림 안에 예상대로 들어 있음** → 두 모드의 결과가 달라지는 원인
- 감지하기 어려운 편차지만, EDM의 연결된 특성과 "업스트림 문제가 다운스트림에 미치는 영향"을 잘 보여줌

## 6.10 프로듀서/이벤트 브로커 연결 문제

- 시나리오 : 이벤트는 타임스탬프 순서대로 생성되는데 프로듀서가 브로커에 접속 불가
  - 프로듀서는 수차례 재시도 → 성공 또는 실패 (최선은 누군가 감지하도록 "시끄럽게" 실패)
  - 그동안 스트림 A는 계속 소비돼 워터마크/스트림 시간은 증가, 스트림 B는 새 데이터가 없다고 여겨짐
- 접속 복구 후 밀린 이벤트를 발행 → 실제 이벤트 시간 순서는 맞지만 월클럭 지연 탓에 **준실시간 컨슈머는 지각 이벤트로 처리**
  - 재처리하는 컨슈머에게는 늦은 이벤트가 아님 (스트림 안에 제 위치로 존재)

## 6.11 마치며

- 무한 이벤트 스트림 + 간헐적 실패의 조합에서는 본질적으로 완벽한 확정성 달성 불가 → 가장 합리적인 솔루션은 지연과 정합성의 트레이드오프가 최적인 지점
- 준실시간 처리와 재처리 모두에서 최선의 확정성을 얻기 위한 이벤트 선택(스케줄링) 방법을 다룸
- 비순차/지각 이벤트는 신중히 고려할 설계 요소. 워터마크와 스트림 시간으로 식별/처리
