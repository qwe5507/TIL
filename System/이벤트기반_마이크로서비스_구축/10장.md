# 10장. 기본 프로듀서/컨슈머 마이크로서비스

다루는 주제
- BPC(기본 프로듀서/컨슈머)의 정의와 특징
- BPC가 알맞은 용도 4가지 (레거시 통합, 게이팅 패턴, 데이터 레이어 위임, 독립 확장)
- 하이브리드 BPC (외부 스트림 처리 프레임워크 활용)

## 이 장 핵심

BPC = 고급 기능 없이 "받아서 → 로직 태우고 → 저장/발행"만 하는 맨몸 컨슈머. 즉 우리가 평소 만드는 평범한 @SqsListener 서비스 그 자체다. 이 장의 질문은 하나 — "그 맨몸으로 어디까지 되나?" 답은 "생각보다 꽤 많이 된다"이고, 되는 목록 4개(레거시 옆에 붙이기, 다 모이면 출발, DB한테 위임, 처리/데이터 확장 분리) + 안 될 때의 우회로 1개(외주 = 하이브리드)가 이 장의 전부. 조인·시간 창·스케줄링이 필요해지는 순간이 "직접 만들지 말고 프레임워크 검토하라"(11~12장)는 신호다.

---

## 10.0 도입

- BPC : 하나 이상의 이벤트 스트림에서 이벤트를 받아 비즈니스 로직을 적용하고, 필요시 출력 스트림에 내보내는 마이크로서비스 (동기식 요청-응답 I/O도 섞을 수 있음, 13장)
- "기본(basic)"이 붙은 이유 = **없는 것** 때문
  - 이벤트 스케줄링(여러 스트림 시간 맞추기), 워터마크(시간 창 마감 선언), 구체화 메커니즘·체인지로그(로컬 상태 자동 백업/복구), 로컬 상태 기반 수평 확장 — 전부 없음
  - 이런 건 카프카 스트림즈/플링크 같은 완전한 기능의(full-featured) 프레임워크의 영역 (11~12장)
  - 직접 라이브러리로 만들 수도 있지만, 그 전에 맨몸으로 요건이 충족되는지부터 확인할 것
- 그래도 BPC가 사랑받는 이유
  - 아무 언어로나 쉽게 구현 → EDM 입문자의 진입 장벽(인지 오버헤드)이 낮음
  - 워크플로 전체가 한 서비스 코드 안에 다 보임 → 이해하기 쉬움
  - 컨테이너로 감싸서 CMS로 배포하면 끝

## 10.1 BPC의 알맞은 용도는?

- 프레임워크 내장 기능은 없지만 폭넓은 요건을 소화함
- 잘 맞는 것 : 확정적 스케줄링이 필요 없는 상태 저장 패턴, 상태 비저장 변환 같은 단순한 패턴
- BPC는 일반적으로 로컬(내부)보다 **외부 상태 저장소**를 씀
  - 이유 : 로컬에 상태를 두면 서버가 죽고 살 때마다 복구를 직접 해야 하는데, 그 복구를 자동화해주는 게 프레임워크(체인지로그)고 맨몸 컨슈머엔 그게 없음
  - 외부 DB에 두면 백업/복구는 DB가 알아서 하고, 어느 인스턴스든 똑같이 접근 가능

### 10.1.1 기존 레거시 시스템과 통합

- 레거시 코드베이스에 프로듀서/컨슈머 클라이언트를 심어서 이벤트 기반 세계에 편입시키는 것. EDM 도입 초기에 흔하고, 4장 전환 전략의 일부
- 레거시는 자기 데이터를 스트림에 생산하고, 필요한 건 다른 스트림에서 소비
- 레거시 코드를 아예 못 건드리는 경우 → **사이드카 패턴** : 본체는 그대로 두고 옆에 붙인다

예시: 사이드카 패턴
- 과거 : 쇼핑몰 프런트엔드가 스케줄 배치로 백엔드 데이터를 긁어와 자기 저장소와 동기화

- 잘 쓰면 레거시 코드를 거의 안 고치고 신기능 추가 가능

### 10.1.2 이벤트 순서와 무관한 상태 저장 비즈니스 로직

- 많은 비즈니스가 "**어떤 순서로 오든 상관없는데, 전부 도착해야 진행**"이라는 요건을 가짐 = **게이팅 패턴(gating pattern)**
  - 게이팅 = 여닫이 문. 조건이 다 차야 문이 열림
- 순서를 안 따지니 워터마크 같은 시간 장치가 필요 없음 → 맨몸 컨슈머로 충분. BPC의 대표 유스케이스

예시: 도서 출판 — 원고, 표지, 단가 셋이 어떤 순서로 오든 상관없지만, 셋 다 있어야 인쇄소로 보냄
- 원고 도착 → 원고 테이블에 저장 → "표지랑 단가 테이블에도 이 책(ISBN) 있나?" 조회 → 없으면 그냥 끝
- 나중에 단가 도착 → 저장 → 조회 → 아직 표지 없음 → 끝
- 마지막으로 표지 도착 → 저장 → 조회 → **셋 다 있음!** → 도서 이벤트 발행

<img width="598" height="359" alt="image" src="https://github.com/user-attachments/assets/18d8dfa2-bef1-4e43-9ad2-1d3a3345b3e4" />

> 그림 10-3: 도서 준비 상태를 게이팅. ISBN별 콘텐츠/표지/단가 테이블(외부 상태 저장소)을 검사해 셋 다 모이면 출력

- 그림에서 ...0010은 셋 다 모여 이미 발행됐고, ...0011은 표지가 없어 대기 중
- 실무의 "A 이벤트랑 B 이벤트 둘 다 완료돼야 다음 단계" 요건이 정확히 이 패턴. 키별 테이블 업서트 + 도착 시 나머지 조회 구조라 순서 보장 없는 SNS/SQS에서도 그대로 됨

> **TIP** 게이팅 패턴에서 사람이 명시적으로 승인하는 단계가 필요할 수도 있다. 13.5절의 '예: 신문 발행 워크플로(승인 패턴)'에서 상세히.

### 10.1.3 데이터 레이어가 너무 많은 일을 하는 경우

- 어려운 로직을 DB가 다 해주는 경우에도 BPC가 적합 : 지리공간 검색, 자유 텍스트 검색, 머신러닝/AI
- ex) "이 좌표에서 제일 가까운 매장 찾기" — 어려운 건 지리공간 쿼리인데 그건 데이터 레이어 몫. 스크랩한 신제품을 배치 훈련된 ML 분류기로 분류하는 것도 마찬가지
- 이때 컨슈머는 이벤트 받아서 쿼리 날리고 결과를 발행하는 **배달부** 역할(단순한 통합 메커니즘)일 뿐 → 배달부는 맨몸이어도 충분

### 10.1.4 독립적으로 처리 및 데이터 레이어 확장

- 처리량과 데이터 크기는 따로 논다 : 낮엔 트래픽 몰리고 밤엔 한산(수면/기상 패턴)해도, 데이터는 밤에도 그대로 있어야 함

예제: 이벤트 집계로 사용자 이용 프로파일 구축
- 사용자 행동 이벤트를 24시간 세션으로 집계해 인기 제품 파악/판촉에 활용. 세션 끝나면 저장소에서 방출(flush)되어 출력 스트림으로 나가고 공간 회수
- 보관 데이터 : 키 = userId, timestamp / 값 = List(productId), 외부 저장소에
- 밤 : 처리 파워가 거의 필요 없음 → 인스턴스를 확 줄여 비용 절감
  - 파티션 어사이너가 입력 파티션들을 남은 인스턴스에 재할당 → 한 대로도 전체 사용자 이벤트 소비 가능
  - 단, 이벤트량이 줄어도 사용자 데이터 자체는 그대로 → **처리 규모를 줄여도 상태 크기는 안 줄어듦**. 상태가 외부 DB에 있으니 서버 수와 무관하게 유지되는 것
- 낮 : 인스턴스 추가로 부하 처리. DB 조회 비용도 늘지만 캐싱/파티셔닝/배칭으로 완만하게 유지 가능
- 한 줄로 : **처리는 오토스케일링으로 늘였다 줄였다, 상태는 DB가 계속 들고 있기** — 확장 축의 분리

> **TIP** 구글, 아마존, 마이크로소프트 같은 서비스 공급사는 이런 패턴에 딱 맞는, 확장성 좋은 유료 읽기/쓰기(pay-per-read/write) 데이터 저장소를 제공한다.

## 10.2 하이브리드 BPC 애플리케이션으로 외부 스트리밍을 처리

- 맨몸으로 안 되는 일(대규모 조인, 복잡한 집계)이 생기면? → 그 부분만 외부 스트림 처리 프레임워크에 **외주**를 주는 패턴
- 비즈니스 로직이 BPC와 외부 프레임워크 사이에 나뉘어 있는 하이브리드 구조. 11장의 대용량 프레임워크는 간단한 통합만으로 붙일 수 있어 잘 맞음
- BPC는 자기 언어의 기능/라이브러리를 그대로 쓰면서, 혼자서는 도저히 못 할 작업을 얹을 수 있음
  - ex) 로컬 저장소에 결과 적재 + 요청-응답 쿼리 제공은 BPC가, 여러 스트림의 복잡한 집계는 외부 프레임워크가

### 10.2.1 예제: 외부 스트림 처리 프레임워크를 이용해 이벤트 스트림 조인

- 대용량 스트림 조인에 특화된 프레임워크의 조인 기능만 빌려 쓰는 BPC
- 외부 처리기가 하는 일 : 스트림을 테이블로 구체화해서 키가 같은 로우끼리 조인

- 진행 방식 : BPC가 호환 클라이언트로 외부 프레임워크에 작업을 제출("이 두 스트림 조인해서 결과를 중간 스트림에 넣어줘") → 프레임워크가 소비/조인해 중간 스트림에 생산 → BPC는 그 중간 스트림을 평범하게 소비
- = 이벤트 스트림 포맷으로 결과를 돌려주는 외부 서비스에 작업을 아웃소싱하는 설계

> 그림 10-5: 중간 이벤트 스트림을 통해 결과를 다시 BPC로 돌려보내는 하이브리드 워크플로. ① BPC 시동 → ② 중간 스트림 생성 → ③ 스트림 처리 로직 제출 → ④ 처리기가 중간 스트림에 기록 → ⑤ BPC가 중간 스트림(+다른 스트림) 소비 → ⑥ 비즈니스 로직에 따라 출력 생산

> **TIP** BPC는 외부 스트림 처리 작업을 실행하기 위해 클라이언트를 인스턴스화한다. BPC가 종료되면 좀비 프로세스가 남지 않도록 외부 스트림 처리 인스턴스도 함께 종료해야 한다.

- 장점 : 혼자서는 어려운 스트림 처리 기능을 마이크로서비스에서 활용. KSQL처럼 SQL로 스트림 작업하는 게 주요 유스케이스. 경량/대용량 프레임워크 양쪽에서 자주 쓰임
- 단점 : 복잡도 증가 — 이게 외주의 비용
  - 외부 프레임워크를 테스트 환경에 통합해야 해서 테스트가 훨씬 복잡 (15장)
  - 가동부가 늘어나 오류 가능성·디버깅·개발 복잡도 증가
  - 경계 콘텍스트 관리도 어려워짐 → 배포/롤백/작업을 쉽게 관리할 방안 필요

## 10.3 마치며

- BPC 패턴은 단순하지만 강력. 상태 저장/비저장 이벤트 기반의 수많은 마이크로서비스 패턴의 근간
- 유연함 : 비즈니스 처리 대부분이 데이터 레이어에서 일어나는 구현체와 궁합이 좋고, 스트림-레거시 인터페이스로도, 확장하면 외부 스트림 처리 시스템 연계로도 활용
- 한계 : 워낙 기본만 있어서 상태 구체화, 이벤트 스케줄링, 타임스탬프 기반 의사결정이 필요해지면 라이브러리에 투자해야 함 → 그 시점이 "직접 만들 것인가, 11~12장의 특화 솔루션을 도입할 것인가"를 결정할 타이밍
