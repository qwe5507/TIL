# 9장. FaaS 응용 마이크로서비스
## 이 장 핵심

함수는 몇 분 살다 반드시 죽는 실행 단위고, 죽을 때 연결과 로컬 상태도 함께 사라진다. 

그래서 24시간 상주 컨슈머에서 당연하던 것들이 하나씩 깨진다 — 상태는 외부에 두고, 오프셋 커밋은 처리 완료 후에 하고, 순서가 필요하면 동기 오케스트레이션으로 줄을 세워야 한다. 

EDM 원칙 자체는 그대로인데 "짧은 수명 + 무상태"라는 제약이 추가된 버전.

---

## 9.0 도입

- FaaS(functions-as-a-service) : 서버리스 솔루션. 인프라 오버헤드 관리 없이 기능을 구축/관리/배포/확장
- 함수 : 특정한 트리거 조건이 발생하면 실행되는 코드 조각. 시작 → 실행 → 작업 완료 시 종료
- 부하에 맞게 실행 함수 개수를 늘리고 줄이기 쉬움 → 부하가 매우 가변적인 상황에 기민하게 대응
- 함수는 "정기적으로 실패하는 기본 컨슈머/프로듀서 구현체"로 이해하면 빠름
- **미리 정해진 시간이 지나면 항상 종료되고 모든 연관된 연결과 상태도 함께 사라짐** → 설계 시 주의

> 이 장 전체가 "상주 Spring 컨슈머를 몇 분 살다 죽는 일회용 프로세스로 바꾸면 뭐가 깨지나?"라는 질문 하나로 압축된다. 아래 규칙들 전부 "죽으면 다 잃는다"에서 파생됨.

## 9.1 함수 기반 솔루션을 마이크로서비스로 설계

### 9.1.1 엄격한 경계 콘텍스트의 멤버십 관리

- 함수와 내부 이벤트 스트림은 반드시 어떤 경계 콘텍스트에 속해야 함 → 함수/데이터의 소유자가 분명하게 식별됨
- 마이크로서비스는 대부분 경계 콘텍스트와 1:1 매핑, 여러 함수를 한 콘텍스트에서 쓰는 n:1도 흔함
- 함수를 너무 잘게 쪼개면 경계선이 흐려짐

실용적인 관리 방법
- 데이터 저장소를 외부 콘텍스트에서 보이지 않게 보호
- 다른 콘텍스트와 결합할 경우 표준 요청-응답 또는 이벤트 기반 인터페이스 사용
- 어떤 함수가 어떤 콘텍스트에 속하는지(함수-제품 1:1 매핑) 메타데이터로 엄격하게 관리
- 경계 콘텍스트에 매핑된 리포지터리 내부에서 함수 코드 관리

### 9.1.2 처리 완료 이후에만 오프셋 커밋

- 주어진 이벤트(배치)가 처리 완료된 이후에만 오프셋을 커밋하는 것이 FaaS 모범 사례

| 커밋 시점 | 특징 |
|---|---|
| 함수 처리 완료 후 | 비FaaS 솔루션과 동일한 전략. **적어도 한 번 이상 처리를 가장 강력하게 보장**. 대신 중복 가능 → 멱등으로 방어 |
| 함수 처음 시작 시 (배치 전달 직후) | 프레임워크의 재시도/알림 기능에 의존. 처리 추적이 쉬워 코레오그래피로 다른 함수를 호출하는 함수가 주로 사용. 재시도 소진 시 **데이터 손실** → 데드-레터 큐로 보내거나 버림. 손실에 민감하면 삼갈 것 |

> - 오프셋 커밋 = SQS로 치면 메시지 삭제 (= "처리했음" 도장)
> - 도장을 먼저 찍고 일하다 죽으면 → 처리된 걸로 기록된 채 **유실**
> - 일 끝내고 찍으면 → 죽어도 다음 인스턴스가 재처리 (대신 **중복**)
> - 결론 : 손실 vs 중복 중 중복을 골라라. 중복은 멱등으로 막을 수 있지만 유실은 복구 불가
> - Lambda + SQS는 사실상 후자 계열 (maxReceiveCount 초과 시 DLQ) → 손실 민감하면 DLQ + 재처리 절차까지 세트

### 9.1.3 적을수록 좋다

- "단일 함수를 쉽게 작성해 여러 서비스에 재사용"이라는 장점을 곧이곧대로 따르면 → 콘텍스트 안에서 무슨 일이 벌어지는지 파악 곤란한 매우 파편화된 솔루션
- 함수 소유권 모호 + 변경 시 다른 서비스에 미칠 영향 불확실. 버저닝은 도움이 되지만 제품마다 다른 버전 관리 시 충돌 가능
- 저자 경험 : **잘게 나눈 함수 여럿보다 함수를 적게 두는 편이 낫다**. 하나만 테스트/디버깅/관리하는 게 훨씬 간편

## 9.2 FaaS 공급자 선택

- 무료 오픈소스 : OpenWhisk, OpenFaaS, Kubless 등 기존 CMS 활용 옵션. 아파치 펄사는 브로커 연동 FaaS 기본 제공
- 서드파티(AWS, GCP, Azure) : 매력적이지만 **자사 상용 이벤트 브로커에 특화**된 프레임워크 제공. 세 업체 모두 브로커 보존 기간이 7일로 제한되는 점이 문제 (카프카는 토픽별 무기한 보존 가능)
- 오픈소스 브로커 + 상용 클라우드 통합(카프카 커넥트 등)도 가능하지만 설정/관리가 만만치 않음. 이미 구독 중인 클라우드가 있으면 첫 실험 오버헤드는 낮음

## 9.3 함수를 마이크로서비스로 개발

함수 기반 솔루션의 4대 컴포넌트 : **함수, 입력 이벤트 스트림, 트리거 로직, 메타데이터를 이용한 에러/확장 정책**

```java
public int myfunction(Event[] events, Context context) {
    println("hello world!");
    return 0;
}
```

- `events` : 처리할 이벤트 배열. 각 이벤트에 key, value, timestamp, offset, partition_id
- `context` : 함수명, 이벤트 스트림 ID, 함수의 잔여 수명 등 콘텍스트 정보

함수-트리거 맵 (FaaS 프레임워크 내부에서 관리)

| 함수 | 이벤트 스트림(들) | 트리거 | 정책과 메타데이터 |
|---|---|---|---|
| myFunction | myInputStream | onNewEvent | < ... > |

- 정책과 메타데이터에 들어가는 것 : 컨슈머 그룹, 컨슈머 프로퍼티(배치 크기, 배치 윈도), 재시도/에러 처리 정책, 확장 정책

> **TIP** 함수 기반 마이크로서비스 구현체는 다른 비FaaS 마이크로서비스처럼 각자 독립적인 컨슈머 그룹을 가진다.

- 함수 코딩 규칙, 관리, 트리거 메커니즘은 공급사/구현체마다 조금씩 다름 → 프레임워크 문서 필독

## 9.4 콜드 스타트, 웜 스타트

함수가 트리거돼서 실제 첫 줄을 실행하기까지의 준비 과정
- **①** 컨테이너(실행 환경)를 새로 시작
- **②** 코드 로드 (JVM이면 JVM 부팅 + 클래스 로딩까지)
- **③** 초기화 : 이벤트 브로커 연결, 필요한 외부 리소스에 클라이언트 접속
- **④** 준비 완료 → 이벤트 처리 시작

- 콜드 스타트 : ①~③을 전부 거쳐야 하는 기본 상태. 함수가 처음 시작되거나 꽤 오랜 휴지기 이후
- 웜 상태 : ①~③이 끝나 이벤트를 처리할 수 있는 상태. 작업 완료/만료 시 일시 중지되어 동면 상태가 됨
- 대부분의 FaaS 프레임워크는 가능하면 종료된 함수를 재사용 : 동면 사이에 브로커 연결이나 상태 저장소 접속이 해제되지 않는 한, 일시 중지된 인스턴스를 재활용해 곧바로 처리 재개

> - 체감 : 실제 로직 50ms + 콜드 준비 몇 초. Java Lambda 첫 호출이 유독 느린 이유 = ②③(JVM+스프링 부팅)이 무거움
> - 핸들러 밖(static)에 DB 클라이언트 선언하는 관례가 이것 때문 → 콜드 때 한 번 만들고 웜에선 재사용
> - 단, 동면은 영원하지 않음 (리소스 필요하면 예고 없이 추방) → 웜의 로컬 상태·커넥션은 운 좋으면 남는 것. **믿고 설계할 계약이 아님**
> - 웜 컨테이너는 동시에 한 요청만 처리 → 요청이 웜 수를 넘으면 초과분은 전부 콜드 = 부하 튈 때마다 내는 숨은 세금

## 9.5 트리거로 함수 시동

- 트리거 : 함수에게 처리를 시작하라고 알리는 장본인. 상주 서버는 스스로 폴링하지만 죽어 있는 함수는 누군가 깨워야 함

### 9.5.1 새 이벤트에 반응해 트리거: 이벤트-스트림 리스너

- 스트림에 이벤트가 생성될 때 트리거. 미리 정의된 컨슈머 배후에서 이벤트 소비를 분리 → 개발자가 작성할 오버헤드 코드가 적음
- 이벤트는 스트림에서 순서대로 배열 형태로, 큐에서 소비하면 순서 없는 묶음 형태로 함수에 직접 삽입
- 스트림-함수 다중 매핑 가능 (하나의 함수가 여러 스트림 소비)
- 상용 3사는 자사 브로커 전용 트리거만 제공, 오픈소스 브로커 직접 트리거는 미지원 → 카프카 커넥트가 서드파티 FaaS 함수를 트리거해 외부 리스너 역할

- 함수 결과는 데이터 출력 + 함수 성공 추적 용도로 자신의 스트림에 출력 가능
- 동기 트리거 : 함수가 다음 이벤트 발행 전에 완료돼야 함 → **처리 순서 유지**에 필수, 대신 병렬 처리 제약
- 비동기 트리거 : 여러 함수에 여러 이벤트 전달 → 순서 미유지, 순서가 안 중요한 경우에만
- **배치 크기** : 최대 몇 개 이벤트를 처리하라고 보낼 것인가 / **배치 윈도** : 바로 트리거하지 않고 추가 이벤트를 얼마나 기다릴 것인가 → 함수 시작 오버헤드를 여러 레코드에 분산

```java
public int myEventfunction(Event[] events, Context context) {
    for (Event event : events) {
        try {
            println(event.key + ", " + event.value);
        } catch (Exception e) { ... }
    }
    // 배치 처리가 완료됐음을 FaaS 프레임워크에 알림
    context.success();
    return 0;
}
```

> **TIP** 컨테이너형 마이크로서비스와 마찬가지로, 트리거는 스트림의 최신 오프셋, 초기 오프셋, 아니면 그 중간 어디서든 이벤트 처리를 시작하도록 설정할 수 있다.

> - Lambda의 SQS/Kinesis 이벤트 소스 매핑이 정확히 이 패턴
> - 배치 크기/윈도 = BatchSize / MaximumBatchingWindowInSeconds
> - 발상 : 깨우는 것 자체가 비싸니(콜드 스타트) 한 번 깨울 때 여러 개 쥐여주자

### 9.5.2 컨슈머 그룹 랙에 반응해 트리거

- 랙(lag) : 컨슈머가 읽은 위치(현재 오프셋) ↔ 스트림 헤드(최신 오프셋)의 차이 = 밀린 일의 양
- 컨슈머 그룹 오프셋을 주기적으로 폴링해 랙을 계산 → 모니터링 프레임워크에 보고 → 임계 초과 시 FaaS 프레임워크가 함수 시작 지시
- 랙이 크면 함수 인스턴스 여러 개, 작으면 하나로 백로그 처리. 랙 크기와 함수 시작 간의 관계를 조정해 SLA 준수
- 스트림 리스너와의 중요한 차이 : **함수가 시작될 때까지 이벤트를 소비하지 않으며**, 시작된 함수가 브로커 연결·이벤트 소비·오프셋 커밋을 전부 스스로 처리

```java
public int myLagConsumerfunction(Context context) {
    String consumerGroup = context.consumerGroup;
    String streamName = context.streamName;
    EventBrokerClient client = new EventBrokerClient(consumerGroup, ...);
    Event[] events = client.consumeBatch(streamName, ...);
    for (Event event : events) { doWork(event); }
    client.commitOffsets();   // 브로커에 오프셋 커밋
    context.success();        // 성공을 FaaS 프레임워크에 알림
    return 0;
}
```

- 너무 자주 트리거하면 마지막 실행 이후 함수가 웜 상태일 가능성이 높아지고, 매번 브로커 연결 + 리밸런스·콜드 스타트 때문에 인스턴스당 처리량이 감소

> - 비유 : 리스너 트리거 = "택배 오면 바로 문 두드려주는 경비실" / 랙 트리거 = "우편함에 10통 이상 쌓이면 알람 → 직접 나가서 꺼내옴"
> - 랙 = SQS의 ApproximateNumberOfMessagesVisible
> - 랙 크기로 인스턴스 수 조절 = SQS 큐 깊이 지표로 ECS 오토스케일링 거는 것과 같은 발상
> - 어울리는 용도 : 실시간일 필요 없는 작업을 **"덜 자주, 크게 몰아서"**

### 9.5.3 스케줄에 따라 트리거

- 일정 주기/지정 날짜에 시작. 소스 스트림을 폴링해 새 이벤트를 가져와 처리하거나 그대로 종료
- SLA 유지엔 짧은 폴링 주기가 필요하지만 너무 잦으면 FaaS 프레임워크·브로커에 과도한 부담. 클라이언트 코드는 랙 트리거 예제와 동일

### 9.5.4 웹훅에 반응해 트리거

- 함수를 직접 호출해 트리거. 모니터링 프레임워크, 스케줄러, 서드파티 애플리케이션과의 맞춤 연계에 사용

### 9.5.5 리소스 이벤트에 반응해 트리거

- 리소스 변경이 트리거 : 저장소의 로우 생성/수정/삭제, 파일 시스템의 파일 생성/수정/삭제 등
- EDM에서는 대부분 이벤트가 스트림을 거치므로 흔치 않지만, 외부 데이터 소스와 연계할 때(FTP 등 파일 서비스로 파일이 들어오는 경우) 아주 요긴

## 9.6 비즈니스 업무를 함수로 처리

FaaS가 잘 맞는 경우
- 상태를 저장하지 않고, 여러 스트림을 확정적으로 처리할 필요가 없고, 큐 방식으로 처리하는 경우 등 **확장의 폭이 매우 넓은 단순한 토폴로지**
- 양이 매우 가변적 → 필요할 때마다 수평 확장 + 신속한 리소스 프로비저닝/해제
- **동시성과 확정성이 관심사가 아닌 경우**에 아주 잘 동작
- 확정성이 문제가 되면 이벤트 스케줄러를 제공해야 함 (기본 컨슈머 솔루션과 동일). 코파티션된 데이터는 한 번에 하나의 함수로만 처리해야 일관됨

## 9.7 상태 관리

- 함수는 수명이 짧아 상태 저장 FaaS 솔루션에는 **외부 상태 저장 서비스가 필수**
- FaaS 공급사는 데이터 위치와 무관한 빠른 확장이 목표 → 일반적으로 '무 로컬 상태(no local state)' 정책 강제
- 웜 상태에서 시작된 함수는 이전 로컬 상태를 쓸 수 있을지도 모르지만 **보장은 없음** → 어떤 상태든 함수가 명시적으로 저장/조회

> **TIP** 해당 경계 콘텍스트 외에는 어떤 것도 접근하지 못하게 함수의 상태 접근 권한을 엄격하게 관리할 것.

- Azure Durable Functions처럼 견고한 상태 저장 함수를 지원하는 프레임워크도 등장 : 상태 관리를 추상화하고 로컬 메모리를 외부 저장소에 자동 저장 → 상태 워크플로 표준화. 선택한 프레임워크의 개선 동향을 주시

## 9.8 함수에서 다른 함수 호출

- 함수 간 통신 : 이벤트 기반 비동기 통신, 요청-응답 호출, 또는 혼합. 다중 함수 솔루션은 흔히 코레오그래피/오케스트레이션 패턴 사용

> **TIP** 비순차 처리 문제를 방지하려면 다음 이벤트를 처리하기 전에 현재 이벤트를 반드시 처리 완료해야 한다.

### 9.8.1 이벤트 기반 통신 패턴

- 한 함수의 출력을 이벤트 스트림에 넣어 다른 함수가 소비. 경계 콘텍스트는 여러 함수 + 내부 스트림으로 구성

<img width="575" height="167" alt="image" src="https://github.com/user-attachments/assets/f572c961-8c69-4e0e-9bdd-f165a8d42017" />

> 그림 9-3: 여러 함수로 구성된 이벤트 기반의 FaaS 토폴로지가 하나의 마이크로서비스를 나타낸다

- 내부 스트림은 콘텍스트 외부 접근 불가. 같은 콘텍스트의 함수들은 동일한 컨슈머 그룹 사용
- 장점 : 함수가 각자 작업 후 오프셋 커밋(자기 컨슈머 그룹 오프셋 관리), 스트림 처리 외 함수 간 조정 불필요, 코레오그래피·오케스트레이션 모두 적용 가능, **처리 중 실패해도 브로커에 이벤트가 남아 재처리 → 데이터 손실 없음**

### 9.8.2 직접 호출 패턴

- 함수가 자기 코드에서 직접 다른 함수를 호출. 파이어 앤 포겟(fire-and-forget) 비동기 / 반환값을 기다리는 동기

**코레오그래피와 비동기 함수 호출**
- 함수는 비즈니스 로직에 따라 다음 함수를 호출하고, 실패/오류 등 다음 단계 처리는 다음 함수와 FaaS 프레임워크에 위임 → 호출을 간단히 연쇄(chaining)

<img width="557" height="115" alt="image" src="https://github.com/user-attachments/assets/58ecf0db-f4d0-43e8-a3c8-cef2f807aebf" />

> 그림 9-4: 경계 콘텍스트 내부의 코레오그래피 비동기 함수 호출

- 함수 A는 배치를 처리하면서 B를 호출하고 자기 컨슈머 오프셋을 업데이트한 뒤 종료. B는 계속 처리해 출력 스트림에 생산
- 중요한 단점 두 가지
  - **처리가 성공할 경우에만 오프셋이 업데이트된다는 보장이 안 됨** : B는 A에 피드백을 주지 않으므로 B가 실패해도 A는 이미 커밋. 이벤트 손실이 대수롭지 않은 워크플로면 무시 가능
  - **순서가 어긋날 수 있음** : B를 여러 번 호출하면 독립 실행되는 B 인스턴스들이 경합 → 먼저 끝나는 순서대로 꼬임. 이벤트별 호출을 배치 단위 호출로 바꿔도 A가 배치 내 이벤트를 B보다 먼저 처리하므로 여전함
- 순서대로 처리하려면 각 이벤트마다 다음 이벤트 처리 전에 A→B 완료를 강제해야 함. A가 쓴 데이터에 B가 의존하고 둘 다 같은 외부 저장소에서 작동하면 특히 비확정적 결과 위험 → 동기 호출 오케스트레이션 고려

**오케스트레이션과 동기 함수 호출**
- 함수를 동기 호출해 결과를 기다린 뒤 나머지 로직 수행 (8장 오케스트레이션 패턴의 함수 구현)

<img width="576" height="218" alt="image" src="https://github.com/user-attachments/assets/a7b706b6-7c2b-43dc-8e21-682c895b5238" />

> 그림 9-5: 경계 콘텍스트 내부의 오케스트레이션 동기 함수 호출

```java
public int orchestrationFunction(Event[] events, Context context) {
    for (Event event : events) {
        // 동기식 함수 호출
        Result resultFromA = invokeFunctionA(event);
        Result resultFromB = invokeFunctionB(event, resultFromA);
        Output output = composeOutputEvent(resultFromA, resultFromB);
        producer.produce("Output Stream", output);
    }
    context.success();  // 컨슈머 오프셋 업데이트 알림
    return 0;
}
```

- A, B를 차례로 호출하고 결과 대기 (A의 출력을 B의 입력으로 전달 가능). 각 이벤트가 다음 이벤트 시작 전에 완료 → **오프셋 순서 확실히 보장**
- 트리거 방식 : 이벤트 스트림-트리거(배치 단위) / 큐-트리거(이벤트마다 고유한 오케스트레이션 함수, 개별 커밋, 도중 실패 시 다음 인스턴스가 픽업)

> 함수 간 통신 선택지 정리
> - 기본값 : 사이에 스트림을 끼워라 (9.8.1) — 서비스 사이에 SQS 끼우는 이유와 동일
> - 순서·정합성 중요 : 동기 오케스트레이션으로 줄 세우기
> - 비동기 체이닝 : 로그 적재처럼 손실·순서가 아무래도 좋은 곳에만

## 9.9 종료 및 중단

- 함수는 작업을 마치거나 할당된 수명(일반적으로 5~10분)이 끝나면 종료. 일시 중지 → 동면 → (리소스/시간 제약으로) 동면에서 추방되기도
- 종료 전 할당된 리소스와 열린 커넥션의 처리 방침을 정해야 함
  - 컨슈머 클라이언트라면 함수 인스턴스에 파티션이 할당돼 있음 → 회수하지 않고 끝내버리면 타임아웃까지 컨슈머 그룹 소유권이 재할당되지 않아 처리 지연 (해당 파티션 이벤트는 리밸런스나 인스턴스 복귀까지 하나도 처리 안 됨)
- 판단 기준
  - 거의 항상 온라인으로 처리하는 함수 : 연결을 끊고 리밸런스할 필요 없음 (동면 후 즉시 복귀 가능성 높음)
  - 가끔씩 실행되는 컨슈머 함수 : **모든 연결을 끊고 파티션 할당을 해제하는 게 최선**. 의심스러우면 연결을 깔끔히 정리 → 외부 저장소·브로커 부하 경감 + 중지된 함수의 파티션 소유권 주장 가능성 감소

## 9.10 함수 튜닝

### 9.10.1 넉넉한 리소스 할당

- 함수마다 CPU/메모리 개별 할당 : 과하면 비용, 부족하면 뻗거나 처리 시간 증가
- **최대 실행 시간** : 처리 시간과 이벤트 수는 거의 비례 → 배치 크기와 밀접. 주어진 배치 처리 예상 최대 시간보다 높게 설정해 불필요한 타임아웃 에러 예방
- 경계 콘텍스트 내 상태 저장소의 외부 I/O도 고려 : 일정한 I/O형 / 산발적 I/O형 워크로드에 따라 리소스 부족 시 처리량·성능 저하

### 9.10.2 배치 이벤트 처리 매개변수

- 할당된 배치를 다 처리 못 하면 실행 실패로 간주 → 배치 재처리. 실행 시간/배치 크기를 안 바꾸면 또 실패할 확률 높음 → 둘 중 하나 조치
  - 함수의 최대 실행 시간을 늘린다
  - 함수가 처리할 이벤트의 최대 배치 크기를 줄인다

> **TIP** 자체적으로 브로커에 연결해 소비하는 함수는 실행 도중 오프셋을 주기적으로 커밋할 수 있어 배치를 부분 완료할 수 있다. 하지만 함수에 소비된 배치를 전달받는 경우에는 처리 중 오프셋을 업데이트할 방법이 없어 불가능하다.

- 이벤트 리스너 트리거 시스템 활용 : 실패 시 배치 크기를 자동으로 둘로 나눠 재실행 (제시간에 마칠 때까지 이등분 반복)

## 9.11 FaaS 솔루션 확장

- FaaS는 작업 병렬화, 특히 **처리 순서가 중요하지 않은 큐/스트림에서 진가** 발휘. 순서가 중요하면 다른 구현체처럼 최대 파티션 수까지만 병렬화 가능
- 확장 정책은 프레임워크 고유 영역 : 컨슈머 입력 랙, 시간대, 처리량, 성능 특성 기반 옵션
- 스스로 브로커에 접속하는 함수는 컨슈머 그룹 가입/탈퇴 시 리밸런스 영향도 주의
  - 너무 잦은 가입/탈퇴 → 그룹이 거의 항상 리밸런스 상태 → 작업 진행 불가
  - 최악엔 리밸런스 교착(rebalance deadlock) : 함수들이 파티션을 할당받았다 도로 뺏기면서 수명만 소진
  - 배치 크기가 작은 단명(short-lived) 함수 다수 + 지연에 너무 민감한 확장 정책이 악화 요인 → 단계적 확장 정책, 이력 루프(hysteresis loop)로 과도한 리밸런스 늪 방지
- **정적 파티션 할당** : 리밸런스 오버헤드 제거 + 코파티션 용도. 함수가 자기 파티션을 미리 알고 시작 → 리밸런스가 전혀 없고 트리거될 때마다 그냥 소비. 대신 파티션별 소비 상태·함수 동작을 개발자가 더 주의 깊게 관찰해야 함

> **WARNING** 스래싱 트리거(thrashing trigger)와 확장 정책에 유의할 것. 파티션 할당을 너무 자주 리밸런스하면 브로커 비용이 많이 든다. 몇 분마다 한 개 정도로 함수 개수를 늘리거나 줄여볼 것.

> 함수가 초 단위로 우르르 생겼다 죽으면 브로커는 "누가 어느 파티션 맡지?"를 계속 다시 정하느라 일은 안 하고 회의만 하는 셈. 증감은 천천히.

## 9.12 마치며

- FaaS 프레임워크는 함수로 마이크로서비스를 구축하도록 개발/관리/배포/트리거/테스트/확장 도구 제공. 함수는 새 이벤트, 컨슈머 그룹 랙, 월클럭 시간, 맞춤 로직으로 트리거됨
- 함수 기반 솔루션이 특히 유용한 곳 : 이벤트 스케줄링이 필요 없는 상태 비저장, 또는 상태는 저장하지만 단순한 비즈니스 문제
- 오케스트레이션 패턴을 쓰면 여러 함수를 정확한 순서로 호출 + 이벤트 순서도 보장
- FaaS는 빠르게 성장/발전 중 → 관심 플랫폼의 최신 동향을 계속 주시할 것
